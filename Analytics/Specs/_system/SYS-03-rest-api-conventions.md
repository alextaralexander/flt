## 1. Цель и область действия

- **Цель**: задать единые правила REST API монолита — пути и версии, методы и коды ответов, конверт ошибок и коды ошибок, пагинацию, сортировку и фильтры, идентификаторы, дату и время, локаль, идемпотентность, оптимистическую блокировку, лимиты, заголовки, аутентификацию, оформление и сверку контрактов OpenAPI, вывод из эксплуатации — так, чтобы сгенерированный клиент фронтенда (ADR-005) и будущие нативные мобильные клиенты работали с любым модулем одинаково, а контракт в ТЗ оставался источником истины (spec-first).
- **Область действия**: backend (все роутеры `/api/v1/<module>`, shared kernel `app/core/http`), frontend (генерация клиента и моков из контрактов), tests (контрактные тесты), CI (job `contracts`, правила Spectral в `src/tools/contracts/.spectral.yaml`). Служебные эндпоинты вне `/api` (`/v1/health`, `/v1/ready`, `/v1/metrics`, `/asyncapi/kafka`) регулируются только требованием SYS-03-R25.
- **Действует с этапа**: 1 (первые роутеры — `identity` и `llm_gateway`, этап 1 Г.5 и Г.6).
- **Уточняет**: CLAUDE.md, разделы «Взаимодействие» (REST), «Backend-сервис (boilerplate)» (конверт `ErrorResponseV1`), «Маршрутизация через HAProxy»; ADR-004 (раздел 3.2 REST, 202 для фоновых операций), ADR-003 (`version` и 409, UUID v7, `created_at`/`updated_at`), ADR-006 (cookie и Bearer, коды ошибок аутентификации), ADR-012 (пути без переписывания, `X-Request-ID`, ответы HAProxy без конверта), ADR-011 (job `contracts`).

## 3. Требования

### SYS-03-R1 Префикс пути `/api/v1/<module>`

- **Формулировка**: каждый REST-роутер модуля должен монтироваться с префиксом `/api/v1/<module>`, где `<module>` — имя модуля из карты модулей SYS-01, в котором символ `_` заменён на `-` (`llm_gateway` → `/api/v1/llm-gateway`, `learning_plan` → `/api/v1/learning-plan`, `identity` → `/api/v1/identity`); единственное исключение — дополнительный префикс `/api/v1/auth` модуля `identity`.
- **Обоснование**: ADR-004, раздел 3.2 (префикс `/api/v1/<module>`, HAProxy путь не переписывает, при выделении модуля маршрут переключается без изменения клиентов); ADR-002 (`ModuleDefinition.extra_prefixes`, тест `test_router_prefix_matches_module`); глоссарий, правило 2 (REST-ресурсы — kebab-case); имя бакета `flt-<module>` в ADR-007 использует ту же замену `_` → `-`. Пример `GET /api/v1/learning-plan/jobs/{id}` в ADR-004 (раздел 3.3) приведён к этому правилу в версии 1.1 ADR-004.
- **Проверка**: архитектурный тест `tests/architecture/test_router_prefix_matches_module.py` (ADR-002, раздел 3.6) с правилом замены `_` → `-`; `extra_prefixes` непуст только у `identity` и равен `("/api/v1/auth",)`.
- **Применимость**: backend.

### SYS-03-R2 Исключения из правила префикса — только через SYS-03

- **Формулировка**: новый префикс, не равный `/api/v1/<module>`, не должен появляться в коде, пока он не внесён в таблицу раздела 6 этой спецификации с обоснованием и не продублирован в `ModuleDefinition.extra_prefixes` модуля-владельца.
- **Обоснование**: ADR-002, раздел 4.3 («оформить исключение `/api/v1/auth/*` как единственное отступление… SYS-03»); ADR-006 (путь `/api/v1/auth` задан OQ-12 для redirect URI и ACL HAProxy в ADR-012). Исключение без записи — скрытое расширение карты модулей наружу.
- **Проверка**: тот же архитектурный тест `test_router_prefix_matches_module`: допустимые `extra_prefixes` берутся из константы `ALLOWED_EXTRA_PREFIXES` в `tests/architecture/conftest.py`, рядом с которой стоит ссылка на раздел 6 SYS-03; добавление префикса без правки константы ломает тест; правка константы без правки SYS-03 ловится на ревью PR (чек-лист шага 2 конвейера).
- **Применимость**: backend, tests.

### SYS-03-R3 Версия API — мажорная, в пути

- **Формулировка**: версия API должна выражаться только сегментом пути `v<N>` с целым `N ≥ 1`; несовместимое изменение контракта модуля должно публиковаться как параллельный роутер `/api/v<N+1>/<module>` при сохранении `/api/v<N>/<module>` на срок из SYS-03-R28; версии в заголовках, query-параметрах и media type не используются.
- **Обоснование**: ADR-004 (путь фиксирован, HAProxy маршрутизирует по префиксу); ADR-005 (orval генерирует клиент из контракта, двум версиям соответствуют два контракта); мобильные клиенты обновляются с задержкой (CLAUDE.md «Ключевые архитектурные требования»: API пригоден для нативных приложений).
- **Проверка**: правило Spectral `flt-path-version` (`^/api/v[1-9][0-9]*/` в начале каждого `paths.*`) в `src/tools/contracts/.spectral.yaml`; CI job `contracts` (ADR-011).
- **Применимость**: backend, CI.

### SYS-03-R4 Стиль путей

- **Формулировка**: сегменты пути должны быть в kebab-case из строчных латинских букв, цифр и дефиса; имена коллекций — существительные во множественном числе (`/courses`, `/word-sets`); вложенность ресурсов — не глубже двух уровней коллекций (`/courses/{course_id}/enrollments/{enrollment_id}` допустимо, `/courses/{course_id}/enrollments/{enrollment_id}/notes` — нет); действие, не выражаемое методом над ресурсом, — `POST /<collection>/{<id>}/<verb>` с глаголом в kebab-case (`POST /courses/{course_id}/publish`); завершающий `/` не используется.
- **Обоснование**: глоссарий, правило 2 (kebab-case, множественное число); одна форма имени ресурса даёт предсказуемые имена хуков orval (ADR-005); ограничение вложенности удерживает пути внутри одного модуля (вложенный ресурс третьего уровня почти всегда принадлежит другому агрегату).
- **Проверка**: правила Spectral `flt-path-kebab-case` (регулярное выражение на каждый статический сегмент `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`), `flt-path-max-depth` (не более двух сегментов-параметров `{…}` в пути), встроенное `path-not-include-query`, `no-trailing-slash` (собственное правило: путь не заканчивается `/`); исключение для `/.well-known/jwks.json` — раздел 6.
- **Применимость**: backend, CI.

### SYS-03-R5 Имена параметров пути

- **Формулировка**: параметр пути, идентифицирующий ресурс, должен называться `<entity>_id` в snake_case по имени сущности в единственном числе (`{course_id}`, `{enrollment_id}`, `{provider_binding_id}`); имя `{id}` без префикса не используется.
- **Обоснование**: при вложенности двух уровней `{id}` неоднозначен; одинаковые имена во всех модулях упрощают генерацию клиента и логи (`endpoint` метрик — шаблон маршрута, ADR-010).
- **Проверка**: правило Spectral `flt-path-param-name` (`^[a-z][a-z0-9_]*_id$` для каждого `parameters[in=path].name`).
- **Применимость**: backend, CI.

### SYS-03-R6 Методы и коды успешных ответов

- **Формулировка**: эндпоинты должны использовать методы и коды из таблицы ниже и никакие другие коды успеха: `GET` коллекции или ресурса — `200`; `POST` создания — `201` с заголовком `Location` на созданный ресурс и телом ресурса; `POST` действия — `200` с результатом или `202` при запуске фонового задания (SYS-03-R27); `PUT` — полная замена, `200` с ресурсом; `PATCH` — частичное изменение по JSON Merge Patch (RFC 7396: отсутствующее поле не меняется, `null` очищает поле), `200` с ресурсом; `DELETE` — `204` без тела, повторный `DELETE` того же ресурса — `404`; `GET`, `HEAD` и `OPTIONS` не изменяют состояние.
- **Обоснование**: ADR-006, раздел 4.2 («GET не меняет состояние» — условие безопасности `SameSite=Lax`); ADR-004 (202 и ссылка на задание для фоновых операций); единый набор кодов нужен orval (`generateEachHttpStatus`) и обработке ошибок фронтенда.
- **Проверка**: правило Spectral `flt-success-codes` (для `get` разрешён только `200`; для `post` — `200`, `201`, `202`; для `put` и `patch` — `200`; для `delete` — `204`; у `201` обязателен заголовок `Location` в `responses.201.headers`); контрактный тест SYS-03-R23 сверяет коды реализации с контрактом; побочные эффекты `GET` — ревью (автоматически не проверяется: тест состояния до и после `GET` пишется в ТЗ только для эндпоинтов с подозрением на побочный эффект, например счётчики просмотров).
- **Применимость**: backend, CI.

### SYS-03-R7 Конверт ошибки `ErrorResponseV1`

- **Формулировка**: любой ответ монолита с кодом 4xx или 5xx на путях `/api/*` должен иметь `Content-Type: application/json` и тело по схеме `ErrorResponseV1` из `app/core/http/schemas.py`: `{"messages": {"INFO": [], "WARNING": [], "ERROR": [<ErrorMessage>]}, "payload": null, "request_id": "<uuid>"}`, где `ErrorMessage` — `{"code": "<module>.<error_name>", "message": "<текст для разработчика, английский>", "details": {<объект>}}`; массив `ERROR` содержит ровно один элемент; обработчики исключений регистрируются только через `error_envelope()` shared kernel.
- **Обоснование**: CLAUDE.md «Backend-сервис (boilerplate)»: ошибки в едином конверте `ErrorResponseV1`; `src/backend/py-monolyth/app/api/exception_handlers.py` (функция `error_envelope`, обработчики доменных ошибок, 422 и `HTTPException`) и `app/core/middlewares/logging_middleware.py` (500 в том же конверте). Поля `message_mnemo_code` и `parameters` boilerplate (`app/core/schemas.py`) переименованы в `code` и `details`, добавлены `message` и `request_id`; класс объявляется в shared kernel, а не импортируется из `py_main_lib.services.schemas.v1_schemas`, потому что конверт содержит `request_id` и коды ошибок FLT и принадлежит монолиту, а не общей библиотеке (OQ-69 resolved: `py-main-lib` правится свободно, неиспользуемые схемы ответов из неё удаляются на этапе 1 Г.1); в конверт нужен `request_id` (ADR-010: ID запроса возвращается клиенту). Массивы `INFO` и `WARNING` сохранены ради совместимости формы, но монолит их не заполняет. Форма `SuccessfulResponseV1` boilerplate (`messages` + `payload`) для успешных ответов **не используется**: тело успешного ответа — сам ресурс (SYS-03-R10).
- **Проверка**: контрактный тест `tests/core/http/test_error_envelope.py`: для каждого зарегистрированного обработчика исключений и для 404 несуществующего маршрута, 405, 422, 500 (тестовый роут, бросающий исключение) ответ валидируется схемой `ErrorResponseV1`; правило Spectral `flt-error-responses-use-envelope` — каждый ответ `4XX`/`5XX`/`default` в контракте ссылается на `#/components/schemas/ErrorResponseV1`; архитектурный тест `test_no_raw_json_error_responses` (AST: в `app/modules/**` нет `JSONResponse(status_code=4..|5..)` и `HTTPException(` вне shared kernel).
- **Применимость**: backend, tests, CI.

### SYS-03-R8 Коды ошибок

- **Формулировка**: значение `code` должно иметь вид `<module>.<error_name>`, где `<module>` — имя модуля-владельца в snake_case или `core` для ошибок shared kernel, `<error_name>` — snake_case из букв, цифр и `_`; коды shared kernel фиксированы таблицей ниже; код модуля объявляется в `app/modules/<module>/public/errors.py` как класс-наследник `DomainError` shared kernel с атрибутами `code`, `http_status`, и перечисляется в разделе «Контракты» ТЗ, которое его вводит.

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `core.bad_request` | некорректный заголовок или query-параметр, который не описывается схемой тела (`core.invalid_cursor` — частный случай для курсора) |
| 401 | `core.unauthenticated` | нет токена, токен не прошёл проверку, сессия отозвана; ответ содержит `WWW-Authenticate: Bearer` |
| 403 | `core.forbidden` | аутентифицирован, но нет права на действие (матрица SYS-06) |
| 403 | `identity.csrf_invalid` | cookie-клиент без валидного `X-CSRF-Token` (ADR-006) |
| 404 | `core.not_found` | ресурс не существует или принадлежит другому пользователю и его существование скрывается (SYS-03-R22) |
| 405 | `core.method_not_allowed` | метод не поддерживается путём |
| 409 | `core.version_conflict` | `version` в запросе не совпадает с текущей (SYS-03-R17); `details.current_version` |
| 409 | `core.request_in_progress` | повтор запроса с тем же `Idempotency-Key` до завершения первого (SYS-03-R18) |
| 409 | `<module>.<state_error>` | конфликт с текущим состоянием: уникальность, недопустимый переход состояния (например `identity.external_account_taken`) |
| 413 | `core.payload_too_large` | тело JSON больше `HTTP_MAX_JSON_BODY_BYTES` (SYS-03-R26) |
| 415 | `core.unsupported_media_type` | `Content-Type` не `application/json` там, где ожидается JSON |
| 422 | `core.validation_failed` | ошибка валидации схемы или значения поля (SYS-03-R9) |
| 422 | `core.idempotency_key_reused` | тот же `Idempotency-Key` с другим телом запроса |
| 429 | `core.rate_limited` | превышен лимит (SYS-03-R19); заголовок `Retry-After` |
| 500 | `core.internal` | необработанное исключение; `details` пуст вне `DEBUG_MODE` |
| 503 | `core.service_unavailable` | зависимость недоступна там, где политика fail-closed (ADR-003: лимиты модели платформы без Redis); заголовок `Retry-After` |

- **Обоснование**: ADR-006 перечисляет коды `invalid_credentials`, `refresh_reused`, `csrf_invalid`, `user_blocked`, `account_exists_use_password`, `external_account_taken` и просит оформить их в SYS-03 — здесь они получают префикс модуля (`identity.invalid_credentials`); ADR-009 — коды стрима (`provider_unavailable` и остальные) в REST появляются как `llm_gateway.provider_unavailable` (SYS-08). Префикс модуля исключает коллизии между модулями и совпадает с форматом `event_type` (SYS-04) и типов WebSocket, что даёт один словарь идентификаторов для i18n (`errors.<code>` — SYS-07) и логов.
- **Проверка**: правило Spectral `flt-error-code-pattern` (все значения `enum` у свойства `code` в примерах и схемах ошибок соответствуют `^[a-z][a-z0-9_]*\.[a-z][a-z0-9_]*$`); архитектурный тест `test_error_codes_prefixed_by_module` (обход подклассов `DomainError` во всех модулях реестра: `code` начинается с `<module>.` своего пакета или `core.` для `app/core`; коды уникальны); unit-тест таблицы `tests/core/http/test_core_error_codes.py` на соответствие HTTP-кодов.
- **Применимость**: backend, tests, CI.

### SYS-03-R9 Ошибки валидации — 422 с перечнем полей

- **Формулировка**: ошибка валидации входных данных (несоответствие схеме Pydantic, недопустимое значение поля по доменному правилу, нечитаемый JSON) должна возвращаться с кодом `422` и `code: core.validation_failed`, а `details.errors` — массив объектов `{"loc": ["body", "<field>", ...], "type": "<pydantic type>", "msg": "<текст>", "ctx": {<контекст>}}` в формате `RequestValidationError.errors()` FastAPI; доменные правила на значения полей добавляют элементы того же вида с `type: "value_error.<rule>"`; `400` для ошибок тела не используется.
- **Обоснование**: boilerplate уже отдаёт 422 в конверте (`request_validation_error_handler`); единый формат позволяет orval и `react-hook-form` раскладывать ошибки по полям формы (ADR-005: zod-схемы из контракта).
- **Проверка**: тест `tests/core/http/test_error_envelope.py::test_validation_error_shape`; правило Spectral `flt-422-present` — у каждой операции с `requestBody` объявлен ответ `422`.
- **Применимость**: backend, frontend, CI.

### SYS-03-R10 Форма тела успешного ответа и представление ресурса

- **Формулировка**: тело успешного ответа должно быть представлением ресурса (объект) или страницей коллекции (SYS-03-R12) без обёртки `payload`; представление каждой сущности с собственной таблицей должно содержать поля `id` (UUID), `created_at`, `updated_at`, `version` (целое ≥ 1); имена полей JSON — snake_case; значения перечислений — строки в snake_case; булевы значения — `true`/`false`; поля с отсутствующим значением передаются как `null`, а не опускаются (кроме тел `PATCH`).
- **Обоснование**: ADR-003, раздел 2.4 (`created_at`, `updated_at`, `version` в ответах; `version` обязателен в `PUT`/`PATCH`); совпадение имён колонок и полей API убирает слой преобразования; стабильная форма `null` упрощает типизацию клиента (`T | null` вместо `T | undefined`).
- **Проверка**: правила Spectral `flt-schema-properties-snake-case` (имена свойств `^[a-z][a-z0-9_]*$`), `flt-resource-base-fields` (схема с суффиксом `Response`, помеченная `x-flt-entity: true`, содержит `id`, `created_at`, `updated_at`, `version` как `required`); архитектурный тест `test_response_schemas_entity_fields` (каждая Pydantic-схема ответа, построенная из модели с `VersionMixin`, экспортирует эти поля).
- **Применимость**: backend, CI.

### SYS-03-R11 Имена схем OpenAPI уникальны и с префиксом модуля

- **Формулировка**: имя класса Pydantic, попадающего в OpenAPI (`components.schemas`), должно начинаться с имени модуля в PascalCase (`IdentityUserResponse`, `LlmGatewayProviderConnectionCreateRequest`) и заканчиваться одним из суффиксов `Request`, `Response`, `Item`, `Page`, `Filter`; shared kernel использует префикс `Core` (`CoreErrorResponseV1` публикуется под именем `ErrorResponseV1` через `model_config.title`).
- **Обоснование**: FastAPI собирает один документ OpenAPI на монолит, одинаковые имена классов разных модулей дают `User`, `User2` и ломают детерминированность генерации (ADR-005: `api:check` сравнивает сгенерированный код); суффиксы отделяют DTO от доменных моделей.
- **Проверка**: тест `tests/contracts/test_openapi_schema_names.py` (в сгенерированном `app.openapi()` нет имён с числовым суффиксом и каждое имя схемы модуля начинается с его PascalCase-префикса); правило Spectral `flt-schema-name-prefix` для контракта модуля.
- **Применимость**: backend, CI.

### SYS-03-R12 Пагинация по курсору по умолчанию

- **Формулировка**: `GET` коллекции должен возвращать страницу вида `{"items": [...], "next_cursor": "<строка>" | null}` и принимать query-параметры `limit` (целое, по умолчанию 20, максимум 100; больше — `422`) и `cursor` (непрозрачная строка base64url, выданная сервером в `next_cursor`; невалидная или чужая для данной сортировки — `400 core.invalid_cursor`); курсор кодирует значения полей сортировки и `id` последнего элемента и применяется как keyset-условие (`WHERE (sort_key, id) > (:k, :id)`); поле `total` в курсорной странице не возвращается.
- **Обоснование**: ADR-003 — первичные ключи UUID v7 монотонны по времени, keyset-пагинация по `(created_at, id)` не требует отдельного индекса и не сдвигается при вставках между запросами (лента, словарь, повторения — растущие коллекции, SYS-02: p95 ≤ 300 мс); `OFFSET` на больших таблицах читает и отбрасывает строки; `COUNT(*)` для `total` — отдельный полный проход.
- **Проверка**: правило Spectral `flt-list-paginated` (операция `get` без параметра пути в конце и с массивом в ответе обязана возвращать схему с `items` и `next_cursor` и объявлять параметры `limit` и `cursor`, кроме операций с `x-flt-pagination: offset` — SYS-03-R13); интеграционный тест shared kernel `tests/core/http/test_cursor_pagination.py` на хелпере `paginate_keyset()` (стабильность при вставке между страницами, отказ на чужом курсоре).
- **Применимость**: backend, CI.

### SYS-03-R13 Смещение — только для административных списков

- **Формулировка**: пагинация по `offset` (`offset`, `limit`, ответ `{"items": [...], "total": <int>, "offset": <int>, "limit": <int>}`) должна использоваться только для списков, доступных исключительно роли `platform_admin` (ADM-01–ADM-06), и помечаться в контракте расширением `x-flt-pagination: offset`; у остальных операций `offset` запрещён.
- **Обоснование**: административные экраны (пользователи, курсы, жалобы) требуют перехода на произвольную страницу и общего количества при объёмах до десятков тысяч строк (OQ-13: 10 000 пользователей за год), где `OFFSET` и `COUNT(*)` дёшевы; для пользовательских списков действует SYS-03-R12.
- **Проверка**: правило Spectral `flt-offset-only-admin` (операция с `x-flt-pagination: offset` имеет `security` только с правами, которые по матрице SYS-06 выданы лишь роли `platform_admin` (код `<module>:<resource>:<action>`, область `any`), и тег модуля); контрактный тест SYS-03-R23 сверяет расширение с реализацией (`paginate_offset()` допускается только в контроллерах с зависимостью `auth_user(<admin permission>)` — AST-тест `test_offset_pagination_admin_only`).
- **Применимость**: backend, CI.

### SYS-03-R14 Сортировка

- **Формулировка**: сортировка коллекции должна задаваться одним query-параметром `sort` вида `<field>[,<field>...]`, где префикс `-` означает убывание (`sort=-created_at,name`); допустимые поля перечисляются в контракте перечислением (`enum`) и в коде константой контроллера; поле вне списка — `422`; при отсутствии параметра действует сортировка по умолчанию, объявленная в контракте (`x-flt-default-sort`); `id` всегда добавляется последним ключом для детерминированности.
- **Обоснование**: один параметр совместим с курсором (SYS-03-R12: курсор кодирует значения ключей сортировки, поэтому `sort` входит в курсор и его смена делает старый курсор невалидным); перечисление полей не даёт сортировать по неиндексированным колонкам.
- **Проверка**: правило Spectral `flt-sort-param` (параметр `sort` имеет `schema.items.enum` или `schema.enum`, присутствует `x-flt-default-sort`); unit-тест хелпера `parse_sort()` shared kernel.
- **Применимость**: backend, CI.

### SYS-03-R15 Фильтры и поиск

- **Формулировка**: фильтры коллекции должны передаваться плоскими query-параметрами с именем поля в snake_case (`status=active`); несколько значений одного поля — повторением параметра (`language=en&language=fr`, семантика «или»); диапазоны — суффиксами `_from` и `_to` включительно (`created_at_from=2026-10-01T00:00:00Z`); полнотекстовый поиск — параметром `q` (строка от 1 до 200 символов); синтаксис `filter[...]`, операторы в значениях (`gte:`) и JSON в query не используются.
- **Обоснование**: плоские параметры описываются в OpenAPI с типами и `enum`, генерируются orval как типизированные аргументы (ADR-005) и валидируются Pydantic без собственного парсера; `q` соответствует соглашению OpenSearch-поиска (ADR-014).
- **Проверка**: правило Spectral `flt-query-param-names` (`^[a-z][a-z0-9_]*$`, запрет символов `[`, `]`, `.` в именах; для параметров с суффиксом `_from`/`_to` — парный параметр и общий тип); тест парсера shared kernel.
- **Применимость**: backend, CI.

### SYS-03-R16 Идентификаторы и дата-время

- **Формулировка**: идентификаторы ресурсов в путях, телах и query должны быть UUID (генерируются как UUID v7 по ADR-003) в каноническом строчном виде с дефисами, в OpenAPI — `type: string, format: uuid`; метки времени — строки ISO 8601 в UTC с суффиксом `Z` и точностью до миллисекунд или секунд (`2026-10-10T12:00:00.123Z`), в OpenAPI — `format: date-time`; на входе принимаются значения с любым смещением и нормализуются в UTC, значения без смещения — `422`; календарные даты — `YYYY-MM-DD` (`format: date`); длительности — целые числа в поле с суффиксом единицы (`duration_minutes`, `ttl_seconds`), не строки ISO 8601 duration; часовой пояс пользователя на представление API не влияет (форматирование — на фронтенде, SYS-07).
- **Обоснование**: ADR-003 (UUID v7, `timestamptz` в UTC, `datetime` только tz-aware); однозначный формат убирает ошибки разбора в браузере и на мобильных платформах; суффикс единицы делает тип числовым для клиента.
- **Проверка**: правила Spectral `flt-uuid-format` (все свойства и параметры с именем `id` или суффиксом `_id` имеют `format: uuid`), `flt-datetime-format` (свойства с суффиксом `_at` — `format: date-time`; `_on` — `format: date`), `flt-duration-naming` (числовые свойства с суффиксом `_seconds`, `_minutes`, `_ms`, `_bytes` — `type: integer`); тест сериализации shared kernel `tests/core/http/test_json_encoding.py` (UTC → `Z`, вход со смещением → UTC, naive → 422).
- **Применимость**: backend, CI.

### SYS-03-R17 Оптимистическая блокировка через `version`

- **Формулировка**: тело `PUT` и `PATCH` для сущности с `version` должно содержать обязательное поле `version` с последним известным клиенту значением; сервер должен выполнять обновление с условием `version = :version`, при несовпадении отвечать `409 core.version_conflict` с `details: {"current_version": <int>}`, при успехе — увеличивать `version` на 1 и возвращать ресурс; заголовки `ETag`, `If-Match` и код `412` для этой цели не используются.
- **Обоснование**: ADR-003, раздел 2.4 (`VersionMixin`, `StaleDataError` → HTTP 409 в конверте; «`version` обязателен в `PUT`/`PATCH`, frontend передаёт его»); поле в теле попадает в сгенерированные типы orval автоматически, в отличие от условных заголовков, и одинаково работает в браузере и в мобильном клиенте; выбор между 409 и 412 (вопрос оркестратора) решён в пользу 409, уже зафиксированного ADR-003.
- **Проверка**: правило Spectral `flt-version-in-update-body` (у операций `put`/`patch` по пути с параметром `_id` схема `requestBody` содержит `required: [version]` или помечена `x-flt-no-version: true` с обоснованием в ТЗ); интеграционный тест shared kernel `tests/core/dao/test_optimistic_locking.py` и тест на N инстансах `tests/n_instances/test_concurrent_update.py` (два `PATCH` через HAProxy на разные инстансы: один `200`, второй `409`, данные не потеряны — SYS-05).
- **Применимость**: backend, frontend, tests.

### SYS-03-R18 Идемпотентность `POST` через `Idempotency-Key`

- **Формулировка**: операция `POST`, которая создаёт ресурс (`201`), запускает фоновое задание (`202`) или вызывает внешний эффект (отправка письма, запрос к провайдеру LLM или речи), должна объявлять в контракте обязательный заголовок `Idempotency-Key` (UUID) и обрабатываться зависимостью `Idempotent()` shared kernel: первый запрос выполняется и его ответ (статус, заголовки `Location` и `Content-Type`, тело) сохраняется в Redis по ключу `shared_kernel:idempotency:<subject>:<key>` с TTL 24 часа, где `<subject>` — `user_id`, а для анонима — идентификатор анонимной сессии из cookie `flt_anon_session` (OQ-77); повтор с тем же ключом и тем же телом (сравнение по `sha256` канонического JSON) возвращает сохранённый ответ с заголовком `Idempotent-Replayed: true`; тот же ключ с другим телом — `422 core.idempotency_key_reused`; повтор во время выполнения первого — `409 core.request_in_progress` с `Retry-After: 1`; `POST` входа, обновления токена и выхода (`/api/v1/auth/login`, `/refresh`, `/logout`) ключ не требуют.
- **Обоснование**: ADR-012, раздел 3.5 (HAProxy повторяет только запросы без отправленного тела; идемпотентность — зона SYS-03); клиент (ADR-005) и мобильные приложения повторяют запросы при обрыве сети; уникальные ограничения PostgreSQL защищают не всякое создание (несколько одинаковых записей или заданий допустимы по домену). Потеря Redis допустима (ADR-003: политика fail-open для кэша): повтор без сохранённого ответа выполняется заново — ТЗ фичи с внешним эффектом указывает это в разделе 6.5.
- **Проверка**: правило Spectral `flt-post-idempotency-key` (операция `post` с ответом `201` или `202` или с расширением `x-flt-side-effect: true` объявляет параметр `Idempotency-Key` `in: header, required: true, schema.format: uuid`; исключения — `x-flt-idempotency-exempt: true` с перечнем в разделе 6); интеграционный тест shared kernel `tests/core/http/test_idempotency.py`; тест на N инстансах `tests/n_instances/test_idempotency_across_instances.py` (два одинаковых `POST` на разные инстансы → один ресурс).
- **Применимость**: backend, tests, CI.

### SYS-03-R19 Лимиты запросов — 429 с `Retry-After`

- **Формулировка**: при превышении лимита монолит должен отвечать `429` с `code: core.rate_limited`, заголовком `Retry-After: <секунды>` (целое, округлённое вверх) и `details: {"scope": "<имя лимита>", "retry_after_seconds": <int>}`; лимиты реализуются ограничителем shared kernel (скользящее окно в Redis, ADR-003) с ключами `<module>:ratelimit:<scope>:<subject>`; значения лимитов — параметры конфигурации модуля; ответы `429` и `413` самого HAProxy (первый рубеж, ADR-012) приходят без конверта, и клиент обязан обрабатывать `429`/`413`/`502`/`503`/`504` с телом, не являющимся JSON.
- **Обоснование**: ADR-003, раздел 2.7 (Lua-ограничитель возвращает `retry_after_ms`); ADR-012 (stick-table HAProxy — первый рубеж без конверта); ADR-006 (лимит попыток входа 10 на email и 50 на IP); OQ-09 и OQ-10 (лимиты быстрого теста).
- **Проверка**: интеграционный тест shared kernel `tests/core/http/test_rate_limit_response.py`; тест на N инстансах `tests/n_instances/core/test_rate_limit_global.py` (лимит `N` запросов исчерпывается запросами через HAProxy на разные инстансы — SYS-05); тест клиента фронтенда `src/lib/api-client.test.ts` на не-JSON ответ `429` (ADR-005).
- **Применимость**: backend, frontend, tests.

### SYS-03-R20 Заголовок `X-Request-ID`

- **Формулировка**: каждый ответ монолита на путях `/api/*` должен содержать заголовок `X-Request-ID`, равный значению, полученному от HAProxy, а при его отсутствии (запуск без HAProxy на стенде local и в pytest) — UUID, сгенерированному middleware shared kernel; то же значение пишется в поле `request_id` конверта ошибки, в каждую строку лога запроса и передаётся в заголовки Kafka и сообщения WebSocket (SYS-04).
- **Обоснование**: ADR-012 (`unique-id-header X-Request-ID`, клиентский заголовок перезаписывается); ADR-010 (`request_id` — ключ корреляции логов HAProxy, инстанса и Kafka-обработчика при выключенных трейсах).
- **Проверка**: тест `tests/core/http/test_request_id.py` (значение из входящего заголовка возвращается; без заголовка — валидный UUID; совпадает с `request_id` в конверте 404); smoke-тест Г.8 ADR-012 (`X-Request-ID` в ответе совпадает с логом HAProxy).
- **Применимость**: backend, tests.

### SYS-03-R21 Аутентификация: Bearer везде, cookie — только для браузера

- **Формулировка**: любой эндпоинт `/api/*`, требующий аутентификации, должен принимать `Authorization: Bearer <access JWT>` и возвращать тот же результат, что и при cookie-аутентификации; порядок извлечения токена, cookie `__Host-flt_access`, `flt_refresh`, `__Host-flt_csrf` и заголовок `X-CSRF-Token` для изменяющих методов cookie-клиентов — по ADR-006, раздел 3.4; эндпоинты не должны читать cookie напрямую (только через `get_current_user` shared kernel) и не должны отвечать HTML или редиректом, кроме операций OAuth `GET /api/v1/auth/{provider}/start` и `/callback` (раздел 6); при `401` ответ содержит `WWW-Authenticate: Bearer`.
- **Обоснование**: CLAUDE.md «Ключевые архитектурные требования» (API и аутентификация проектируются под нативные мобильные приложения); ADR-006 (один бэкенд для cookie и Bearer, cookie-путь дополнен CSRF); CORS на prod не настраивается, так как фронтенд, API и хранилище на одном origin (ADR-012, раздел 3.4: `ALLOW_ORIGINS` пустой, `["*"]` только на local).
- **Проверка**: фикстура интеграционных тестов `api_client` по умолчанию использует Bearer, фикстура `web_client` — cookie и CSRF; параметризованный тест `tests/core/security/test_auth_transports.py` прогоняет каждый защищённый маршрут из `app.routes` обоими способами и сравнивает статус; архитектурный тест `test_no_direct_cookie_access` (AST: `request.cookies` только в `app/core/security`); правило Spectral `flt-security-bearer-and-cookie` (каждая операция с `security` перечисляет обе схемы `bearerAuth` и `cookieAuth`, кроме помеченных `x-flt-public: true`).
- **Применимость**: backend, tests, CI.

### SYS-03-R22 401, 403 и 404 для чужих ресурсов

- **Формулировка**: без действительного токена сервер должен отвечать `401 core.unauthenticated`; с токеном без права на действие — `403 core.forbidden`; при обращении к ресурсу, принадлежащему другому пользователю, существование которого не является публичным (профиль, словарь, материалы, подключения провайдеров, переписка), — `404 core.not_found`, а не `403`; `details` ответов `403` не раскрывают недостающие permissions вне `DEBUG_MODE`.
- **Обоснование**: boilerplate скрывает `missing_permissions` и `is_deleted` (`exception_handlers.py`); перечисление идентификаторов чужих ресурсов через различие `403`/`404` — утечка (SYS-02); матрица прав — SYS-06.
- **Проверка**: шаблон ТЗ требует критерий приёмки «чужой ресурс → 404» для каждого приватного ресурса (раздел 4.2); тест `tests/core/http/test_error_envelope.py::test_forbidden_hides_permissions`.
- **Применимость**: backend, tests.

### SYS-03-R23 Spec-first: контракт OpenAPI и сверка с реализацией

- **Формулировка**: контракт REST модуля должен лежать в `Analytics/Specs/<module>/api/openapi.yaml` (OpenAPI 3.1.0, один файл на модуль, `info.version` — SemVer, `servers: [{url: /}]`), быть утверждён на G1 до написания тестов и кода; контрактный тест `tests/contracts/test_openapi_<module>.py` должен сравнивать документ, сгенерированный FastAPI (`app.openapi()`, отфильтрованный по путям с префиксами модуля), с контрактом после нормализации и падать при любом расхождении, кроме допустимых: порядок ключей; текст `description`, `summary`, `title`, `example`, `examples`; блок `info`, кроме `version`; `servers`; `tags[].description`; расширения `x-*`, не перечисленные в этой спецификации; представление `nullable` (`anyOf` с `null` против `type: [..., "null"]`); порядок элементов `enum` и `required`. Сравниваются: пути, методы, `operationId`, теги, параметры (имя, расположение, обязательность, схема), `requestBody`, коды ответов, схемы ответов и компонентов (типы, форматы, `required`, `enum`, ограничения), `security`, заголовки ответов, расширения `x-flt-*`.
- **Обоснование**: CLAUDE.md «Взаимодействие» (контракты spec-first, FastAPI генерирует OpenAPI, контрактные тесты сверяют с контрактом ТЗ); ADR-005 (orval и MSW генерируются из контракта в `Analytics/Specs/<module>/api/openapi.yaml`, `api:check` в CI); ADR-011 (job `contracts`). Нормализация нужна, потому что FastAPI и Pydantic добавляют заголовки и варьируют представление `nullable`.
- **Проверка**: сам контрактный тест (создаётся скаффолдером `make scaffold-module` из шаблона `tests/contracts/_template_openapi.py`; архитектурный тест `test_every_module_has_contract_test` проверяет наличие теста и файла контракта у каждого модуля реестра с роутером); CI job `backend-tests`; `pnpm api:check` (ADR-005).
- **Применимость**: backend, frontend, tests, CI.

### SYS-03-R24 `operationId` и теги

- **Формулировка**: каждая операция должна иметь уникальный в монолите `operationId` вида `<module>_<verb><Resource>`: `<module>` — имя модуля в snake_case, `<verb>` — один из `list`, `get`, `create`, `update` (PUT), `patch`, `delete` или глагол действия в lowerCamelCase (`publish`, `testConnection`), `<Resource>` — имя ресурса в PascalCase в единственном числе для одиночного ресурса и во множественном для `list` (`courses_listCourses`, `courses_getCourse`, `identity_login`, `llm_gateway_testProviderConnection`); единственный тег операции — имя модуля в snake_case; `operationId` после утверждения контракта не меняется (переименование — новая операция и deprecation старой).
- **Обоснование**: orval строит имена хуков из `operationId` (`useCoursesListCourses`), смена имени ломает фронтенд (ADR-005); тег = модуль группирует Swagger по модулям и позволяет фильтровать документ по модулю в контрактном тесте.
- **Проверка**: правила Spectral `operation-operationId-unique` (встроенное), `flt-operation-id-pattern` (`^[a-z][a-z0-9_]*_[a-z][a-zA-Z0-9]*$` и префикс равен имени модуля из пути), `flt-operation-single-tag` (ровно один тег, равный имени модуля); контрактный тест SYS-03-R23 сверяет `operationId`.
- **Применимость**: backend, CI.

### SYS-03-R25 Служебные эндпоинты и документация вне `/api`

- **Формулировка**: эндпоинты `/v1/health`, `/v1/ready`, `/v1/metrics` (роль `api` на порту 8000, роль `worker` на 8001) и `/asyncapi/kafka` должны оставаться вне префикса `/api` и не входить в контракты модулей; документация OpenAPI должна отдаваться на `/api/docs` и `/api/openapi.json`; других путей вне `/api/v1/<module>`, `/api/docs`, `/api/openapi.json`, `/api/redoc`, `/ws`, `/ws/agent` и служебных `/v1/*`, `/asyncapi/*` у приложения быть не должно.
- **Обоснование**: ADR-004, раздел 3.2; ADR-010 (`/v1/metrics`, OQ-21, OQ-62); ADR-012 (служебные пути до монолита снаружи не доходят, документация закрыта ACL без `FLT_EXPOSE_DOCS`).
- **Проверка**: архитектурный тест `tests/architecture/test_route_inventory.py` (обход `app.routes`: каждый путь соответствует одному из разрешённых шаблонов); smoke-тест Г.8 (ADR-012).
- **Применимость**: backend, deploy, tests.

### SYS-03-R26 Типы содержимого и размер тела

- **Формулировка**: запросы и ответы с телом должны использовать `application/json; charset=utf-8`; размер тела JSON не должен превышать `HTTP_MAX_JSON_BODY_BYTES` (по умолчанию 1 МиБ; больше — `413 core.payload_too_large`); загрузка и скачивание файлов через `/api/*` не выполняются — файлы идут presigned URL в хранилище по маршруту `/flt-*` (ADR-007), а API принимает только метаданные и подтверждения; `multipart/form-data` допускается только для операций, перечисленных в разделе 6.
- **Обоснование**: ADR-003 (ориентир 1 МБ на `jsonb`-запись, крупнее — MinIO); ADR-007 и ADR-012 (лимит 25 МБ в HAProxy на `/api/`, загрузки — presigned POST/PUT); единый тип содержимого упрощает клиент и моки.
- **Проверка**: правило Spectral `flt-json-only` (`requestBody.content` и `responses.*.content` содержат только `application/json`, кроме операций с `x-flt-multipart: true`); тест middleware `tests/core/http/test_body_limit.py`.
- **Применимость**: backend, CI.

### SYS-03-R27 Фоновые операции — `202` и ресурс задания

- **Формулировка**: операция, выполнение которой длится дольше 2 секунд или не требует немедленного результата (ADR-004, правило выбора транспорта), должна отвечать `202` с заголовком `Location: /api/v1/<module>/jobs/{job_id}` и телом `{"job_id": "<uuid>", "status": "queued"}`; модуль с заданиями должен предоставлять `GET /api/v1/<module>/jobs/{job_id}` с представлением `{"id", "kind", "status": "queued|running|succeeded|failed|cancelled", "progress": {"percent": <int 0..100>, "stage": "<str>", "message_key": "<i18n key>"}, "result_ref": "<REST-путь результата или null>", "error": {"code", "details"} | null, "created_at", "updated_at", "version"}` и `DELETE /api/v1/<module>/jobs/{job_id}` для отмены (`204`; завершённое задание — `409 <module>.job_finished`); REST-эндпоинты не должны обращаться к провайдерам LLM или речи синхронно, кроме проверки подключения из SYS-08 (раздел 6).
- **Обоснование**: ADR-004, разделы 2.4 и 3.1 (таблица `<module>.jobs`, команда через outbox, прогресс по WebSocket, `GET /api/v1/<module>/jobs/{id}` как REST-состояние канала); ADR-009, раздел 3.2 (интерактивные запросы LLM — только WebSocket; фоновые — задание); ADR-012 (`timeout server 60s` для REST); OQ-13 (p95 REST ≤ 300 мс без обращения к LLM).
- **Проверка**: правило Spectral `flt-202-location` (ответ `202` объявляет заголовок `Location` и схему `CoreJobAcceptedResponse`); правило `flt-jobs-resource` (контракт модуля с ответом `202` содержит пути `/jobs/{job_id}` с `get` и `delete`); архитектурный тест `test_no_llm_calls_in_controllers` (AST: в `app/modules/**/api/` нет вызовов `LlmGatewayService.stream_completion`/`complete` и `SpeechService.*`, кроме allowlist раздела 6).
- **Применимость**: backend, CI.

### SYS-03-R28 Вывод операций и версий из эксплуатации

- **Формулировка**: устаревающая операция или версия должна быть помечена в контракте `deprecated: true` и отдавать заголовки `Deprecation: @<unix-время решения>` (RFC 9745) и `Sunset: <HTTP-date>` (RFC 8594), а при наличии замены — `Link: <путь замены>; rel="successor-version"`; срок между `Deprecation` и `Sunset` — не менее 90 дней и не раньше конца следующего этапа; после `Sunset` операция удаляется из контракта и кода одной фичей с записью в матрице трассировки.
- **Обоснование**: нативные мобильные клиенты обновляются с задержкой (CLAUDE.md «Ключевые архитектурные требования»); стандартные заголовки позволяют клиенту (ADR-005: интерсептор axios пишет предупреждение в консоль) и мониторингу (`http_requests_total{endpoint}` по устаревшим маршрутам, ADR-010) отслеживать использование.
- **Проверка**: правило Spectral `flt-deprecated-has-sunset` (операция с `deprecated: true` имеет расширение `x-flt-sunset` в формате `date` и заголовки `Deprecation` и `Sunset` в ответах); тест middleware `tests/core/http/test_deprecation_headers.py` (заголовки выставляются по декоратору `@deprecated(sunset=date(...))` shared kernel).
- **Применимость**: backend, CI.

### SYS-03-R29 Совместимые и несовместимые изменения контракта

- **Формулировка**: в пределах версии `v<N>` допускаются только совместимые изменения: добавление необязательного поля в запрос, добавление поля в ответ, добавление операции, добавление необязательного query-параметра, добавление значения перечисления в ответ (клиенты обязаны допускать неизвестные значения перечислений ответа и неизвестные поля); удаление или переименование поля, пути или операции, изменение типа, перевод поля в обязательное, сужение перечисления запроса — несовместимые и выполняются только через SYS-03-R3 и SYS-03-R28.
- **Обоснование**: один контракт обслуживает браузер и мобильные клиенты разных версий; правило совпадает с правилом версионирования событий Kafka (SYS-04) и миграций expand/contract (ADR-003).
- **Проверка**: CI job `contracts` запускает `oasdiff breaking <контракт в main> <контракт в PR>` для каждого изменённого `openapi.yaml` и падает при несовместимом изменении без увеличения мажорной версии в пути (`uv run flt-tools contracts check` оборачивает вызов — ADR-011); на фронтенде zod-схемы ответов генерируются с `.passthrough()` и `z.enum(...).catch("unknown")` для перечислений ответа (ADR-005, настройка orval).
- **Применимость**: backend, frontend, CI.

### SYS-03-R30 Локаль запроса

- **Формулировка**: монолит должен определять локаль запроса в порядке: язык интерфейса из профиля аутентифицированного пользователя (`identity.users.ui_language`, ADR-006) → cookie `flt_ui_language` (явный выбор языка до входа или анонимом, SYS-07) → заголовок `Accept-Language` (разбор по RFC 9110, выбор первого поддерживаемого языка из `ru`, `en`, `ar`) → `ru` (язык по умолчанию, SYS-07); значение не из множества `ru`, `en`, `ar` в профиле или cookie пропускается; выбранная локаль возвращается в заголовке `Content-Language`, доступна обработчикам через `RequestContext.locale` и используется только для локализуемого содержимого ответа (тексты CMS, названия из справочников, письма), а не для сообщений об ошибках: поле `message` конверта всегда на английском, фронтенд локализует по `code` и `details`.
- **Обоснование**: CLAUDE.md «i18n с первого дня» (язык интерфейса — настройка, строки UI не хардкодятся); SYS-07 детализирует языки, направление письма и форматы; приоритет профиля над заголовком нужен, потому что язык браузера и выбранный язык интерфейса различаются (OQ-25: язык по умолчанию `ru` и порядок источников — SYS-07, здесь тот же порядок для REST).
- **Проверка**: тест `tests/core/http/test_locale_resolution.py` (четыре источника в порядке приоритета, `Content-Language`, недопустимое значение cookie и `Accept-Language` → `ru`); правило Spectral `flt-error-message-not-localized` отсутствует (не выразимо) — ревью: в ТЗ раздел 8.2 перечисляет ключи i18n для кодов ошибок.
- **Применимость**: backend, frontend, tests.

### SYS-03-R31 Схемы DTO модуля и их размещение

- **Формулировка**: Pydantic-схемы запросов и ответов REST должны лежать в `app/modules/<module>/schemas/` (внутренний слой по ADR-002); схемы, которые нужны другим модулям, — в `app/modules/<module>/public/schemas.py`; DTO REST не должны наследоваться от моделей SQLAlchemy и не должны содержать поля, отсутствующие в контракте (`model_config = ConfigDict(extra="forbid")` для запросов).
- **Обоснование**: ADR-002 (слои модуля, `public` — единственное, что импортируют соседи); `extra="forbid"` делает опечатку в имени поля ошибкой 422, а не молчаливым игнорированием.
- **Проверка**: контракт import-linter `module-internal-layers` (ADR-002); архитектурный тест `test_request_schemas_forbid_extra` (все классы с суффиксом `Request` имеют `extra="forbid"`).
- **Применимость**: backend.

### Пример 6. Доменная ошибка модуля (SYS-03-R8)

```python

from app.core.http.errors import DomainError


class InvalidCredentialsError(DomainError):
```

## 6. Исключения и как их согласовать

Порядок согласования: вопрос в `Analytics/open-questions.md` → решение человека → строка в таблице ниже → исключение в проверке (`ALLOWED_EXTRA_PREFIXES`, расширение `x-flt-*` в контракте, allowlist архитектурного теста) со ссылкой на эту таблицу.

|---|---|---|---|---|

## 7. Вне рамок

- Матрица «роль × действие», имена permissions и правило доступа без подтверждения 18+ — SYS-06.
- Языки интерфейса, язык по умолчанию (OQ-25), форматы дат и чисел на фронтенде, RTL — SYS-07.
- Формат сообщений WebSocket, топики и события Kafka, AsyncAPI — SYS-04.
- Хранение состояния, TTL ключей Redis, поведение при отказе Redis, методика тестов на N инстансах — SYS-05.
- Коды ошибок провайдеров LLM и речи, их отображение в `completion.error` — SYS-08.
- Нефункциональные нормативы (p95, лимиты HAProxy, заголовки безопасности, TLS) — SYS-02 и ADR-012.
- Структура и запуск CI job `contracts`, размещение `src/tools/contracts` (OQ-70, resolved) — SYS-12 и ADR-011.
- Генерация клиента, zod-схем и моков MSW из контракта — ADR-005 и спецификация `app_shell`.
- Доступ к файлам (presigned URL, бакеты, подтверждение загрузки) — ADR-007.
- HTTP-кэширование (`ETag`, `Cache-Control`, `If-None-Match`) для ответов API не вводится на этапах 1–3; при появлении потребности — изменение SYS-03 (статус `changed`).
- Массовые операции (bulk create/update/delete) не вводятся на этапах 1–3.
