## 1. Цель и область действия

- **Цель**: превратить принципы CLAUDE.md «Масштабирование и состояние» и решения ADR-003 и ADR-004 в проверяемые требования: инстанс монолита не хранит состояние, постоянное состояние лежит в PostgreSQL и MinIO, временное — в Redis с префиксом модуля и TTL, конкурентные изменения с разных инстансов не теряются и не дублируются, WebSocket-события доходят до клиента на любом инстансе, периодические задачи и задания выполняются один раз, миграции совместимы с предыдущей версией кода, инстанс можно остановить в любой момент; и задать единую методику тестов каждой фичи на стенде из N = 3 инстансов.
- **Область действия**: backend (shared kernel и все доменные модули), deploy (стенд `docker-compose.ci.yml`, параметры остановки и пулов в docker-compose и Helm), tests (архитектурные тесты `tests/architecture/`, тесты `tests/n_instances/`), CI (job `stand-n3`). Frontend затрагивается только в части восстановления состояния после переподключения WebSocket (ADR-005 реализует, здесь — требование к серверу).
- **Действует с этапа**: 1 (п. Г.2 архитектурные тесты, Г.3 стенд из N инстансов, Г.4 shared kernel, Г.8 развёртывание, Г.11 E2E).
- **Уточняет**: CLAUDE.md, разделы «Масштабирование и состояние», «Модульный монолит», «Определение готовности»; ADR-003 (хранение состояния), ADR-004 (взаимодействие, роли запуска, остановка); CLAUDE.md «Отличия проекта от boilerplate», п. 10 (тестовая БД — вместе с SYS-10).

## 3. Требования

Требования сгруппированы по темам: инстанс без состояния (R1–R5), размещение состояния (R6–R10), Redis (R11–R17), конкурентность (R18–R23), WebSocket между инстансами (R24–R27), задания и периодические задачи (R28–R32), миграции (R33–R38), остановка, пулы и время (R39–R43), методика тестов на N инстансах (R44–R54).

### SYS-05-R1 Запрет изменяемого состояния на уровне модуля Python

- **Формулировка**: Код в `app/` не должен объявлять на уровне модуля Python изменяемые объекты, которые изменяются после старта процесса: словари, списки, множества, `deque`, экземпляры классов с изменяемыми атрибутами, используемые как хранилище между запросами.
- **Обоснование**: CLAUDE.md «Масштабирование и состояние»: «инстанс не хранит состояние между запросами: ни в глобальных переменных, ни в локальных кэшах». Любой запрос может попасть на любой инстанс; значение, сохранённое в глобальной переменной одного инстанса, невидимо остальным.
- **Проверка**: архитектурный тест `tests/architecture/test_no_process_state.py::test_no_module_level_mutable_state` (будет создан): AST-обход всех файлов `app/**/*.py`; нарушение — присваивание на уровне модуля, правая часть которого является литералом `{}`, `[]`, `set()`, вызовом `dict()`, `list()`, `set()`, `collections.deque()`, `collections.defaultdict()`, `collections.OrderedDict()`, либо имя которого объявлено без аннотации `Final` и далее изменяется в теле функций файла (`global <имя>`, `<имя>[...] =`, `<имя>.append(`, `<имя>.update(`, `<имя>.add(`, `<имя>.pop(`). Allowlist — таблица раздела 6 с указанием файла и имени; тест читает allowlist из `tests/architecture/process_state_allowlist.toml` и падает, если запись allowlist ссылается на несуществующее имя.
- **Применимость**: backend.

### SYS-05-R2 Запрет кэшей `functools` на данных из хранилищ

- **Формулировка**: Функции и методы в `app/modules/**` не должны использовать декораторы `functools.lru_cache`, `functools.cache`, `functools.cached_property` и `async_lru.alru_cache`; в `app/core/**` эти декораторы допустимы только для функций из allowlist неизменяемой конфигурации (раздел 6).
- **Обоснование**: ADR-003, раздел 3, правило 5: кэш в памяти процесса разрешён только для неизменяемой конфигурации, загруженной при старте; кэш на функции, читающей PostgreSQL или Redis, даёт разным инстансам разные ответы.
- **Проверка**: архитектурный тест `tests/architecture/test_no_process_state.py::test_no_functools_cache_on_data` (будет создан): AST-поиск декораторов с указанными именами (прямой импорт и через `functools.`); для `app/modules` — любое вхождение является нарушением; для `app/core` — нарушение, если полное имя функции отсутствует в `process_state_allowlist.toml`. Дополнительно правило ruff `B019` (`lru_cache` на методах) включено в `pyproject.toml`.
- **Применимость**: backend.

### SYS-05-R3 Запрет записи на диск инстанса

- **Формулировка**: Код в `app/` не должен создавать, записывать или изменять файлы и каталоги на файловой системе инстанса; единственное исключение — каталог `tempfile.gettempdir()` в пределах обработки одного запроса или сообщения с удалением до его завершения.
- **Обоснование**: CLAUDE.md «Масштабирование и состояние»: файлы не хранятся на диске инстанса; сами файлы — в MinIO, метаданные — в PostgreSQL (ADR-003, п. 2.8 A; ADR-007). Файл, записанный одним инстансом, недоступен другим и теряется при остановке контейнера.
- **Проверка**: (1) архитектурный тест `tests/architecture/test_no_process_state.py::test_no_disk_writes` (будет создан): AST-поиск вызовов `open(...)` с аргументом `mode`, содержащим `w`, `a`, `x` или `+`, методов `Path.write_text`, `Path.write_bytes`, `Path.mkdir`, `Path.touch`, `Path.unlink`, `Path.rename`, функций `os.makedirs`, `os.mkdir`, `os.remove`, `os.rename`, `shutil.copy`, `shutil.copy2`, `shutil.copyfile`, `shutil.move`, `shutil.rmtree` вне функций, в которых в той же области видимости используется `tempfile.TemporaryDirectory`, `tempfile.NamedTemporaryFile` или `tempfile.mkdtemp`; каталог `app/*/migrations` и `cli/` исключены (скаффолдер пишет исходники, миграции — не runtime). (2) Контейнеры `api` и `worker` в `docker-compose.ci.yml` и в Helm (`securityContext.readOnlyRootFilesystem: true`, `emptyDir` на `/tmp`) запускаются с файловой системой только для чтения и `tmpfs` на `/tmp`: любая запись вне `/tmp` падает на стенде N3 и в kind (SYS-11).
- **Применимость**: backend, deploy.

### SYS-05-R4 Отсутствие sticky-сессий

- **Формулировка**: Балансировка запросов на инстансы роли `api` должна выполняться по кругу без привязки клиента к инстансу: в `haproxy.cfg` не должно быть директив `cookie`, `stick on`, `stick-table` с `store server`, `balance source`, `balance uri`, `hash-type` для backend-ов `be_api` и `be_api_ws`.
- **Обоснование**: CLAUDE.md «Масштабирование и состояние»: «Sticky-сессии не используются. Корректность не зависит от того, на какой инстанс попал клиент»; ADR-012, раздел 3.5.
- **Проверка**: (1) тест конфигурации `tests/architecture/test_haproxy_cfg.py::test_no_sticky_directives` (будет создан; читает `deploy/config/haproxy/haproxy.cfg`, разбирает секции `backend be_api` и `backend be_api_ws`, ищет перечисленные директивы). (2) Тест на стенде N3 `tests/n_instances/core/test_round_robin.py::test_requests_hit_all_instances` (будет создан): 30 запросов `GET /api/v1/auth/.well-known/jwks.json` через HAProxy из одного клиента с одним cookie дают не менее трёх различных значений `X-Instance-Id`.
- **Применимость**: deploy, tests.

### SYS-05-R5 Заголовок `X-Instance-Id`

- **Формулировка**: Каждый HTTP-ответ инстанса роли `api` (включая ответы с ошибками и ответ handshake WebSocket) должен содержать заголовок `X-Instance-Id` со значением `instance_id` из ADR-010 (`HOSTNAME` контейнера); HAProxy на стендах без переменной `FLT_EXPOSE_DOCS` должен удалять этот заголовок из ответов клиентам.
- **Обоснование**: Тесты масштабируемости (R47–R52) и smoke-тесты обязаны доказывать, что шаги сценария выполнились на разных инстансах; без идентификатора инстанса в ответе это недоказуемо. На prod идентификатор контейнера клиентам не нужен, поэтому HAProxy его снимает тем же переключателем, что открывает документацию API (ADR-012).
- **Проверка**: unit-тест middleware shared kernel `tests/core/http/test_instance_header.py` (будет создан; маркер `req("SYS-05-R5")`); тест конфигурации `tests/architecture/test_haproxy_cfg.py::test_instance_header_stripped_on_prod` (будет создан: наличие `http-response del-header X-Instance-Id` под `.if !defined(FLT_EXPOSE_DOCS)`).
- **Применимость**: backend, deploy.

### SYS-05-R6 Классификация состояния в ТЗ

- **Формулировка**: ТЗ каждой фичи должно относить каждый элемент состояния фичи ровно к одному хранилищу по таблице ниже и описывать его в разделе 6 ТЗ (6.1 PostgreSQL, 6.2 Redis, 6.3 MinIO); элементы, не попадающие ни в одну строку, не должны вводиться без изменения этой таблицы (статус `changed` SYS-05).
- **Обоснование**: CLAUDE.md «Масштабирование и состояние», таблица «Где хранится состояние»; ADR-003. Без явной классификации в ТЗ состояние оседает в памяти процесса «по умолчанию».
- **Проверка**: шаблон ТЗ (`feature-spec.md`, раздел 6) и проверка `flt-tools specs check` (SYS-12): в ТЗ со статусом `approved` и выше разделы 6.1–6.3 заполнены (либо содержат «Не применимо» с причиной); ревью на G1 сверяет классификацию с таблицей.
- **Применимость**: все (документация), tests (проверка спецификаций).

### SYS-05-R7 Таблицы модулей: схема, обязательные колонки, UUID v7

- **Формулировка**: Каждая таблица доменного модуля должна лежать в схеме PostgreSQL с именем модуля, наследовать `EntityBase` shared kernel и иметь колонки `id uuid` (первичный ключ, значение `new_id()` — UUID v7), `created_at timestamptz`, `updated_at timestamptz`, `version integer`; исключение — технические таблицы `outbox`, `processed_events`, `scheduled_runs`, `alembic_version` и таблицы, помеченные в модели атрибутом `__flt_technical__ = True` с обоснованием в спецификации модуля.
- **Обоснование**: ADR-003, п. 2.1 A, 2.3 A, 2.4 A и правило 10 раздела 3; ADR-002, раздел 3.4. Единые колонки нужны оптимистической блокировке (R18) и конвенциям REST (SYS-03).
- **Проверка**: архитектурные тесты `tests/architecture/test_schema_ownership.py` (будут созданы; выполняются после `make migrate` на тестовой БД): `test_public_schema_has_no_tables`, `test_tables_live_in_module_schema`, `test_no_cross_schema_foreign_keys` (запрос к `information_schema.table_constraints` и `referential_constraints`), `test_mandatory_columns_present`, `test_primary_keys_are_uuid`; `test_new_id_is_uuid_v7` в `tests/core/test_ids.py` (версия UUID = 7, монотонность 1 000 подряд сгенерированных значений).
- **Применимость**: backend.

### SYS-05-R8 Граница PostgreSQL и MinIO

- **Формулировка**: Модель SQLAlchemy не должна объявлять колонки типа `LargeBinary`/`bytea`, кроме перечисленных в allowlist `tests/architecture/bytea_allowlist.toml` (криптографический материал до 4 КБ: `llm_gateway.provider_keys.ciphertext`, `llm_gateway.provider_keys.nonce`, `identity.refresh_tokens.token_hash`, `identity.one_time_tokens.token_hash`), а колонки `jsonb` не должны использоваться для содержимого, которое ТЗ описывает как файл (материал, медиа, аудио, экспорт).
- **Обоснование**: ADR-003, п. 2.8 A: файлы — в MinIO, `bytea` — только криптографический материал до 4 КБ, ориентир `jsonb` — до 1 МБ.
- **Проверка**: архитектурный тест `tests/architecture/test_schema_ownership.py::test_bytea_only_in_allowlist` (будет создан; обход `module.metadata.tables`); ограничение на размер `jsonb` — `CHECK (pg_column_size(<col>) <= 1048576)` в миграции для каждой `jsonb`-колонки пользовательского контента, наличие проверяет `test_jsonb_columns_have_size_check`; ревью раздела 5 ТЗ на G1.
- **Применимость**: backend.

### SYS-05-R9 Метаданные файлов в PostgreSQL

- **Формулировка**: Каждый объект MinIO должен иметь строку метаданных в таблице модуля-владельца, построенной на миксине `StoredFileMixin` shared kernel (`bucket`, `object_key`, `size_bytes`, `content_type`, `sha256`, `owner_user_id`, `status`), и модуль не должен обращаться к хранилищу иначе как через `FileStorage` shared kernel.
- **Обоснование**: ADR-003, п. 2.8 A; ADR-007; ADR-002, контракт import-linter 7 (`aioboto3`, `botocore` запрещены в модулях).

### SYS-05-R18 Оптимистическая блокировка через `version`

- **Формулировка**: Изменение сущности с колонкой `version` должно выполняться через ORM с `version_id_col`, запрос `PUT`/`PATCH` должен содержать текущее значение `version`, а конфликт версий (`StaleDataError` или несовпадение переданного `version`) должен возвращаться клиенту как `409` с кодом `core.version_conflict` (SYS-03-R17) в конверте `ErrorResponseV1`, без повторной попытки на сервере.

### SYS-05-R19 Инварианты уникальности — ограничениями PostgreSQL

- **Формулировка**: Правило вида «не более одной записи с таким сочетанием полей» должно быть выражено уникальным ограничением или уникальным индексом PostgreSQL (для таблиц с soft delete — частичным, `WHERE deleted_at IS NULL`), а не только проверкой в коде; нарушение (`IntegrityError` по уникальному индексу) должно возвращаться как `409` с кодом вида `<module>.<state_error>` (SYS-03, например `identity.email_taken`).

- **Применимость**: backend.

### SYS-05-R20 Распределённые блокировки: где обязательны и как устроены

- **Формулировка**: Операция, которую в кластере должен выполнять ровно один исполнитель (периодическая задача, relay outbox, перестроение индекса, перешифровка ключей, миграция данных воркером, уборка), должна выполняться под блокировкой `locks.acquire(name, ttl, wait)` shared kernel (`SET <module>:lock:<name> <token> NX PX`, освобождение и продление — Lua-скриптами с проверкой токена) и дополнительно защищаться инвариантом PostgreSQL (уникальное ограничение, `version`, `FOR UPDATE SKIP LOCKED`); блокировка не должна быть единственной гарантией корректности.
- **Обоснование**: ADR-003, п. 2.7 A: блокировка — средство избежать двойной работы; при failover Sentinel два инстанса могут одновременно держать её, поэтому критическая секция обязана быть идемпотентной или защищённой инвариантом.
- **Проверка**: интеграционные тесты shared kernel с реальным Redis `tests/core/redis/test_locks.py` (будут созданы): `test_second_acquire_fails_until_ttl`, `test_release_ignores_foreign_token`, `test_extend_requires_token`, `test_lock_expires_without_heartbeat`; архитектурный тест `test_scheduled_tasks_run_under_lock` (каждая задача из `schedules.py` модулей выполняется планировщиком shared kernel, который берёт блокировку, — проверка, что модули не регистрируют собственные циклы `asyncio.create_task` в lifespan); тест на стенде N3 по шаблону R51.
- **Применимость**: backend.

### SYS-05-R21 Идемпотентность консьюмеров и периодических задач

- **Формулировка**: Обработчик Kafka должен быть идемпотентным через вставку в `<module>.processed_events` в одной транзакции с бизнес-изменением (ADR-004), а периодическая задача — давать тот же результат при повторном запуске; повторная доставка того же `event_id` не должна менять данные и не должна публиковать событие повторно.
- **Обоснование**: CLAUDE.md «Взаимодействие»: консьюмеры идемпотентны; at-least-once доставка Kafka и повтор при остановке воркера (R31).
- **Проверка**: интеграционный тест каждого консьюмера `test_<handler>_is_idempotent` (SYS-10: `TestKafkaBroker`, двойная публикация одного сообщения, сравнение состояния БД и числа строк `outbox`); тест на стенде N3 по шаблону R50; идемпотентность изменяющих REST-запросов (`Idempotency-Key`) — SYS-03.
- **Применимость**: backend.

### SYS-05-R22 Одна транзакция — один модуль

- **Формулировка**: Публичный API модуля (`Protocol` в `public/interfaces.py`) не должен принимать и возвращать `AsyncSession` или объекты моделей SQLAlchemy; вызываемый модуль открывает собственную сессию, а согласованность между модулями обеспечивается событиями через outbox.

### SYS-05-R23 Уровень изоляции и параметры соединения

- **Формулировка**: Engine SQLAlchemy должен создаваться с `isolation_level="READ COMMITTED"` и серверными параметрами `search_path=public`, `timezone=UTC`, `application_name=flt-<role>-<instance_id>`, `statement_timeout` 30 с для роли `api` и 10 мин для `worker`, `idle_in_transaction_session_timeout=60s`; блокирующие выборки (`SELECT ... ### SYS-05-R32 Длительность одного сообщения и разбиение заданий

### SYS-05-R34 Совместимость миграции с предыдущей версией кода (expand/contract)

- **Обоснование**: CLAUDE.md: «Миграции совместимы с предыдущей версией кода: при обновлении старые и новые инстансы работают одновременно»; ADR-003, п. 2.5 A.

### SYS-05-R40 Пулы соединений PostgreSQL по ролям и бюджет соединений

- **Формулировка**: Фабрика engine shared kernel должна задавать размер пула по роли запуска — `api`: `pool_size=10`, `max_overflow=10`; `worker`: `pool_size=5`, `max_overflow=5`; `all` — как `api`; `migrate` — `pool_size=1`, `max_overflow=0`; все роли — `pool_pre_ping=True`, `pool_recycle=1800`, `pool_timeout=10`; конфигурация стенда должна удовлетворять формуле `Σ по ролям (реплики × (pool_size + max_overflow)) + 20 ≤ 0.75 × max_connections`, а PgBouncer не должен добавляться, пока реплик роли `api` не более 6 и формула выполняется.
- **Обоснование**: ADR-003, п. 2.2 A и правило 4 раздела 3. Для стенда N3: `3 × 20 + 2 × 10 + 20 = 100 ≤ 150` при `max_connections = 200`.
- **Проверка**: unit-тест `tests/core/dao/test_engine_factory.py::test_pool_size_by_role` (будет создан); тест конфигурации SYS-11 `test_pg_connection_budget` (читает реплики из `docker-compose.yml`, `docker-compose.ci.yml`, `values*.yaml`, `max_connections` из конфигурации PostgreSQL и проверяет формулу); метрика `flt_db_pool_connections{state}` с алертом при `overflow` > 0 дольше 5 минут (ADR-010).
- **Применимость**: backend, deploy.

### SYS-05-R41 Готовность по ролям без Redis

- **Формулировка**: `/v1/ready` должен проверять только зависимости роли (`api` — PostgreSQL; `worker` — PostgreSQL и Kafka; `media_agent` — PostgreSQL и LiveKit) и отвечать `503` при их недоступности; результат проверки допустимо кэшировать в памяти процесса не дольше 5 секунд.
- **Обоснование**: ADR-003, правило 8; ADR-010, раздел 3.4: отказ Redis не должен снимать с балансировки все инстансы сразу; кэш 5 с — защита от шторма проверок HAProxy, compose и probes (исключение в разделе 6).
- **Проверка**: интеграционные тесты `tests/core/test_readiness.py` (будут созданы): `test_ready_503_without_postgres`, `test_ready_200_without_redis`, `test_worker_ready_503_without_kafka`, `test_ready_cache_ttl_5s`; smoke на стенде N3: после `docker stop flt-api-2` в `haproxy:8404/stats;csv` сервер в состоянии `DOWN` не позднее 10 с.
- **Применимость**: backend, tests.

### SYS-05-R42 Время: `timestamptz`, UTC и `Clock`

- **Формулировка**: Все колонки времени должны иметь тип `timestamptz`, значения — в UTC; код не должен вызывать `datetime.now()`, `datetime.utcnow()`, `datetime.today()`, `time.time()` для бизнес-времени — только `Clock.now()` shared kernel (tz-aware UTC), подменяемый в тестах.
- **Обоснование**: ADR-003, раздел 3, правило 3. Инстансы в разных часовых поясах контейнеров и naive-`datetime` дают расхождение данных между инстансами.
- **Проверка**: правила ruff `DTZ` (flake8-datetimez) включены в `pyproject.toml`; архитектурный тест `tests/architecture/test_clock_usage.py` (будет создан: AST-поиск `datetime.now`, `utcnow`, `today`, `time.time` в `app/` вне `app/core/time/`); `test_mandatory_columns_present` проверяет `DateTime(timezone=True)` у всех колонок `DateTime`.
- **Применимость**: backend.

### SYS-05-R43 Уборка просроченных и отозванных токенов (решает OQ-71, часть SYS-05)

- **Формулировка**: Модуль `identity` должен объявлять периодическую задачу `identity.purge_tokens` (ежесуточно в 03:00 UTC, под блокировкой планировщика по R28), которая удаляет пачками по 10 000 строк: `refresh_tokens` с `revoked_at` или `expires_at` старше срока хранения из SYS-02 и `one_time_tokens` с `used_at` или `expires_at` старше срока хранения из SYS-02; задача идемпотентна и записывает число удалённых строк в `identity.scheduled_runs`.
- **Обоснование**: OQ-71 (planned → SYS-02 для сроков, SYS-05 для задачи): таблицы токенов растут без ограничения; удаление пачками не держит блокировки и не конкурирует с входом пользователей. Рекомендованные сроки (90 дней для refresh-токенов, 30 дней для одноразовых) утверждает SYS-02.
- **Проверка**: интеграционный тест `tests/modules/identity/integration/test_purge_tokens.py` (будет создан: сид из 25 000 просроченных и 100 действующих токенов, запуск задачи, проверка, что действующие остались, просроченные удалены за 3 пачки, повторный запуск ничего не меняет); тест на стенде N3 R28 с этой задачей.
- **Применимость**: backend (модуль `identity`).

### SYS-05-R44 Состав и запуск стенда N3

- **Формулировка**: Стенд для тестов масштабируемости должен подниматься командой `docker compose -p flt -f deploy/docker-compose/docker-compose.yml -f deploy/docker-compose/docker-compose.ci.yml --profile ci up -d --wait --scale api=3` и содержать: `haproxy` (порт `8080` хоста без TLS, `8404` — только в сети compose), `api` × 3 (без публикации порта 8000 на фиксированный адрес; диапазон `8000-8009:8000` для прямого доступа тестов — R46), `worker` × 2, `migrate` (роль `migrate`, `restart: "no"`), `postgres` (`max_connections=200`, базы `flt` и `flt_test`), `redis` (один экземпляр, `requirepass`), `kafka` (один брокер, `replication.factor = 1`, автосоздание топиков выключено — топики создаёт `migrate`), `minio`, `frontend` (Nginx со статикой), по профилю `test` — `mailpit` и `mock-oidc`; OpenSearch, Qdrant, Prometheus, Grafana и Fluent Bit в профиль `ci` не входят.

### SYS-05-R45 Маркер `n_instances` и расположение тестов

- **Формулировка**: Тест масштабируемости должен находиться в каталоге `tests/n_instances/<module>/` (для shared kernel — `tests/n_instances/core/`), нести маркер `@pytest.mark.n_instances` и маркер критерия или требования (`ac(...)` или `req(...)`), пропускаться при запуске без параметра `--stand-url` (сообщение «нужен стенд N3») и не должен входить в подсчёт покрытия `make test-cov`.
- **Обоснование**: SDD_plan.md §5, шаг 5: тесты на N инстансах входят в тесты backend; ADR-011: `uv run pytest -m n_instances` в job `stand-n3`; шаблон ТЗ, раздел 13, использовал предварительное имя `multi_instance` — заменяется на `n_instances` (раздел 4.2).
- **Проверка**: регистрация маркера в `pyproject.toml` (`markers`), плагин `tests/n_instances/conftest.py` (опция `--stand-url`, автопропуск); архитектурный тест `tests/architecture/test_test_layout.py::test_n_instances_tests_marked` (будет создан: каждый тест в `tests/n_instances/**` имеет маркер `n_instances`, и ни один тест вне каталога его не имеет); SYS-10 (конфигурация coverage исключает каталог).
- **Применимость**: tests.

### SYS-05-R46 Фикстуры стенда N3

- **Формулировка**: Пакет `tests/n_instances/conftest.py` должен предоставлять фикстуры: `stand` — базовый URL через HAProxy (`--stand-url`, по умолчанию `http://127.0.0.1:8080`) и HTTP-клиент с cookie-jar; `instances` — упорядоченный словарь `instance_id → URL прямого доступа` для всех инстансов `api`, построенный командой `docker compose -p flt port --index <n> api 8000` и запросом `GET /v1/health` к каждому (значение `X-Instance-Id`); `on_instance(n)` — клиент, обращающийся напрямую к n-му инстансу; `stop_instance(name)` и `start_instance(name)` — `docker stop <name>` и `docker start <name>` для контейнеров `flt-api-<n>`, `flt-worker-<n>` с ожиданием состояния в HAProxy и гарантированным запуском остановленного контейнера в teardown; `ws(url)` — WebSocket-клиент с конвертом ADR-004; `pg` и `redis_direct` — прямые соединения к PostgreSQL и Redis стенда для проверок состояния; `kafka_reader(topic)` — тестовый консьюмер.
- **Обоснование**: Шесть обязательных сценариев (R47–R52) требуют одновременно пути через балансировщик и пути «на конкретный инстанс»; имена контейнеров compose — `<project>-<service>-<n>` (ADR-011).
- **Проверка**: тесты фикстур `tests/n_instances/core/test_fixtures.py` (будут созданы: `instances` содержит ровно 3 записи с разными `instance_id`; `on_instance(2)` возвращает `X-Instance-Id` второго инстанса; `stop_instance` переводит сервер в `DOWN` за ≤ 10 с, teardown возвращает `UP`).
- **Применимость**: tests.

### SYS-05-R51 Сценарий 5: глобальные лимиты и блокировки

### Пример 3. Распределённая блокировка с инвариантом PostgreSQL (SYS-05-R20)

```python
# app/modules/llm_gateway/jobs/reencrypt_keys.py — перешифровка ключей учеников (ADR-013, п. 3.4)
async def reencrypt_batch(locks: Locks, repo: ProviderKeyRepository, crypto: KeyCrypto) -> int:
    async with locks.acquire("reencrypt_keys", ttl=timedelta(seconds=30), wait=timedelta(seconds=0)):
        # heartbeat продлевает блокировку каждые 10 с, пока выполняется пачка
        async with repo.session() as session:
            rows = await repo.select_for_reencrypt(session, limit=1000)   # FOR UPDATE SKIP LOCKED
            for row in rows:
                row.ciphertext, row.nonce = crypto.reencrypt(row.ciphertext, row.nonce, row.key_version)
                row.key_version = crypto.active_version                   # version += 1 (R18)
            await session.commit()
            return len(rows)
```

Блокировка исключает параллельную пачку; `FOR UPDATE SKIP LOCKED` и `version` делают операцию корректной, даже если блокировка потеряна при failover Sentinel (ADR-003, п. 2.7 A).

## 7. Вне рамок

- Конкретные значения лимитов (быстрый тест, попытки входа) и сроки хранения данных — SYS-02 и SYS-08; здесь только механизм и максимумы TTL.
- Формат конверта WebSocket, имена каналов, envelope событий Kafka, ретраи и DLQ — SYS-04 (по ADR-004).
- Конвенции REST: поле `version` в запросах, коды `409 core.version_conflict` и `409 <module>.<state_error>` (нарушение уникальности) в `ErrorResponseV1` (SYS-03-R7, R17), `Idempotency-Key` — SYS-03.
- Конфигурация стендов (PostgreSQL `max_connections`, Redis `maxmemory`, Sentinel в Helm, `values-ci.yaml`, бэкапы), тест паритета compose и Helm и чек-лист VPS — SYS-11.
- Разведение тестовой БД и стенда local, фикстуры `redis_down`, `redis_no_persistent_keys`, `db_migrate`, заглушка LLM — SYS-10 (OQ-31).
- Состав job-ов CI, обязательные проверки и бюджет минут — SYS-12 (по ADR-011).
- Доступ клиентов к файлам, presigned URL и жизненный цикл объектов MinIO — ADR-007.
- Автомасштабирование (HPA) в Kubernetes — OQ-30, SYS-11.
- PgBouncer: не добавляется до порога R40; способ подключения — новый ADR при достижении порога.
- `LISTEN/NOTIFY` как ускоритель relay outbox — не используется до появления потребности (ADR-004, раздел 4.2).
