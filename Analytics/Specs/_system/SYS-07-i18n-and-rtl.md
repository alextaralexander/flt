## 1. Цель и область действия

- **Цель**: задать единые правила, по которым платформа с первого дня работает на русском, английском и арабском языках интерфейса (включая направление справа налево), отделяет язык интерфейса от изучаемых языков, корректно показывает текст со смешанным направлением, вязь и иероглифы, форматирует даты, числа и время по локали и часовому поясу пользователя и проверяет всё это автоматически. Правила обязательны для каждого модуля: без них строки UI, письма и ответы LLM расходятся по языкам, а RTL ломается при первом же новом экране.
- **Область действия**: frontend (app_shell и все модули `src/features`), backend (коды ошибок, письма и уведомления, форматирование в шаблонах, язык запросов к LLM, реестр языков), контракты REST и WebSocket (ключи и коды вместо текстов), тесты (unit, компонентные, E2E, визуальные), CI (проверка полноты переводов и правил ESLint). Локальный агент (ADR-008) — только в части строк трея (раздел 7).
- **Действует с этапа**: 1 (app_shell, переключение языка, E2E «ходячего скелета» на трёх языках — SDD_plan.md, этап 1 Г.7 и Г.11). Требования к изучаемым языкам (R24, R25) реализуются модулями `languages` и `learner_profile` на этапах 4–5, но их контракт фиксируется здесь.
- **Уточняет**: CLAUDE.md, разделы «Ключевые архитектурные требования» (пункт «i18n с первого дня») и «Frontend (boilerplate) → Отличия проекта от boilerplate», п. 4; ADR-005, разделы 3.3 «i18n» и 3.4 «RTL» (ADR задаёт механизм, эта спецификация — правила и значения: порядок определения языка, хранение выбора, система счисления, шрифты, bidi, часовые пояса); решает OQ-25.

## 3. Требования

### SYS-07-R1 Язык интерфейса и изучаемые языки — разные настройки с разными владельцами

- **Формулировка**: платформа должна хранить язык интерфейса пользователя в колонке `identity.users.ui_language` (тип `text`, значение — код из R2, по умолчанию результат определения по R3 при регистрации), а изучаемые языки с уровнями — в сущностях модуля `learner_profile` (`learner_language`: «ученик × изучаемый язык», глоссарий), и не должна выводить одно из другого ни в коде, ни в UI.
- **Обоснование**: CLAUDE.md «Ключевые архитектурные требования»: «язык интерфейса и изучаемый язык — разные настройки»; ADR-006 размещает `ui_language` в таблице `users` модуля `identity`, потому что язык нужен для писем регистрации и восстановления пароля (VIS-04, VIS-05) на этапе 2, когда модуля `learner_profile` ещё нет; изучаемые языки появляются на этапе 4 (STU-07, STU-33) и принадлежат `learner_profile`. Ученик, изучающий арабский, может пользоваться русским интерфейсом, и наоборот.
- **Проверка**: архитектурный тест `tests/architecture/test_i18n_ownership.py` (`<будет создан>`): в `module.metadata` модуля `identity` есть колонка `users.ui_language`, ни в одной другой схеме нет колонки с именем `ui_language`; в схеме `learner_profile` (с этапа 4) нет колонки `ui_language`. Контракт `identity` (`GET /api/v1/auth/me`) содержит поле `ui_language` — контрактный тест SYS-03.
- **Применимость**: backend.

### SYS-07-R2 Перечень языков интерфейса — один источник для backend и frontend

- **Формулировка**: перечень языков интерфейса должен задаваться константой `UI_LANGUAGES = ("ru", "en", "ar")` в shared kernel (`app/core/i18n/languages.py`) и константой `SUPPORTED_UI_LANGUAGES = ['ru', 'en', 'ar'] as const` во frontend (`src/lib/i18n/languages.ts`), с языком по умолчанию `ru` в обоих местах; добавление языка интерфейса должно выполняться только через изменение этой спецификации (новая версия) и обеих констант одновременно.
- **Обоснование**: CLAUDE.md: «Языки интерфейса на старте: русский, английский, арабский»; OQ-25 — язык по умолчанию `ru` (аудитория РФ, 152-ФЗ). Два списка, которые могут разойтись, дают письма на языке, которого нет в UI, или наоборот.
- **Проверка**: тест `src/testing/architecture/ui-languages-parity.test.ts` (`<будет создан>`) читает `app/core/i18n/languages.py` регулярным выражением и сравнивает с `SUPPORTED_UI_LANGUAGES`; на backend — `tests/core/i18n/test_languages.py`: `UI_LANGUAGES` содержит `DEFAULT_UI_LANGUAGE`, все значения проходят валидацию кода языка (R25); для каждого значения существуют каталоги `locales/<lang>/` во всех модулях (R11, R14).
- **Применимость**: backend, frontend.

### SYS-07-R3 Порядок определения языка интерфейса (решает OQ-25)

- **Формулировка**: frontend должен определять язык интерфейса в следующем порядке, беря первое найденное значение из `SUPPORTED_UI_LANGUAGES`: (1) `ui_language` аутентифицированного пользователя из ответа `GET /api/v1/auth/me`; (2) cookie `flt_ui_language` (R6); (3) первый поддерживаемый язык из `navigator.languages` после отбрасывания региона (`ru-RU` → `ru`, `ar-EG` → `ar`); (4) `ru`. Backend должен определять язык запроса в том же порядке, где источник (3) — заголовок `Accept-Language` по RFC 9110 (q-веса, первый поддерживаемый первичный субтег), и предоставлять результат как `RequestContext.locale` (SYS-03-R30; реализация — `app/core/i18n/request_language.py`, зависимость `RequestLanguage`) для контроллеров, обработчиков WebSocket и Kafka-консьюмеров (для консьюмеров — из заголовка сообщения `ui_language`, который публикатор копирует из контекста запроса); порядок источников в SYS-03-R30 должен совпадать с этим требованием, включая cookie `flt_ui_language` между профилем и `Accept-Language`.
- **Обоснование**: OQ-25 (planned → SYS-07): рекомендация «профиль → явный выбор → браузер → по умолчанию, по умолчанию русский» принята; порядок одинаков на обеих сторонах, иначе письмо после регистрации приходит не на том языке, который посетитель видел в форме. Явный выбор хранится в cookie, а не в `localStorage` (как предполагал пример в ADR-005, 3.3, делегируя выбор этой спецификации), потому что cookie читает и backend для анонимных запросов (быстрый тест VIS-03: язык объяснений модели платформы) без отдельного заголовка. Cookie — состояние браузера, не инстанса (CLAUDE.md «Масштабирование и состояние»).
- **Проверка**: unit-тест `src/lib/i18n/detect-language.test.ts` (`<будет создан>`) на все четыре источника и их приоритет, включая неподдерживаемые значения (`de`, пустая cookie, `zh-Hans`); backend — `tests/core/i18n/test_request_language.py`: таблица случаев (пользователь с `ui_language=ar` и `Accept-Language: en` → `ar`; аноним с cookie `en` и `Accept-Language: ar` → `en`; аноним без cookie с `Accept-Language: de, ar;q=0.8` → `ar`; ничего → `ru`). E2E Г.11: браузер с `locale: 'ar'` без cookie открывает портал на арабском (SYS-10).
- **Применимость**: backend, frontend, tests.

### SYS-07-R4 Языковой префикс в URL не используется

- **Формулировка**: маршруты frontend (`src/app/routes`) и пути REST не должны содержать язык (`/ru/...`, `/en/courses`, `?lang=`); язык определяется только по R3.
- **Обоснование**: OQ-25: «языковой префикс в URL не вводить на этапе 1»; одна ссылка работает для всех языков, SEO лендинга решается в ТЗ VIS-01 (пререндер или `cms`). Префикс в URL создаёт дубли маршрутов и ломает относительные адреса `/api`, `/ws`, `/flt-*` (ADR-012).
- **Проверка**: архитектурный тест `src/testing/architecture/reserved-paths.test.ts` (ADR-005, 3.5) дополняется проверкой: ни один путь роутера не начинается с `/<код языка>/` для кодов из `SUPPORTED_UI_LANGUAGES` и не содержит сегмента `:lang`; правило Spectral для OpenAPI (SYS-03, `src/tools/contracts/.spectral.yaml`): параметр `lang` или `locale` в query запрещён.
- **Применимость**: frontend, backend, CI.

### SYS-07-R5 Смена языка без перезагрузки страницы

- **Формулировка**: переключатель языка app_shell должен быть доступен на каждом экране (в шапке для анонима и в меню пользователя после входа), а смена языка должна выполняться вызовом `i18n.changeLanguage(lang)` без перезагрузки страницы с одновременным обновлением `document.documentElement.lang`, `document.documentElement.dir`, `DirectionProvider` Radix, cookie `flt_ui_language` и — для аутентифицированного пользователя — отправкой `PATCH /api/v1/auth/me` с полем `ui_language` (контракт — ТЗ STU-06; до этапа 4 вызов не выполняется и язык сохраняется только в cookie).
- **Обоснование**: STU-06; ADR-005, 3.4 (`applyDocumentDirection` на событие `languageChanged`); перезагрузка теряет состояние незавершённого стрима LLM и формы.
- **Проверка**: E2E `e2e/tests/app-shell/language-switch.spec.ts` (`<будет создан>`, этап 1 Г.11): переключение ru → en → ar без навигации, проверка `html[lang]`, `html[dir]`, текста заголовка на каждом языке и cookie; компонентный тест `src/components/layouts/language-switcher.test.tsx`.
- **Применимость**: frontend, tests.

### SYS-07-R6 Cookie явного выбора языка

- **Формулировка**: явный выбор языка должен сохраняться в cookie с именем `flt_ui_language`, значением — кодом из R2, атрибутами `Path=/`, `Max-Age=31536000`, `SameSite=Lax`, `Secure` при `https`, без `HttpOnly` (пишет frontend); backend не должен устанавливать эту cookie сам, а должен только читать её; любое другое значение cookie должно игнорироваться (переход к следующему источнику R3).
- **Обоснование**: один источник явного выбора для обеих сторон (R3); cookie без `HttpOnly` безопасна — она не содержит секрета и не влияет на авторизацию; `SameSite=Lax` достаточно, cookie не используется в проверке CSRF (ADR-006).
- **Проверка**: unit-тест `src/lib/i18n/cookie.test.ts` (`<будет создан>`): атрибуты записи; backend `tests/core/i18n/test_request_language.py`: значение `fr` в cookie игнорируется; проверка, что ни один обработчик не вызывает `set_cookie("flt_ui_language", ...)` — grep-тест в `tests/architecture/test_i18n_ownership.py`.
- **Применимость**: frontend, backend.

### SYS-07-R7 Ресурсы i18next: namespace на модуль, ключи по схеме

- **Формулировка**: каждый frontend-модуль должен хранить переводы в `src/features/<module>/locales/{ru,en,ar}.json` с namespace, равным имени модуля в kebab-case, и регистрировать их в `src/app/i18n-resources.ts` (ADR-005, 3.3); app_shell и shared-слой используют namespace `common` (`src/lib/i18n/locales/{ru,en,ar}/common.json`); ключи должны быть английскими, вложенными через точку по схеме `<screen>.<element>[.<state>]` (в коде обращение `t('login.form.submit')` внутри `useTranslation('identity')` или полное `identity:login.form.submit`); модуль не должен использовать namespace другого модуля.
- **Обоснование**: CLAUDE.md «Модульный монолит → Frontend»: модуль владеет своими ресурсами и может быть вынесен в микрофронтенд; ADR-005, 3.3 задаёт механизм. Схема ключей делает ключ самодокументируемым и позволяет `i18next-parser` сгруппировать их по экрану.
- **Проверка**: ESLint-правило `flt/i18n-namespace-matches-module` (`eslint-rules/i18n-namespace-matches-module.js`, `<будет создан>`): в файлах `src/features/<m>/**` аргумент `useTranslation(...)` и префикс ключей вида `x:y` равны `<m>` или `common`; архитектурный тест `src/testing/architecture/i18n-resources.test.ts` (`<будет создан>`): у каждого каталога `src/features/<m>` есть три файла locales и запись в `src/app/i18n-resources.ts`; формат ключей — регулярное выражение `^[a-z0-9]+(-[a-z0-9]+)*(\.[a-z0-9]+(-[a-z0-9]+)*)+(_(zero|one|two|few|many|other))?$`.
- **Применимость**: frontend, CI.

### SYS-07-R8 Множественное число — только суффиксами i18next по CLDR

- **Формулировка**: строки, зависящие от числа, должны объявляться ключами с суффиксами CLDR `_zero`, `_one`, `_two`, `_few`, `_many`, `_other` и интерполяцией `{{count}}` (ADR-005, 3.3: i18next v4 через `Intl.PluralRules`); для `ru` обязательны формы `one`, `few`, `many`, `other`; для `en` — `one`, `other`; для `ar` — все шесть; код не должен собирать множественное число конкатенацией или условиями (`count === 1 ? ... : ...`); библиотека `i18next-icu` не используется.
- **Обоснование**: русский и арабский имеют соответственно 4 и 6 категорий CLDR; встроенный механизм i18next v4 покрывает их без ICU-синтаксиса, который требует второй грамматики ключей и увеличивает ресурсы; `i18next-icu` отклонён, потому что `Intl.PluralRules` уже даёт правильные категории, а ICU-форматы дат и чисел заменяет R19.
- **Проверка**: `i18n:check` (R10) с правилом `i18next-parser` `pluralSeparator: '_'` и проверкой `plurals` — отсутствие формы категории для языка приводит к падению; unit-тест `src/lib/i18n/plurals.test.ts` (`<будет создан>`) на `t('common:lesson.minutes', {count})` для `count` ∈ {0, 1, 2, 3, 5, 11, 21, 100, 101} на трёх языках; ESLint `no-restricted-syntax` с селектором на тернарный оператор, оба операнда которого — вызовы `t()` с одинаковым префиксом ключа (`<будет создан>` в `eslint.config.js`).
- **Применимость**: frontend, CI.

### SYS-07-R9 Строки UI только через `t()`

- **Формулировка**: в JSX модулей и shared-компонентов не должно быть строковых литералов, видимых пользователю: правило `react/jsx-no-literals` в режиме `noStrings: true, ignoreProps: false` для `src/features/**`, `src/components/**`, `src/app/**` с перечнем `allowedStrings`, в который входят только пробел, знаки пунктуации `.`, `,`, `:`, `;`, `—`, `–`, `/`, `|`, `(`, `)`, `%`, `+`, `×` и цифры; `aria-label`, `title`, `placeholder`, `alt` — тоже через `t()`.
- **Обоснование**: CLAUDE.md «Определение готовности»: «Строки UI вынесены в i18n»; ADR-005, 3.3 и 3.6 вводят правило; перечень `allowedStrings` фиксируется здесь, чтобы его не расширяли под конкретный экран; окончательный перечень утверждается вместе с перечнем зеркалируемых иконок (OQ-82).
- **Проверка**: ESLint в `pnpm lint` (job `frontend`, ADR-011); перечень `allowedStrings` сверяется тестом `src/testing/architecture/eslint-config.test.ts` (`<будет создан>`) с таблицей этой спецификации.

### SYS-07-R22 Шрифты: собственная раздача, подмножества по `unicode-range`, без внешних хостов

- **Формулировка**: шрифты должны поставляться в сборке frontend (`src/assets/fonts/**/*.woff2`) и объявляться в `src/index.css` правилами `@font-face` с `font-display: swap` и `unicode-range` по письменностям; внешние хосты шрифтов (Google Fonts, jsDelivr, любой CDN) запрещены, CSP `font-src 'self'` (ADR-005, 3.8) не расширяется; стартовый набор — `Noto Sans` (подмножества `latin`, `latin-ext`, `cyrillic`, `cyrillic-ext`), `Noto Naskh Arabic` (подмножество `arabic`), на этапе 5 (STU-11) добавляются `Noto Sans SC`, `Noto Sans JP`, `Noto Sans KR` подмножествами по диапазонам CJK; стек `--font-sans` в `@theme`: `"Noto Sans", "Noto Naskh Arabic", system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, "Noto Sans CJK SC", sans-serif`; для арабского текста размер строки `line-height` не ниже `1.6` (класс `leading-relaxed` на `html[lang=ar]` в `src/index.css`); размер каждого файла подмножества не должен превышать 150 КиБ.
- **Обоснование**: CLAUDE.md «Персональные данные»: запрос шрифта к Google передаёт IP пользователя за рубеж — 152-ФЗ; доступность внешних CDN из РФ нестабильна; `unicode-range` позволяет браузеру скачивать только подмножества для символов на странице, поэтому CJK-шрифты не нагружают пользователей с латиницей; Noto покрывает все письменности реестра языков одним семейством.
- **Проверка**: архитектурный тест `src/testing/architecture/fonts.test.ts` (`<будет создан>`): в `dist/` после `pnpm build` нет ссылок на `fonts.googleapis.com`, `fonts.gstatic.com`, `cdn.jsdelivr.net`; каждое правило `@font-face` содержит `unicode-range` и `font-display: swap`; размер файлов ≤ 150 КиБ; E2E проект `ar`: запрос шрифта `Noto Naskh Arabic` идёт на `self` (перехват `page.on('request')`), на странице нет запросов к сторонним хостам (общая проверка SYS-02).
- **Применимость**: frontend, CI.

### SYS-07-R23 Атрибут `lang` на тексте изучаемого языка

- **Формулировка**: любой элемент, содержащий текст изучаемого языка (слово в словаре, задание, ответ ученика, пример произношения), должен иметь атрибут `lang` с кодом языка из реестра (через `<Bidi lang>` R20 или напрямую на блочном контейнере), чтобы браузер выбирал глифы (`zh-Hans` против `ja` для одного и того же иероглифа), правила переноса и синтезатор речи браузера.
- **Обоснование**: STU-10, STU-11: иероглифы одного кода Unicode выглядят по-разному в китайском и японском шрифтах; без `lang` браузер берёт шрифт по языку документа.
- **Проверка**: компонентные тесты модулей `dictionary`, `lessons` (этапы 2–5) проверяют `lang` на карточках; правило Testing Library в shared `src/testing/test-utils.tsx`: хелпер `expectLearningText(element, code)`; ревью ТЗ фич — раздел «UI» шаблона требует указать элементы с текстом изучаемого языка (раздел 4.2).
- **Применимость**: frontend, tests.

### SYS-07-R24 Реестр языков — единственный источник метаданных языка

- **Формулировка**: модуль `languages` (этап 4, STU-08; расширение — этап 5, STU-09–STU-11) должен вести реестр языков с полями `code` (BCP-47, R25), `name_native`, `names` (названия на языках интерфейса — ключи i18n `languages:<code>`), `script` (ISO 15924: `Latn`, `Cyrl`, `Arab`, `Hans`, `Hant`, `Jpan`, `Kore`, `Hebr`, `Grek`), `direction` (`ltr` или `rtl`), `search_analyzer` (ключ группы анализаторов ADR-014: `ru`, `en`, `ar`, `zh`, `ja`, `ko`, `und`), `transliteration_schemes` (перечень идентификаторов схем: `pinyin`, `romaji`, `ala_lc`, `bgn_pcgn`, `iso_9`; пустой для латиницы), `is_learning_language`, `is_ui_language`; публичный API модуля (`app/modules/languages/public`) должен предоставлять `LanguageRegistry` (`get(code)`, `list(learning_only=False)`), а frontend — тот же реестр через `GET /api/v1/languages` с кэшем TanStack Query; другие модули не должны хранить собственные таблицы языков и не должны выводить направление или письменность из кода языка самостоятельно; до этапа 4 shared kernel предоставляет статическую таблицу `app/core/i18n/languages.py` только для языков интерфейса (R2) с теми же полями.
- **Обоснование**: глоссарий «Реестр языков» — «точка расширения для плагинов, добавляющих языки» (SYS-09); ADR-014, 2.6 — поля `text_<lang>` по кодам реестра; направление и письменность нужны `dictionary`, `lessons`, `speech`, `materials` — дублирование таблицы в каждом модуле неизбежно разойдётся.
- **Проверка**: архитектурный тест `tests/architecture/test_no_language_tables_outside_registry.py` (`<будет создан>`): ни одна таблица вне схемы `languages` не имеет колонок `script`, `direction`, `text_direction`; контрактный тест SYS-03 на `GET /api/v1/languages`; тест модуля `languages`: для каждого языка с `is_learning_language` поле `search_analyzer` существует в шаблонах индексов ADR-014.
- **Применимость**: backend, frontend.

### SYS-07-R25 Формат кода языка — канонический BCP-47 везде

- **Формулировка**: все идентификаторы языков в данных, контрактах REST и AsyncAPI, ключах i18n, именах файлов ресурсов, полях индексов и payload Qdrant должны быть тегами BCP-47 в канонической форме (`en`, `ru`, `ar`, `zh-Hans`, `zh-Hant`, `pt-BR`, `sr-Cyrl`), валидируемыми Pydantic-типом `LanguageCode` shared kernel (`app/core/i18n/types.py`, регулярное выражение `^[a-z]{2,3}(-[A-Z][a-z]{3})?(-[A-Z]{2})?$` плюс проверка по реестру); суффикс поля индекса OpenSearch `text_<key>` берётся из `search_analyzer` реестра, а не из кода; имена файлов ресурсов i18n используют код как есть (`zh-Hans.json`).
- **Обоснование**: ADR-014 (`text_zh`, `language` в payload), SYS-04 (поле `locale` в событиях, пример `"locale": "ru"` в ADR-004); разнобой `zh_CN`, `zh-cn`, `chi` в разных модулях ломает поиск и сопоставление.
- **Проверка**: правило Spectral SYS-03/SYS-04: поля с именами `language`, `ui_language`, `learning_language`, `locale` в контрактах имеют `pattern` из этого требования; unit-тест `tests/core/i18n/test_language_code.py`; ESLint-проверка имён файлов в `locales/` по тому же выражению (архитектурный тест R7).
- **Применимость**: backend, frontend, CI.

### SYS-07-R26 Тесты: три языка, RTL-скриншоты, мобильный размер

- **Формулировка**: (а) сквозной E2E «ходячего скелета» (этап 1 Г.11) и каждый E2E-сценарий ТЗ, помеченный в разделе «UI» как «многоязычный», должны выполняться параметризованно на `ru`, `en`, `ar` (проекты Playwright `chromium-desktop`, `chromium-mobile`, `ar` — ADR-005, 3.7, плюс параметр `locale` сценария); (б) проект `ar` должен делать скриншотные сравнения лэйаута app_shell (шапка, навигация, меню пользователя, переключатель языка, диалог ошибки) с допуском `maxDiffPixelRatio: 0.01`; (в) компонентные тесты рендерят компоненты с реальными ресурсами `ru` через `src/testing/test-utils.tsx` и ищут элементы по роли и `aria-label`, а не по тексту; (г) каждая история Storybook компонентов `src/components/ui` должна проходить в `@storybook/addon-vitest` с глобальным `direction: rtl` и `direction: ltr` (два проекта Vitest); (д) unit-тесты `src/lib/i18n/direction.test.ts` покрывают `getDirection` для всех языков реестра.
- **Обоснование**: CLAUDE.md «TDD → E2E: ключевые пользовательские сценарии из спецификаций, в т.ч. RTL-языки»; SDD_plan.md этап 1 Г.11 (переключение трёх языков) и SYS-10 (E2E на десктопном и мобильном размерах).
- **Проверка**: job `e2e` CI (ADR-011) с тремя проектами; снимки хранятся в `e2e/__screenshots__/ar/`; `pnpm test` включает проекты Vitest `storybook-ltr` и `storybook-rtl`; SYS-10 фиксирует маркировку сценариев.
- **Применимость**: tests, CI.

### SYS-07-R27 Строки локального агента

- **Формулировка**: строки трея и уведомлений локального агента (ADR-008, этап 4) должны храниться в `src/agent/flt_agent/locales/{ru,en,ar}.json` с теми же ключами-схемами и проверкой полноты, что и backend (R13), язык агента должен выбираться из `ui_language`, который платформа передаёт в `agent.hello_ack`, с запасным вариантом — язык ОС и затем `en`.
- **Обоснование**: агент — часть интерфейса ученика; правило «строки UI вынесены в i18n» распространяется на него.
- **Проверка**: тест `src/agent/tests/test_locales_complete.py` (`<будет создан>`, этап 4) — те же проверки, что в `tests/architecture/test_i18n_templates_complete.py`.

### Пример 3. Определение языка запроса на backend и письмо получателю (SYS-07-R3, SYS-07-R13, SYS-07-R14)

```python
# app/core/i18n/request_language.py
RequestLanguage = Annotated[str, Depends(resolve_request_language)]

async def resolve_request_language(request: Request, user: CurrentUserOrNone) -> str:
    """Язык запроса: профиль → cookie flt_ui_language → Accept-Language → ru."""
    if user is not None and user.ui_language in UI_LANGUAGES:
        return user.ui_language
    cookie = request.cookies.get("flt_ui_language")
    if cookie in UI_LANGUAGES:
        return cookie
    return pick_from_accept_language(request.headers.get("accept-language"), UI_LANGUAGES, DEFAULT_UI_LANGUAGE)
```

### Пример 4. Форматирование и часовой пояс на frontend (SYS-07-R19, SYS-07-R21)

```ts
// src/lib/i18n/format.ts
const INTL_LOCALES = { ru: 'ru', en: 'en-GB', ar: 'ar-u-nu-latn-ca-gregory' } as const;

export function formatDateTime(iso: string, lng: UiLanguage, timeZone: string): string {
  return new Intl.DateTimeFormat(INTL_LOCALES[lng], { dateStyle: 'medium', timeStyle: 'short', timeZone })
    .format(new Date(iso));
}
```

`formatDateTime('2026-10-10T12:00:00Z', 'ar', 'Asia/Riyadh')` → `10 أكتوبر 2026، 15:00` (латинские цифры). Вызов `new Date(iso).toLocaleString()` в компоненте — нарушение R19.

## 7. Вне рамок

- Выбор пользователем системы счисления (`arab`) или календаря (хиджра) — не делается; при появлении запроса — изменение таблицы R19 через `changed`-версию и поле профиля (ТЗ STU-24 «продвинутые параметры»).
- Ввод текста на вязи и иероглифах (виртуальная клавиатура, IME, транслитерация при вводе) — ТЗ STU-09–STU-11 (этап 5); здесь — только `dir` и `lang`.
- Перевод пользовательского контента (курсы, записи, сообщения) — не выполняется; контент показывается на языке автора с `<Bidi lang>`.
- Языковой префикс в URL и SEO лендинга — ТЗ VIS-01.
- Форматы дат и времени в самих контрактах REST — SYS-03; формат событий Kafka — SYS-04.
- Качество ответов LLM на арабском и CJK (выбор модели) — SYS-08 и ТЗ STU-01, STU-03.
- Локализация документации API (`/api/docs`) — не делается, документация на английском.
- Строки интерфейса плагинов и их ресурсы — SYS-13.
