## 1. Контекст

- **Проблема**: монолит запускается в N инстансах без состояния в процессе (CLAUDE.md, «Масштабирование и состояние»), а каждый модуль владеет своими данными и готов к выделению в микросервис (CLAUDE.md, «Модульный монолит»). Нужно зафиксировать, как именно это обеспечивается на уровне хранилищ: PostgreSQL (схемы, пул соединений, ключи, базовые колонки, миграции без простоя), Redis (клиент, префиксы, TTL, блокировки, лимиты, pub/sub, отказ Redis, Sentinel) и граница между PostgreSQL и MinIO для крупных файлов.
- **Почему сейчас**: этап 1, пункт Г.4 (shared kernel: база SQLAlchemy и Alembic для модулей, клиент Redis с префиксами, распределённые блокировки) и Г.8 (миграции отдельным шагом в docker-compose и Helm). Без этого решения нельзя писать SYS-05 и спецификацию shared kernel.
- **Ограничения**:
  - CLAUDE.md, «Масштабирование и состояние»: состояние только в PostgreSQL, MinIO и Redis; у всех ключей Redis есть TTL; потеря Redis не теряет постоянных данных; оптимистические блокировки и уникальные ограничения; миграции отдельным шагом и совместимы с предыдущей версией кода; в Kubernetes Redis с репликой и Sentinel, в docker-compose один экземпляр.
  - CLAUDE.md, «Модульный монолит»: схема PostgreSQL на модуль, свои миграции, без FK, JOIN и `relationship` между модулями; Redis — только ключи с префиксом `<module>:`.
  - Решения этапа 0: OQ-07 (prod — docker-compose на VPS в РФ, Helm проверяется в kind), OQ-13 (стартовая нагрузка: 100 одновременных пользователей, 300 WebSocket, p95 REST ≤ 300 мс), OQ-31 (разведение тестовой БД — SYS-10).
  - Boilerplate (`src/backend/py-monolyth`): SQLAlchemy 2.0 async + asyncpg, одна схема `PG_SCHEMA` на сервис (`alembic env.py` подставляет её в `target_metadata.schema`), engine с параметрами `POOL_SIZE=10`, `POOL_MAX_OVERFLOW=5`, `POOL_RECYCLE=240`; базовая модель `py_main_lib.entities.alchemy.BaseEntityModel` даёт `id` UUID v4, `created_by: String NOT NULL`, `created_date`, `last_modified_by`, `last_modified_date`, `is_deleted`, без колонки версии; `MIGRATE_ON_START=True` по умолчанию — каждый инстанс применяет миграции при старте; Redis — один клиент `redis.asyncio.Redis` на процесс (`app/core/dao/caching/redis_conn.py`) и `RedisDAO` с `setex(expire=3600)` по умолчанию, при этом сырой клиент доступен и позволяет `SET` без TTL; блокировок, лимитов и pub/sub в boilerplate нет.
- **Если не решить**: модули начнут писать таблицы в общую схему и обращаться к сырому клиенту Redis, появятся ключи без TTL и запросы между схемами, миграции при старте N инстансов будут конкурировать, а выделение модуля в микросервис потребует переписывания слоя данных.
- **Ссылки**: CLAUDE.md «Масштабирование и состояние», «Модульный монолит», «Отличия проекта от boilerplate» (п. 10); SDD_plan.md этап 1 А.3, Б.5, Г.4, Г.8; OQ-07, OQ-13, OQ-17, OQ-31; ADR-002, ADR-004, ADR-006, ADR-007.

## 2. Рассматриваемые варианты

Решение состоит из восьми независимых подвопросов; варианты рассматриваются внутри каждого.

### 2.1. Изоляция данных модулей в PostgreSQL

#### Вариант A. Одна база `flt`, схема на модуль, одна роль БД

- **Описание**: одна база данных `flt`; каждый модуль владеет схемой с именем модуля (`identity`, `llm_gateway`, `dictionary`); схема `public` не содержит таблиц (только расширения); модели объявляют схему явно через `MetaData(schema="<module>")`; `search_path` соединения — `public` (для функций расширений), поэтому любое обращение к таблице без имени схемы падает; одна роль `flt` — владелец всех схем; у каждого модуля свой каталог миграций Alembic, своя секция `alembic.ini` и своя таблица `alembic_version` в своей схеме (ADR-002, вариант H).
- **Плюсы**:
  - границы владения видны в DDL и проверяются архитектурным тестом (таблица лежит в схеме своего модуля, FK между схемами отсутствуют);
  - один пул соединений на инстанс, одна транзакция на запрос внутри модуля;
  - выделение модуля: `pg_dump --schema=<module>` переносит данные модуля целиком.
- **Минусы**:
  - одна роль БД не мешает модулю прочитать чужую схему — защищает только архитектурный тест;
  - JOIN между схемами технически возможен, нужен запрет на уровне кода (ADR-002: import-linter не видит SQL) — дополняется тестом на `FOREIGN KEY` между схемами по `information_schema`.
- **Масштабирование на N инстансах**: нейтрально — инстансы делят одну базу; версия записи и уникальные ограничения защищают от конкурентных изменений.
- **Выделение модулей в микросервисы**: помогает — схема переносится в отдельную базу без изменения моделей и миграций.
- **Трудоёмкость и риски**: низкая; переделка `alembic env.py` и базы моделей boilerplate (ADR-002).

#### Вариант B. Одна база, схема и отдельная роль БД на модуль

- **Описание**: как A, плюс роль `flt_<module>` на каждый модуль с правами только на свою схему; пул соединений на модуль.
- **Плюсы**:
  - СУБД сама запрещает чтение чужой схемы.
- **Минусы**:
  - пул соединений на модуль: при 20 модулях и N = 3 суммарное число соединений растёт кратно числу модулей, нужен PgBouncer с первого дня;
  - транзакция на запрос невозможна при вызове нескольких модулей через разные соединения — тот же эффект, что и в микросервисах, но уже сейчас;
  - управление 20 ролями и паролями в `.env` и Vault.
- **Масштабирование на N инстансах**: хуже — число соединений = N × модули × пул.
- **Выделение модулей в микросервисы**: помогает так же, как A.
- **Трудоёмкость и риски**: средняя; риск исчерпания `max_connections`.

#### Вариант C. База данных на модуль

- **Описание**: отдельная база PostgreSQL на каждый модуль в одном кластере.
- **Плюсы**:
  - полная изоляция, идентичная микросервисной.
- **Минусы**:
  - 20 баз в docker-compose и Helm, 20 пулов на инстанс, бэкапы и мониторинг на каждую;
  - невозможны даже служебные запросы между модулями (например, отчёты администратора платформы собираются только в приложении).
- **Масштабирование на N инстансах**: как B.
- **Выделение модулей в микросервисы**: помогает максимально.
- **Трудоёмкость и риски**: высокая; несоразмерно для MVP (OQ-13: 10 000 пользователей за год).

### 2.2. Пул соединений и PgBouncer

#### Вариант A. Пул SQLAlchemy на инстанс, размер по роли, без PgBouncer

- **Описание**: `create_async_engine` с пулом на процесс; размер зависит от роли запуска (ADR-004): роль `api` — `pool_size=10`, `max_overflow=10`; роль `worker` — `pool_size=5`, `max_overflow=5`; роль `all` (локальная разработка) — как `api`. `pool_pre_ping=true`, `pool_recycle=1800`, `pool_timeout=10`. PostgreSQL `max_connections=200`. Контрольная формула фиксируется в SYS-05: `Σ по ролям (реплики × (pool_size + max_overflow)) + 20 (резерв: migrate, экспортёры, администратор) ≤ 0.75 × max_connections`. Для стенда из N = 3 `api` и 2 `worker`: 3 × 20 + 2 × 10 + 20 = 100 ≤ 150.
- **Плюсы**:
  - нет лишнего контейнера; asyncpg использует prepared statements без ограничений;
  - при 100 одновременных пользователях (OQ-13) и p95 ≤ 300 мс 60 соединений роли `api` достаточно: 60 соединений × (1000 / 300) ≈ 200 запросов к БД в секунду.
- **Минусы**:
  - при росте реплик выше 6 `api` нужен PgBouncer, и переход потребует отключить кэш prepared statements asyncpg.
- **Масштабирование на N инстансах**: линейный рост соединений с N; ограничение задаётся формулой и проверяется тестом конфигурации (SYS-11).
- **Выделение модулей в микросервисы**: нейтрально — у каждого сервиса свой пул.
- **Трудоёмкость и риски**: низкая.

#### Вариант B. PgBouncer в режиме transaction с первого дня

- **Описание**: контейнер PgBouncer между инстансами и PostgreSQL; пул на инстанс остаётся, но соединения мультиплексируются.
- **Плюсы**:
  - число соединений к PostgreSQL не зависит от N.
- **Минусы**:
  - режим transaction несовместим с серверными prepared statements asyncpg: требуется `statement_cache_size=0` и отказ от `SET`-команд уровня сессии (`statement_timeout` переносится в параметры роли);
  - `LISTEN/NOTIFY` и advisory locks уровня сессии недоступны;
  - ещё один контейнер в docker-compose и Helm, ещё одна точка отказа и метрики.
- **Масштабирование на N инстансах**: лучше при N > 6.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: средняя; риск трудноуловимых ошибок с prepared statements.

### 2.3. Первичные ключи

#### Вариант A. UUID v7, генерируется приложением

- **Описание**: все первичные ключи — `uuid` типа UUID v7 (RFC 9562: старшие 48 бит — миллисекунды Unix-времени, остальное — случайные). Генерирует shared kernel функцией `new_id()`: при Python 3.14 (ADR-001) — `uuid.uuid7()` стандартной библиотеки, при 3.13 — пакет `uuid-utils`. В PostgreSQL 18 есть `uuidv7()`, он используется как `server_default` только в миграциях данных.
- **Плюсы**:
  - монотонно растут по времени: вставки идут в правый конец B-tree, индекс не фрагментируется, `WAL` на вставку меньше, чем у v4;
  - ID известен до `INSERT`: событие outbox и ключ идемпотентности формируются в той же транзакции без `RETURNING`;
  - глобально уникальны между модулями и инстансами, не выдают количество записей (в отличие от `bigserial`).
- **Минусы**:
  - раскрывает время создания записи (приемлемо: время создания и так отдаётся API как `created_at`; для секретов — токенов, кодов подтверждения — UUID как значение не используется, только случайные байты);
  - 16 байт против 8 у `bigint`.
- **Масштабирование на N инстансах**: генерация без координации между инстансами.
- **Выделение модулей в микросервисы**: помогает — ссылки между модулями по ID остаются валидными при переносе данных.
- **Трудоёмкость и риски**: низкая; зависимость `uuid-utils` снимается при переходе на Python 3.14.

#### Вариант B. UUID v4 (как в boilerplate)

- **Описание**: `uuid.uuid4()` из `BaseEntityModel` py-main-lib.
- **Плюсы**:
  - ничего не менять.
- **Минусы**:
  - случайные ключи: вставки в случайные страницы индекса, рост размера индекса и WAL на объёмных таблицах (`word_review`, `progress`, журнал аудита);
  - сортировка по ID не совпадает с порядком создания, нужен отдельный индекс по `created_at` для пагинации по курсору.
- **Масштабирование на N инстансах**: как A.
- **Выделение модулей в микросервисы**: как A.
- **Трудоёмкость и риски**: нулевая сейчас, рост стоимости индексов позже.

#### Вариант C. `bigint` с последовательностью

- **Описание**: `GENERATED ALWAYS AS IDENTITY`.
- **Плюсы**:
  - компактно, быстро.
- **Минусы**:
  - ID известен только после `INSERT`; последовательности принадлежат базе — при переносе модуля в другую базу ID разных модулей начнут совпадать, ссылки по ID между модулями теряют глобальную уникальность;
  - раскрывает количество записей в публичных URL.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: мешает.
- **Трудоёмкость и риски**: низкая сейчас, высокая при выделении.

### 2.4. Базовые колонки, оптимистическая блокировка и удаление

#### Вариант A. Собственная база моделей shared kernel: `id`, `created_at`, `updated_at`, `version`; удаление физическое, soft delete через `deleted_at` по явному решению ТЗ

- **Описание**: shared kernel объявляет `Base` (с `NAMING_CONVENTION` boilerplate) и миксины: `IdMixin` (`id uuid PK`, default `new_id()`), `TimestampMixin` (`created_at timestamptz NOT NULL DEFAULT now()`, `updated_at timestamptz NOT NULL DEFAULT now()`, обновляется приложением), `VersionMixin` (`version integer NOT NULL DEFAULT 1`, подключён как `__mapper_args__ = {"version_id_col": version}`: SQLAlchemy добавляет `WHERE version = :old` в `UPDATE` и поднимает `StaleDataError`, который shared kernel переводит в HTTP 409 в конверте `ErrorResponseV1`), `SoftDeleteMixin` (`deleted_at timestamptz NULL`). Сущность `EntityBase = Base + IdMixin + TimestampMixin + VersionMixin`. `BaseEntityModel` из py-main-lib в моделях FLT не используется. Политика удаления: по умолчанию `DELETE`; `SoftDeleteMixin` подключается только там, где ТЗ требует восстановления или истории (пользователь при блокировке, курс при отключении ADM-02, контент CMS); для таблиц с soft delete репозиторий фильтрует `deleted_at IS NULL` по умолчанию, уникальные индексы — частичные (`WHERE deleted_at IS NULL`). Удаление персональных данных по запросу (152-ФЗ, SYS-02) выполняется физическим удалением или обезличиванием; soft delete требование 152-ФЗ не закрывает.
- **Плюсы**:
  - оптимистическая блокировка включается одной строкой и работает одинаково во всех модулях и на любом инстансе;
  - имена колонок совпадают с конвенциями REST (SYS-03: `created_at`, `updated_at`, `version` в ответах);
  - `deleted_at` хранит время удаления (нужно для сроков хранения SYS-02), `is_deleted` — нет.
- **Минусы**:
  - код boilerplate (`MyEntity`, `BaseDAO` py-main-lib, рассчитанный на `is_deleted`) переделывается на этапе 1 Г.1 и Г.4;
  - `version` обязателен в `PUT`/`PATCH` запросах клиентов — frontend передаёт его (SYS-03).
- **Масштабирование на N инстансах**: конкурентные `UPDATE` одной записи с разных инстансов: один проходит, второй получает 409 и повторяет с актуальными данными — изменения не теряются.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая.

#### Вариант B. `BaseEntityModel` py-main-lib как есть

- **Описание**: оставить `id` v4, `created_by: String NOT NULL`, `created_date`, `last_modified_*`, `is_deleted`; версию записи добавлять вручную там, где вспомнили.
- **Плюсы**:
  - совместимость с `BaseDAO` py-main-lib без правок.
- **Минусы**:
  - нет колонки версии — оптимистическая блокировка не обеспечивается по умолчанию;
  - `created_by NOT NULL` ломается на записях, созданных системой (воркер, миграция данных, анонимный быстрый тест);
  - `is_deleted` без времени удаления; имена `created_date` расходятся с конвенцией REST.
- **Масштабирование на N инстансах**: потеря конкурентных изменений там, где версию не добавили.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: нулевая сейчас; риск потерянных обновлений.

### 2.5. Миграции при N инстансах

#### Вариант A. Отдельный шаг `migrate` до запуска новых инстансов, правила expand/contract

- **Описание**: `MIGRATE_ON_START=false` на всех стендах, кроме `make dev` на local; в docker-compose — сервис `migrate` из того же образа с ролью `migrate` (ADR-004), `api` и `worker` зависят от него через `condition: service_completed_successfully`; в Helm — Job `flt-migrate` с аннотациями `helm.sh/hook: pre-install,pre-upgrade`. Миграции модуля независимы: `make migrate` выполняет `alembic -n <module> upgrade head` для каждого модуля реестра (секция `alembic.ini` и каталог ревизий на модуль — ADR-002, вариант H; веток `branch_labels` нет). Каждая миграция совместима с предыдущей версией кода, так как во время обновления старые и новые инстансы работают одновременно. Правила (проверяются на ревью миграции, SYS-05): (1) добавление колонки — только `NULL` или с `DEFAULT`; (2) переименование колонки или таблицы — запрещено одной миграцией: добавить новую → код пишет в обе → заполнить (backfill) → код читает новую → удалить старую не раньше следующего релиза; (3) удаление колонки или таблицы — только когда ни один развёрнутый релиз на неё не ссылается; (4) `NOT NULL` на существующей колонке — после backfill через `CHECK (... IS NOT NULL) NOT VALID` + `VALIDATE CONSTRAINT`; (5) индексы на непустых таблицах — `CREATE INDEX CONCURRENTLY` (`postgresql_concurrently=True` внутри `op.get_context().autocommit_block()`); (6) `lock_timeout = '5s'` и `statement_timeout = '60s'` в `env.py` на время DDL, при срабатывании миграция повторяется; (7) миграции данных объёмом свыше 10 000 строк выполняются не в Alembic, а фоновым заданием роли `worker` порциями по 1 000 строк (ADR-004); (8) один файл миграции меняет только схему своего модуля.
- **Плюсы**:
  - при обновлении нет гонки N инстансов за DDL-блокировки;
  - откат кода без отката миграции возможен благодаря совместимости;
  - миграция падает до запуска нового кода, а не на половине инстансов.
- **Минусы**:
  - переименования занимают два релиза;
  - нужен контейнер `migrate` в обоих вариантах развёртывания.
- **Масштабирование на N инстансах**: обеспечивает обновление без остановки.
- **Выделение модулей в микросервисы**: помогает — каталог миграций и таблица версий модуля уезжают вместе с ним.
- **Трудоёмкость и риски**: средняя дисциплина при написании миграций; снижается чек-листом в шаблоне ТЗ.

#### Вариант B. Миграции при старте каждого инстанса (как в boilerplate)

- **Описание**: `MIGRATE_ON_START=true`.
- **Плюсы**:
  - просто для одного инстанса.
- **Минусы**:
  - N инстансов стартуют одновременно и конкурируют за `alembic_version`; Alembic не берёт глобальную блокировку, возможен двойной запуск одной миграции;
  - сбой миграции на одном инстансе оставляет кластер в смешанном состоянии;
  - инстанс приложения получает права DDL.
- **Масштабирование на N инстансах**: не работает надёжно.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: нулевая сейчас, инциденты при обновлениях.

### 2.6. Клиент Redis, префиксы и обязательный TTL

#### Вариант A. Обёртка shared kernel `ModuleRedis` с префиксом модуля и обязательным TTL; сырой клиент закрыт

- **Описание**: redis-py asyncio (`redis>=5.2`, уже в зависимостях), один клиент на процесс, создаётся лениво в lifespan (как в boilerplate). Модуль получает `ModuleRedis(prefix="identity")` через контейнер зависимостей (ADR-004); все ключи получают префикс `identity:` автоматически. Публичные методы принимают `ttl: timedelta` обязательным аргументом без значения по умолчанию: `set`, `set_json`, `incr` (с `EXPIRE` в одном `MULTI`), `hset`, `sadd`, `zadd`, `publish` (TTL не нужен), `get`, `delete`, `eval` для Lua-скриптов shared kernel. Методов `persist` и `set` без TTL нет. Прямой импорт `redis` разрешён только пакету shared kernel (контракт import-linter, ADR-002). В pytest фикстура shared kernel после каждого теста выполняет `SCAN` и падает, если у ключа `TTL == -1` (SYS-10). Ключи: `<module>:<entity>:<id>[:<sub>]`, например `identity:session:01999d1e-...`, `assessment:quick_test:ip:203.0.113.5:count`. Максимальные TTL по назначению фиксируются в SYS-05: сессия — по ADR-006; кэш — не более 24 ч; окно лимита — не более 24 ч; блокировка — не более 60 с без продления; состояние быстрого теста — 24 ч (OQ-09).
- **Плюсы**:
  - ключ без TTL невозможно создать через публичный API shared kernel; нарушение ловят import-linter и фикстура;
  - префикс модуля гарантирован кодом, а не дисциплиной;
  - при выделении модуля его ключи выбираются по `SCAN <module>:*`.
- **Минусы**:
  - обёртка покрывает не все команды Redis: новая команда добавляется в shared kernel с обязательным TTL.
- **Масштабирование на N инстансах**: один общий Redis для всех инстансов, состояние не зависит от инстанса.
- **Выделение модулей в микросервисы**: помогает — у модуля свой префикс, а при выделении — своя база Redis или свой экземпляр без изменения кода модуля.
- **Трудоёмкость и риски**: низкая.

#### Вариант B. `RedisDAO` boilerplate и доступ к сырому клиенту

- **Описание**: оставить `RedisDAO.save(key, value, expire=3600)` и `get_redis_client()`.
- **Плюсы**:
  - ничего не менять.
- **Минусы**:
  - `get_redis_client()` даёт сырой `SET` без TTL;
  - префикс — ответственность вызывающего (`get_key(namespace, key)`), нет контроля;
  - TTL по умолчанию 3600 скрывает ошибку проектирования ключа.
- **Масштабирование на N инстансах**: как A.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: нулевая сейчас; ключи без TTL накапливаются до `maxmemory`.

### 2.7. Распределённые блокировки и лимиты

#### Вариант A. Блокировка `SET NX PX` с токеном владельца и Lua-освобождением; лимиты — скользящее окно на `ZSET` в Lua

- **Описание**: `acquire`: `SET <module>:lock:<name> <token> NX PX <ttl_ms>`, `token = secrets.token_hex(16)`; `release` — Lua `if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end`; `extend` — Lua с `PEXPIRE` при совпадении токена, вызывается фоновым heartbeat-ом для задач длиннее TTL; API: `async with locks.acquire("outbox:identity", ttl=timedelta(seconds=30), wait=timedelta(seconds=5))`, при неудаче — исключение `LockNotAcquired`. Лимит: Lua-скрипт в одном вызове `ZREMRANGEBYSCORE key 0 now-window`, `ZCARD`, при `count < limit` — `ZADD key now <uuid>`, `PEXPIRE key window`; возвращает `(allowed, remaining, retry_after_ms)`; ключ `<module>:ratelimit:<scope>:<subject>`, например `assessment:ratelimit:quick_test_ip:203.0.113.5`. Параметры лимитов — конфигурация модуля.
- **Плюсы**:
  - атомарность за счёт одной команды и Lua; владелец не может снять чужую блокировку; истёкшая блокировка снимается сама;
  - скользящее окно без всплеска на границе окна, точный `retry_after`;
  - без Redlock: Redlock требует 5 независимых мастеров Redis (противоречит составу контейнеров) и всё равно не даёт fencing-токена при паузе процесса. В FLT блокировка — средство избежать двойной работы, а не единственная гарантия корректности: критические секции дополнительно защищены инвариантами PostgreSQL (уникальные ограничения, `version`, `FOR UPDATE SKIP LOCKED` в outbox). Потеря блокировки при failover Sentinel приводит самое большее к повторному выполнению идемпотентной задачи.
- **Минусы**:
  - при failover Sentinel до репликации ключа два инстанса могут одновременно держать блокировку (смягчение выше);
  - скользящее окно хранит до `limit` элементов на ключ: для лимитов свыше 10 000 событий в окне нужен счётчик с двумя окнами — добавляется в shared kernel при появлении потребности.
- **Масштабирование на N инстансах**: блокировка и лимит общие для всех инстансов — требование CLAUDE.md «лимиты и блокировки действуют глобально».
- **Выделение модулей в микросервисы**: нейтрально — у сервиса тот же shared kernel как библиотека.
- **Трудоёмкость и риски**: низкая; скрипты Lua покрываются интеграционными тестами с реальным Redis.

#### Вариант B. Advisory locks PostgreSQL и лимиты в таблице

- **Описание**: `pg_advisory_xact_lock` для критических секций, таблица счётчиков для лимитов.
- **Плюсы**:
  - нет зависимости от Redis для корректности.
- **Минусы**:
  - advisory lock уровня сессии несовместим с будущим PgBouncer в режиме transaction;
  - лимит на IP при каждом запросе быстрого теста — запись в PostgreSQL с WAL, нагрузка на источник истины ради временных данных;
  - противоречит CLAUDE.md: лимиты и блокировки — в Redis.
- **Масштабирование на N инстансах**: работает.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая, но нарушает принятый принцип.

### 2.8. Граница PostgreSQL / MinIO

#### Вариант A. Файлы в MinIO, метаданные в PostgreSQL; `bytea` для пользовательского контента запрещён

- **Описание**: любой объект, являющийся файлом (материалы учеников, медиа CMS, демо-видео, синтезированное аудио, экспорты, изображения записей), хранится в MinIO; в PostgreSQL модуля — таблица метаданных: `id`, `bucket`, `object_key`, `size_bytes`, `content_type`, `sha256`, `owner_id`, `status` (`pending` → `uploaded`), `created_at`. Структурированный контент (словарная статья, содержимое занятия, программа обучения) — `jsonb` в PostgreSQL; ориентир размера одной `jsonb`-записи — до 1 МБ, выше — в MinIO со ссылкой из PostgreSQL. `bytea` допускается только для криптографического материала (зашифрованные API-ключи учеников, SYS-08) размером до 4 КБ. Доступ клиентов к файлам, бакеты, presigned URL, подтверждение загрузки — ADR-007.
- **Плюсы**:
  - источник истины PostgreSQL остаётся компактным, бэкапы и репликация быстрые;
  - метаданные участвуют в транзакциях и событиях outbox, байты — нет.
- **Минусы**:
  - два хранилища на одну сущность: удаление требует события «файл удалён» и уборки объекта (ADR-007).
- **Масштабирование на N инстансах**: ни один инстанс не держит файлы на диске.
- **Выделение модулей в микросервисы**: помогает — бакет модуля уезжает вместе с ним.
- **Трудоёмкость и риски**: низкая на этапе 1 (клиент MinIO нужен с этапа 2 для демо-видео).

#### Вариант B. Файлы до 10 МБ в `bytea`, крупнее — в MinIO

- **Описание**: гибрид по размеру.
- **Плюсы**:
  - одна транзакция на файл и метаданные.
- **Минусы**:
  - TOAST-хранение раздувает базу и WAL, нагрузка на бэкапы;
  - два пути кода для одной сущности, range-запросы к видео из PostgreSQL невозможны.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: средняя; рост базы.

## 3. Решение

- **Выбран**: 2.1 — A; 2.2 — A; 2.3 — A; 2.4 — A; 2.5 — A; 2.6 — A; 2.7 — A; 2.8 — A.
- **Решение**: постоянное состояние хранится в одной базе PostgreSQL `flt` со схемой на модуль (SQLAlchemy 2.0 async + asyncpg, пул на инстанс с размером по роли запуска, без PgBouncer до порога из SYS-05), первичные ключи — UUID v7, у каждой сущности `created_at`, `updated_at` и `version` для оптимистической блокировки, миграции Alembic выполняются отдельным шагом `migrate` по правилам expand/contract; временное состояние — в Redis через обёртку shared kernel с префиксом модуля и обязательным TTL, блокировки `SET NX PX` с токеном владельца, лимиты скользящим окном, pub/sub для WebSocket; файлы — в MinIO, их метаданные — в PostgreSQL.
- **Обоснование**: вариант A каждого подвопроса даёт изоляцию модулей средствами кода и DDL без умножения контейнеров и соединений, соответствует стартовой нагрузке OQ-13 и сохраняет путь выделения модуля (перенос схемы, префикса Redis и бакета без изменения кода модуля).
- **Отвергнуты**:
  - 2.1 B — кратный рост соединений и преждевременная микросервисная транзакционность; 2.1 C — 20 баз для MVP.
  - 2.2 B — несовместимость PgBouncer transaction mode с prepared statements asyncpg без текущей потребности; порог перехода зафиксирован ниже.
  - 2.3 B — фрагментация индексов и отсутствие порядка по времени; 2.3 C — ID не уникальны между базами при выделении модуля.
  - 2.4 B — нет колонки версии, `created_by NOT NULL` ломает системные записи.
  - 2.5 B — гонка N инстансов за DDL.
  - 2.6 B — сырой клиент допускает ключи без TTL и без префикса.
  - 2.7 B — advisory locks несовместимы с будущим PgBouncer и противоречат принципу «лимиты в Redis».
  - 2.8 B — рост базы и два пути кода.
- **Дополнительные правила решения** (входят в SYS-05):
  1. **Транзакции.** Одна транзакция — один модуль. Публичный API другого модуля вызывается вне транзакции вызывающего и открывает собственную сессию; сессия SQLAlchemy никогда не передаётся через границу модуля. Согласованность между модулями — через события outbox (ADR-004). Уровень изоляции — `READ COMMITTED`; `SELECT ... FOR UPDATE` допустим внутри модуля.
  2. **Серверные параметры соединения** (`connect_args={"server_settings": {...}}`): `search_path=public`, `timezone=UTC`, `application_name=flt-<role>-<instance_id>`, `statement_timeout` — 30 с для роли `api`, 10 мин для `worker`, `idle_in_transaction_session_timeout=60s`.
  3. **Время.** Все колонки времени — `timestamptz`, значения в UTC; `datetime` в коде только tz-aware; текущее время — через `Clock` shared kernel (подменяется в тестах).
  4. **Порог PgBouncer.** PgBouncer (transaction mode, `statement_cache_size=0`) добавляется в оба варианта развёртывания, когда число реплик роли `api` превышает 6 или сумма по формуле п. 2.2 A превышает `0.75 × max_connections`. До этого — не добавляется.
  5. **Кэш в памяти процесса** разрешён только для неизменяемой конфигурации, загруженной при старте (настройки, реестр модулей, скомпилированные Lua-скрипты). `functools.lru_cache` и `functools.cache` на функциях, читающих PostgreSQL или Redis, запрещены; проверяется архитектурным тестом (SDD_plan.md этап 1 Г.2).
  6. **Redis pub/sub** для WebSocket: каналы `ws:channel:<channel>` и `ws:user:<user_id>` принадлежат shared kernel, каналы запрос–ответ между инстансами (`<module>:...:inbox`, `<module>:reply:<request_id>`) — модулю-владельцу (имена и протокол — ADR-004, ADR-008); `ModuleRedis.publish` подставляет префикс модуля; для подписки используется отдельное соединение `PubSub`, не из общего пула. Сообщения pub/sub не хранятся: клиент после переподключения восстанавливает состояние из PostgreSQL через REST.
  7. **Сессии** (ADR-006): ключ `identity:session:<sid>` с TTL — кэш активности сессии (`sid` = `family_id` семейства refresh-токенов); отзывы — `identity:revoked_sid:<sid>` и `identity:revoked_user:<user_id>` с TTL, равным сроку access-токена; refresh-токены — в таблице `identity.refresh_tokens`. Проверка подписи JWT и обновление по refresh-токену от Redis не зависят.
  8. **Поведение при недоступности Redis** (таблица ниже) — обязательная часть ТЗ каждой фичи, использующей Redis. `/v1/ready` от Redis не зависит (иначе отказ Redis снимает с балансировки все инстансы сразу; роли и их readiness — ADR-004); состояние Redis отдаётся в деталях `/v1/health` и метрикой `flt_redis_up` (ADR-010).

| Назначение Redis | Поведение при недоступности | Режим |
|---|---|---|
| Кэш | промах, чтение из PostgreSQL, запись в кэш пропускается, предупреждение в лог один раз в минуту | fail-open |
| Сессии | проверка подписи JWT продолжает работать; проверка отзыва пропускается (fail-open, окно ≤ 10 минут, метрика `flt_auth_revocation_check_skipped_total` и алерт — подтверждено пользователем 2026-10-10); refresh и вход работают через PostgreSQL, лимит попыток входа не учитывается (как лимиты API ниже) — ADR-006 | частично fail-open |
| Лимиты модели платформы (быстрый тест, OQ-09) | 503 с `Retry-After: 30` — платформа не тратит токены без учёта | fail-closed |
| Лимиты запросов к API зарегистрированных пользователей | запрос пропускается, метрика `flt_ratelimit_bypassed_total` | fail-open |
| Распределённые блокировки | периодическая задача пропускает запуск; relay outbox не стартует; задания Kafka выполняются (их защищает inbox в PostgreSQL) | fail-closed |
| Pub/sub WebSocket | события с других инстансов не доставляются; соединения не рвутся; клиент получает состояние через REST при следующем действии | деградация |
| Состояние быстрого теста | тест прерывается с сообщением «попробуйте позже» | потеря допустима (CLAUDE.md) |

  9. **Redis в docker-compose**: один экземпляр `redis:8-alpine`, `--maxmemory 256mb --maxmemory-policy volatile-lru --save "" --appendonly no` (все ключи с TTL, персистентность не нужна), пароль из `.env`. **В Kubernetes**: мастер + реплика + 3 Sentinel; клиент — `redis.asyncio.Sentinel(sentinels, socket_timeout=0.5).master_for("flt")`; выбор режима — настройка `REDIS_MODE=standalone|sentinel`, `REDIS_SENTINEL_HOSTS`, `REDIS_SENTINEL_MASTER=flt`; фабрика клиента в shared kernel, код модулей от режима не зависит.
  10. **Схема `public`** не содержит таблиц; расширения (`pg_trgm`, `citext`, при необходимости) ставятся миграцией shared kernel в `public`. Архитектурный тест после `make migrate` (миграции всех модулей реестра) проверяет: таблицы только в схемах модулей, `FOREIGN KEY` между схемами отсутствуют, у каждой таблицы есть `id`, `created_at`, `updated_at`, `version` (кроме таблиц, помеченных в модели как технические: `outbox`, `processed_events`, `alembic_version`).
- **Границы решения**: раскладка пакетов и файлов миграций модуля, адаптация скаффолдера и контракты import-linter — ADR-002; бакеты, presigned URL и жизненный цикл файлов — ADR-007; формат сессии и токенов — ADR-006; outbox, inbox и роли запуска — ADR-004; производные индексы OpenSearch и Qdrant — ADR-014; разделение тестовой БД и стенда local (OQ-31) — SYS-10; политика бэкапов PostgreSQL и MinIO — SYS-11.

## 4. Последствия

### 4.1. Положительные

- Любой инстанс обрабатывает любой запрос: состояние только в PostgreSQL, Redis и MinIO, что проверяется тестами на N = 3 инстансах.
- Конкурентные изменения с разных инстансов не теряются (`version` → 409), не дублируются (уникальные ограничения, UUID v7, известный до вставки).
- Обновление без остановки: миграции идут отдельным шагом и совместимы с предыдущим релизом.
- Ключ Redis без TTL или без префикса модуля не проходит import-linter и тестовую фикстуру.
- Выделение модуля: `pg_dump --schema`, `SCAN <module>:*`, бакет модуля — без изменения кода модуля.

### 4.2. Отрицательные и их смягчение

| Последствие | Смягчение |
|---|---|
| Переименования в схеме занимают два релиза | чек-лист expand/contract в шаблоне ТЗ (раздел «Модель данных»), ревью миграций на G2 |
| Одна роль БД не мешает модулю прочитать чужую схему | архитектурные тесты (import-linter, проверка `information_schema`), ревью SQL; отдельные роли — при выделении модуля |
| Число соединений растёт линейно с N | формула в SYS-05, тест конфигурации в SYS-11, порог PgBouncer зафиксирован |
| Блокировка Redis может быть потеряна при failover Sentinel | блокировки защищают только идемпотентные операции; корректность обеспечивают инварианты PostgreSQL |
| `version` обязателен в запросах изменения — дополнительная работа frontend | генерация клиента из OpenAPI (ADR-005) включает поле автоматически; SYS-03 задаёт правило |
| Клиенты теряют события pub/sub при разрыве соединения | каждый канал WebSocket имеет REST-эндпоинт текущего состояния (ADR-004); частичный ответ LLM сохраняется в PostgreSQL модулем-владельцем с `interrupted = true`, стрим не возобновляется (ADR-009) |
| Зависимость `uuid-utils` при Python 3.13 | снимается при переходе на 3.14 (ADR-001); вызовы идут через `new_id()` |
