## 1. Контекст

- **Проблема**: платформа хранит файлы разных модулей с разной политикой доступа: публичные демо-видео и медиа CMS-страниц (VIS-01, ADM-03), приватные материалы учеников (STU-27 — «видит только загрузивший»), контент курсов преподавателей (TCH-03), изображения записей и фото профиля (STU-35), записи занятий (TCH-08, ADR-015). Нужно решить, как файлы раскладываются по бакетам, как клиент загружает и читает файлы (напрямую в MinIO через HAProxy или через монолит — OQ-18), где лежат метаданные, как файлы удаляются по требованию 152-ФЗ, как хранилище резервируется и шифруется, и что из этого делается на этапе 1.
- **Почему сейчас**: этап 1, пункты Г.4 (shared kernel) и Г.8 (MinIO входит в полный состав контейнеров). Первый потребитель — демо-видео VIS-01 на этапе 2; архитектура доступа влияет на маршруты HAProxy (ADR-012) и на модель данных каждого модуля с файлами.
- **Ограничения**:
  - CLAUDE.md «Масштабирование и состояние»: файлы не хранятся на диске инстанса, сами файлы — в MinIO, метаданные — в PostgreSQL; любой запрос может попасть на любой инстанс;
  - CLAUDE.md «Модульный монолит»: модуль владеет своими бакетами MinIO, своими таблицами и миграциями; ссылки между модулями — по идентификаторам;
  - CLAUDE.md «Маршрутизация через HAProxy»: HAProxy — единственная точка входа, TLS завершается на нём; доступ к MinIO снаружи — только решением этого ADR;
  - CLAUDE.md «Ключевые архитектурные требования»: 152-ФЗ — хранение в РФ (prod — VPS в РФ, OQ-07), удаление по запросу; персональные данные не попадают в логи;
  - boilerplate: клиентов S3 в `src/backend/py-monolyth` нет; в `src/backend/py-main-lib/py_main_lib/adapters/` есть `s3_file_uploader.py` и `s3_file_downloader.py` на `aioboto3`, но библиотека ставится в монолит с `--no-deps` (`Dockerfile`), поэтому `aioboto3` в окружении монолита отсутствует;
  - лимиты нагрузки SYS-02 (OQ-13): 100 одновременных пользователей, 10 000 зарегистрированных за первый год — объём файлов на старте измеряется десятками гигабайт, не терабайтами.
- **Если не решить**: модули этапа 2 (cms) и этапа 5 (materials) реализуют загрузку по-разному; байты файлов пойдут через инстансы монолита и ограничат горизонтальное масштабирование; без единого жизненного цикла файлов появятся «осиротевшие» объекты и невозможность доказуемого удаления по 152-ФЗ.
- **Ссылки**: CLAUDE.md «Маршрутизация через HAProxy», «Состав контейнеров», «Масштабирование и состояние»; SDD_plan.md этап 1 А.7, этап 2 (VIS-01), этап 5 (STU-27), этап 6 (TCH-03, TCH-08), этап 7 (STU-35); OQ-18.

## 2. Рассматриваемые варианты

Все варианты используют S3-совместимый API хранилища из кода монолита (клиент — библиотека `aioboto3`, см. раздел 3) и хранят метаданные файлов в PostgreSQL в схеме модуля-владельца. Различаются путь байтов файла и схема прав доступа.

### Вариант A. Всё напрямую: presigned URL и для загрузки, и для чтения любых файлов

- **Описание**: HAProxy публикует MinIO по путям бакетов `/flt-*` (path-style S3, без переписывания пути). Монолит никогда не передаёт байты файлов: на загрузку выдаёт presigned POST (одна часть) или presigned PUT частей multipart-загрузки, на чтение — presigned GET с TTL 15 минут, в том числе для публичных демо-видео и медиа CMS. Все бакеты приватные.
- **Плюсы**:
  - инстансы монолита не нагружены передачей файлов, пропускная способность ограничена только MinIO;
  - range-запросы для видео (`<video>` с перемоткой) обслуживает MinIO без доработок;
  - один механизм для всех файлов.
- **Минусы**:
  - публичные медиа получают нестабильные URL с истекающей подписью: не кэшируются браузером и CDN дольше TTL, нельзя вставить постоянную ссылку на демо-видео в CMS-контент и в письма;
  - на каждый просмотр стартовой страницы монолит выдаёт подписанные ссылки на медиа (операция локальная, без сети, но добавляет вызовы в рендер страницы).
- **Масштабирование на N инстансах**: выдача presigned URL — чистое вычисление с общими ключами доступа, состояния в процессе нет; подтверждение загрузки — изменение строки в PostgreSQL с проверкой статуса; Redis не используется. Остановка инстанса не прерывает загрузку: байты идут в MinIO, подтверждение примет другой инстанс.
- **Выделение модулей в микросервисы**: нейтрально — модуль уносит с собой бакет, таблицу и выдачу ссылок; маршрут HAProxy не меняется.
- **Трудоёмкость и риски**: низкая; риск — утечка подписанной ссылки действует до истечения TTL.

### Вариант B. Все байты через монолит

- **Описание**: MinIO наружу не публикуется. Загрузка — `multipart/form-data` в REST монолита, который пишет объект в MinIO; чтение — эндпоинт монолита с проверкой прав на каждый запрос, который стримит объект из MinIO клиенту с поддержкой `Range`.
- **Плюсы**:
  - права проверяются на каждый запрос, отозванный доступ действует мгновенно;
  - MinIO полностью закрыт снаружи, HAProxy не содержит правил для хранилища;
  - проверка типа и размера файла выполняется до записи в хранилище.
- **Минусы**:
  - каждый байт проходит через процесс Python (uvicorn): видео 2 ГБ и учебники 200 МБ занимают воркеры и память инстансов, задержка REST растёт (p95 ≤ 300 мс по SYS-02 под угрозой);
  - вертикальный предел — пропускная способность инстансов, а не хранилища; масштабирование файловой нагрузки требует масштабировать весь монолит;
  - корректная поддержка `Range`, `If-None-Match`, `Content-Disposition` и возобновляемых загрузок пишется и тестируется самостоятельно;
  - HAProxy и uvicorn требуют настройки таймаутов и лимитов тела запроса под крупные файлы.
- **Масштабирование на N инстансах**: состояния в процессе нет, но длительная загрузка привязана к одному инстансу: его остановка прерывает передачу, клиент начинает заново.
- **Выделение модулей в микросервисы**: нейтрально; при выделении модуль уносит свой стриминговый эндпоинт.
- **Трудоёмкость и риски**: средняя; риск — деградация задержек REST под файловой нагрузкой.

### Вариант C. Гибрид: публичные файлы по постоянным URL, приватные — presigned GET, загрузка — presigned напрямую

- **Описание**: как вариант A, но публичные объекты (демо-видео, медиа опубликованных CMS-страниц) лежат в префиксе `public/` бакета `flt-cms` с политикой анонимного чтения и доступны по постоянным URL `https://<domain>/flt-cms/public/<key>`. Приватные файлы (материалы, контент курсов, изображения записей, фото профиля, записи занятий) читаются по presigned GET с TTL 15 минут, который выдаёт модуль-владелец после проверки прав. Загрузка всех файлов — presigned POST (одна часть, до 64 МиБ) или multipart с presigned PUT частей, затем подтверждение в монолите. Байты через монолит не проходят; фоновые задания модулей читают объекты из MinIO напрямую (sha256, извлечение текста, перекодирование изображений).
- **Плюсы**:
  - все плюсы варианта A;
  - публичные медиа кэшируются (`Cache-Control: public, max-age=31536000, immutable`, ключ объекта неизменяем) и имеют постоянные ссылки для CMS-контента;
  - приватность материалов (STU-27) обеспечивается коротким TTL и проверкой прав при выдаче ссылки.
- **Минусы**:
  - две схемы доступа (политика бакета и presigned GET) — обе описываются в shared kernel одной функцией `public_url` / `presign_download`;
  - MinIO доступен снаружи по путям `/flt-*`: нужны ACL HAProxy (методы, запрет листинга) и тест, что они действуют.
- **Масштабирование на N инстансах**: как у варианта A.
- **Выделение модулей в микросервисы**: нейтрально; политика анонимного чтения принадлежит бакету `flt-cms`, то есть модулю `cms`.
- **Трудоёмкость и риски**: низкая; риски — те же, что у A, плюс ошибка в политике бакета может открыть приватный префикс; смягчается автотестом «анонимный GET к `flt-materials` возвращает 403».

## 3. Решение

- **Выбран**: Вариант C.
- **Решение**: файлы хранятся в S3-совместимом хранилище (MinIO) в бакете модуля-владельца `flt-<module>`, метаданные — в таблице этого модуля в PostgreSQL. Клиент загружает файлы напрямую в хранилище по presigned POST или multipart presigned PUT через HAProxy по пути бакета `/flt-<module>/…` (path-style, без переписывания пути и без отдельного имени хоста) и подтверждает загрузку в монолите; публичные медиа читаются по постоянным URL из префикса `public/` бакета `flt-cms`, приватные — по presigned GET с TTL 15 минут, выданному модулем после проверки прав. Байты файлов через инстансы монолита не передаются. Сервер хранилища на этапе 1 — последний опубликованный образ MinIO с зафиксированным тегом; выбор продукта для prod — OQ-64 до развёртывания VPS (этап 2); код завязан только на S3 API (подтверждено пользователем 2026-10-10).
- **Обоснование**: вариант C сохраняет горизонтальное масштабирование монолита (CLAUDE.md «Масштабирование и состояние») и даёт постоянные кэшируемые ссылки на публичные медиа, чего нет у варианта A; вариант B нарушает бюджет задержек SYS-02 под файловой нагрузкой и усложняет код стриминга. Рекомендация Claude в OQ-18 (вариант 3 там) совпадает с этим решением; уточнение: отдача приватных файлов через монолит не используется совсем — presigned GET с TTL 15 минут достаточен для приватности материалов, а право доступа проверяется при каждой выдаче ссылки.
- **Отвергнуты**:
  - Вариант A — публичные медиа без постоянных URL и кэширования.
  - Вариант B — байты через инстансы монолита ограничивают масштабирование и задержки REST.
- **Границы решения**: ADR не определяет форматы и лимиты файлов конкретных модулей (это их ТЗ: STU-27, ADM-03, STU-35.2), не решает хранение записей голоса и видео по 152-ФЗ (OQ-35; здесь — только механизм хранения и удаления), не выбирает CDN (на старте не нужен). Выбор сервера хранилища для prod (см. 3.10) — OQ-64; правило выбора Helm chart-ов для инфраструктуры задаёт SYS-11 (OQ-28).

Частные решения, входящие в это ADR:

### 3.1. Клиент хранилища в shared kernel; адаптеры py-main-lib не переиспользуются

Рассмотрено: (а) переиспользовать `py_main_lib.adapters.s3_file_uploader.S3FileUploader` и `s3_file_downloader.S3FileDownloader`; (б) написать собственный пакет `app/core/storage` на `aioboto3`.

Выбрано (б). Причины по результатам изучения кода: `S3FileUploader` рассчитан на временные файлы RAG-индексатора (жёстко зашитый префикс `temp-files/rag-indexer/`, автосоздание бакета при каждом инстанцировании, нет presigned URL, нет multipart, нет `head_object`); `S3FileDownloader` смешивает прямой доступ к S3 с HTTP-вызовами чужого файлового сервиса (`/v1/files/download_link`, заголовок `X-Service-Name: aitunnel-adapter`), извлечением текста через `PyPDF2` и `python-docx` и русскоязычными сообщениями исключений общего типа `Exception`; оба модуля логируют через `colored_logger`, а не через structlog монолита, и не типизированы под mypy strict. Из них заимствуются приёмы: повтор с экспоненциальной задержкой при `ClientError`, `EndpointConnectionError`, `BotoCoreError` (3 попытки, 1 с → 2 с → 4 с) и транслитерация имени файла `sanitize_filename` для заголовка `Content-Disposition`. Библиотека `aioboto3` добавляется в `pyproject.toml` монолита явно (`aioboto3>=15,<16`); py-main-lib не трогается.

Публичный API пакета `app/core/storage` (имена окончательные, сигнатуры уточняет спецификация shared kernel):

```python
class FileStorage(Protocol):
    """Клиент S3-совместимого хранилища; один экземпляр на процесс, создаётся в lifespan."""

    async def create_upload(self, bucket: str, key: str, *, content_type: str,
                            max_bytes: int, expires_in: int = 900) -> PresignedPost: ...
    async def create_multipart_upload(self, bucket: str, key: str, *, content_type: str,
                                      total_bytes: int, part_bytes: int = 16 * 2**20,
                                      expires_in: int = 3600) -> MultipartUpload: ...   # upload_id, список presigned PUT частей
    async def complete_multipart_upload(self, bucket: str, key: str, upload_id: str,
                                        parts: list[UploadedPart]) -> None: ...
    async def abort_multipart_upload(self, bucket: str, key: str, upload_id: str) -> None: ...
    async def head(self, bucket: str, key: str) -> ObjectInfo | None: ...               # size, content_type, etag
    def presign_download(self, bucket: str, key: str, *, expires_in: int = 900,
                         filename: str | None = None, inline: bool = False) -> str: ...  # без сети
    def public_url(self, bucket: str, key: str) -> str: ...                             # для префикса public/
    async def open_stream(self, bucket: str, key: str) -> AsyncIterator[bytes]: ...     # только для фоновых заданий
    async def delete(self, bucket: str, key: str) -> None: ...
```

Правила: модули вызывают только `FileStorage`; `aioboto3` импортируется только внутри `app/core/storage` (контракт import-linter ADR-002 запрещает импорт `aioboto3` и `botocore` из модулей). `presign_download`, `public_url` и `create_upload` строят URL с публичным адресом `S3_PUBLIC_BASE_URL` (prod — `https://<домен>`, dev — `http://flt.localhost`, без пути): клиент `aioboto3` для подписи создаётся с `endpoint_url = S3_PUBLIC_BASE_URL` и `addressing_style = "path"`, поэтому подпись SigV4 вычисляется для хоста и пути `/<bucket>/<key>` — ровно того запроса, который MinIO получит через HAProxy без переписывания пути и `Host` (см. 3.5). Для операций самого монолита (HEAD, multipart complete, delete, `open_stream`) используется второй клиент с внутренним `S3_ENDPOINT_URL`.

### 3.2. Бакет на модуль: `flt-<module>`

Рассмотрено: (а) один бакет `flt` с префиксами `<module>/`; (б) бакет на модуль `flt-<module>`.

Выбрано (б): соответствует правилу CLAUDE.md «модуль владеет своими бакетами», политики доступа, lifecycle-правила, квоты и резервное копирование настраиваются на бакет, при выделении модуля в микросервис бакет переносится как есть. Имена бакетов: `flt-cms`, `flt-materials`, `flt-social`, `flt-classroom`, `flt-local-runtime` (дистрибутивы локального агента, ADR-008); бакет фото профиля — у модуля-владельца по SYS-01. Имя бакета — имя модуля, в котором `_` заменён на `-` (ограничение имён бакетов S3: строчные буквы, цифры и дефис). Префикс `flt-` постоянен (OQ-08: в коде всегда `flt`). Схема ключей внутри бакета:

| Назначение | Ключ | Пример |
|---|---|---|
| Файл пользователя | `u/<owner_user_id>/<file_id>.<ext>` | `u/0192f2a0-…/0192f3b1-….pdf` |
| Публичное медиа CMS | `public/<file_id>.<ext>` | `public/0192f4c2-….mp4` |
| Черновик медиа CMS | `drafts/<file_id>.<ext>` | `drafts/0192f4c2-….mp4` |
| Запись занятия (ADR-015) | `recordings/<lesson_id>/<file_id>.mp4` | `recordings/0192f5d3-…/0192f5e4-….mp4` |
| Временные объекты заданий | `tmp/<job_id>/<name>` | `tmp/0192f6f5-…/page-001.txt` |

`<file_id>` — UUID v7 из shared kernel; расширение берётся из белого списка типа, а не из имени файла пользователя. Имя файла пользователя в ключ не попадает (152-ФЗ и инъекции в заголовки), оно хранится в колонке `original_filename` и подставляется в `Content-Disposition` после транслитерации. Префикс `u/<owner_user_id>/` даёт перечисление всех объектов пользователя для удаления по запросу.

### 3.3. Метаданные в PostgreSQL в схеме модуля-владельца

Shared kernel даёт миксин SQLAlchemy `StoredFileMixin` и Pydantic-схему `StoredFile`; каждый модуль создаёт свою таблицу (`materials.files`, `cms.media_files`, `social.post_images`, `classroom.recordings`) своей миграцией Alembic и добавляет свои колонки. Обязательные колонки миксина:

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | uuid, PK | идентификатор файла, совпадает с `<file_id>` в ключе |
| `bucket` | text | бакет |
| `key` | text, unique вместе с `bucket` | ключ объекта |
| `size` | bigint, nullable | размер; заполняется при подтверждении из `HEAD` |
| `content_type` | text | заявленный тип; после обработки — определённый по содержимому |
| `sha256` | char(64), nullable | вычисляется фоновым заданием при обработке |
| `owner_user_id` | uuid, nullable | владелец; `NULL` у публичных медиа CMS (владелец — платформа, автор пишется в журнал аудита) |
| `original_filename` | text, nullable | имя файла у пользователя |
| `status` | enum `file_status` | `pending` → `uploaded` → `processing` → `ready` → `deleted` |
| `multipart_upload_id` | text, nullable | идентификатор незавершённой multipart-загрузки |
| `created_at`, `updated_at`, `deleted_at` | timestamptz | время создания, изменения, пометки на удаление |

Статусы: `pending` — ссылка на загрузку выдана, объект ещё не подтверждён (добавлен к перечню из постановки задачи, иначе невозможно отличить осиротевшие ссылки); `uploaded` — подтверждён, `HEAD` успешен; `processing` — выполняется фоновое задание; `ready` — доступен пользователям; `deleted` — помечен на удаление, объект удаляется или удалён. Внешних ключей на таблицы других модулей нет (`owner_user_id` — ссылка по идентификатору на `identity`).

### 3.4. Поток загрузки

1. `POST /api/v1/<module>/<resource>` (например `/api/v1/materials/files`) с телом `{original_filename, content_type, size, sha256?}`. Модуль проверяет право, белый список типов и лимит размера своего ТЗ, квоту пользователя (колонка квоты — в модуле), создаёт строку в статусе `pending` и возвращает `{file_id, expires_at, upload}`: при `size ≤ S3_SINGLE_UPLOAD_MAX_BYTES` (64 МиБ) `upload = {kind: "post", url, fields}` — presigned POST с условиями `content-length-range` и точным `Content-Type`; иначе `upload = {kind: "multipart", upload_id, part_bytes, parts: [{number, url}]}` — presigned PUT частей (16 МиБ, не более 10 000 частей).
2. Браузер отправляет байты напрямую на `https://<domain>/<bucket>` (POST) или `https://<domain>/<bucket>/<key>?partNumber=…` (PUT), где `<bucket>` = `flt-<module>`. Origin запроса совпадает с origin приложения — CORS не нужен (аргумент в пользу того же хоста, 3.5). Vite в dev-режиме проксирует пути `/flt-*` так же, как `/api` и `/ws` (ADR-005).
3. `POST /api/v1/<module>/<resource>/{file_id}/confirm` (для multipart — с перечнем `parts: [{number, etag}]`). Монолит выполняет `UPDATE … SET status='uploaded' WHERE id=:id AND status='pending'` (идемпотентно: повторное подтверждение возвращает текущее состояние), для multipart вызывает `complete_multipart_upload`, затем `HEAD`: объект существует, `size` не превышает лимит, `content_type` совпадает. При нарушении — объект удаляется, строка переводится в `deleted`, ответ — ошибка `FILE_UPLOAD_INVALID` в конверте `ErrorResponseV1`. При успехе через outbox публикуется фоновое задание обработки файла модуля (ADR-004; имя топика — по SYS-04).
4. Воркер модуля читает объект через `open_stream`: определяет тип по содержимому (библиотека `filetype`; `text/html` и `image/svg+xml` отклоняются всегда), считает `sha256`, выполняет обработку модуля (изображения — перекодирование через Pillow с удалением EXIF; материалы — извлечение текста для ADR-014), переводит строку в `ready` и публикует событие `<module>.file_ready`. Дубликаты по `sha256` внутри одного владельца модуль вправе схлопывать.
5. Осиротевшие загрузки: периодическое задание роли `worker` под распределённой блокировкой `shared_kernel:lock:files-gc` раз в 15 минут переводит строки `pending` старше 24 часов в `deleted`, прерывает их multipart-загрузки (`abort_multipart_upload`) и удаляет объекты, если они появились. Lifecycle-правила бакетов — страховка: `AbortIncompleteMultipartUpload` через 1 день, истечение префикса `tmp/` через 1 день.

### 3.5. Публикация хранилища: пути бакетов `/flt-*` на том же хосте без переписывания

Рассмотрено: (а) отдельное имя хоста `s3.<domain>` или `files.<domain>` (отдельная запись DNS и SAN в сертификате — домен не выбран, OQ-08; загрузка из браузера становится cross-origin и требует CORS на MinIO); (б) префикс `/s3/` на хосте приложения с удалением префикса в HAProxy; (в) path-style адресация на хосте приложения: все бакеты называются `flt-<module>`, поэтому ACL `path_beg /flt-` однозначно отделяет запросы к хранилищу от `/api/*`, `/ws/*` и путей фронтенда, путь и `Host` не меняются.

Выбрано (в) — решение оркестратора 2026-10-10. Отвергнуты: (б) — снятие префикса меняет канонический путь запроса, который входит в подпись SigV4, и ломает presigned URL (подписывать «путь без префикса» и вставлять префикс после — хрупкий обходной приём); (а) — требует DNS-записи и сертификата с дополнительным SAN до выбора домена и делает загрузку cross-origin с CORS. Фрагмент конфигурации HAProxy (окончательная — ADR-012, `deploy/config/haproxy/haproxy.cfg`):

```
frontend fe_https
    acl is_s3            path_beg /flt-
    acl s3_method_ok     method GET HEAD PUT POST
    acl s3_bucket_level  path_reg ^/flt-[a-z0-9-]+/?$
    http-request deny deny_status 405 if is_s3 !s3_method_ok
    http-request deny deny_status 403 if is_s3 s3_bucket_level !METH_POST
    use_backend be_minio if is_s3

backend be_minio
    http-response set-header X-Content-Type-Options nosniff
    http-response set-header Content-Security-Policy "default-src 'none'; sandbox"
    timeout server 600s
    timeout client 600s
    server minio1 "${MINIO_HOST}":9000 check
```

Правила: путь и заголовок `Host` не переписываются — подпись SigV4 проверяется MinIO по тому же хосту и пути, для которых монолит её вычислил (`S3_PUBLIC_BASE_URL`, 3.1); `POST` на уровне бакета разрешён только потому, что presigned POST адресуется бакету; `GET`/`HEAD`/`PUT` на уровне бакета (листинг, `?uploads`, `?policy`, создание бакета) запрещены; admin API и health MinIO (`/minio/admin/*`, `/minio/health/*`) снаружи недостижимы — пути не начинаются с `/flt-` и уходят на Nginx, который отвечает SPA-страницей или 404; фронтенд не использует маршруты, начинающиеся с `/flt-` (правило для `src/app/routes`, ADR-005). Ограничение частоты запросов к `/flt-*` — общее правило ADR-012. Тест на стенде из N инстансов: ссылка на загрузку выдана инстансом 1, байты ушли через HAProxy, подтверждение принял инстанс 2, presigned GET от инстанса 3 открывается через HAProxy; анонимный `GET /flt-materials/u/…` возвращает 403; `GET /flt-materials/` — 403; `GET /minio/health/live` снаружи не достигает MinIO.

### 3.6. Политики доступа и учётная запись монолита

- Монолит работает от выделенной учётной записи хранилища `flt-backend` с политикой «все действия S3 над `arn:aws:s3:::flt-*` и `arn:aws:s3:::flt-*/*`», без прав администратора. Ключи — `S3_ACCESS_KEY`, `S3_SECRET_KEY` из `.env` (docker-compose) или Vault (ADR-013). Корневые учётные данные MinIO (`MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`) использует только контейнер инициализации развёртывания.
- Политика анонимного чтения: только `s3:GetObject` на `arn:aws:s3:::flt-cms/public/*`. Остальные бакеты и префиксы без анонимного доступа.
- Инициализация делится на два шага: (1) уровень развёртывания — одноразовый контейнер `minio-init` на образе `mc` создаёт учётную запись `flt-backend` и её политику (специфично для MinIO, лежит в `deploy/`); (2) уровень приложения — команда `python -m cli storage-init` (идемпотентна: создаёт бакеты `flt-*`, применяет политику анонимного чтения, lifecycle-правила и `Cache-Control` по умолчанию через стандартный S3 API) выполняется в той же роли и в том же шаге, что миграции Alembic (ADR-004: сервис `migrate` в docker-compose, Job в Helm), до запуска инстансов. Инстансы бакеты не создают (в отличие от `S3FileUploader` boilerplate).

### 3.7. Безопасность содержимого; антивирус

- Белые списки типов — в ТЗ модулей; shared kernel запрещает всегда: `text/html`, `application/xhtml+xml`, `image/svg+xml`, `application/x-msdownload`, `application/x-sh`. Тип определяется по содержимому в фоновом задании; расхождение с заявленным — `FILE_TYPE_MISMATCH`, статус `deleted`.
- Для всего, что не изображение, видео, аудио или PDF, presigned GET выдаётся с `Content-Disposition: attachment`; HAProxy добавляет `X-Content-Type-Options: nosniff` и запрещающий CSP.
- Изображения (записи, фото профиля) всегда перекодируются (Pillow) — исходный файл заменяется, EXIF удаляется.
- Антивирусная проверка на этапах 1–5 **не выполняется**: материалы ученика видит только он сам, медиа CMS загружает администратор платформы, изображения перекодируются. В шаге `processing` предусмотрен хук `scanner` (интерфейс в shared kernel, реализация-заглушка `NoopScanner`). Потребность появляется на этапе 6, когда преподаватель раздаёт файлы ученикам (TCH-03): ClamAV в отдельном контейнере стоит 1–2 ГБ ОЗУ на VPS — решение выносится в новый открытый вопрос (см. отчёт оркестратору), ТЗ TCH-03 не утверждается без него.

### 3.8. Удаление, 152-ФЗ, версионирование, резервное копирование

- Удаление пользователем: строка → `deleted`, `deleted_at = now()`; объект физически удаляется периодическим заданием через 7 суток (окно отмены ошибочного удаления), строка после удаления объекта хранится ещё 30 суток для аудита и затем удаляется.
- Удаление по запросу субъекта персональных данных и удаление аккаунта: событие `identity.user_deleted` (имя по SYS-04) → каждый модуль с файлами удаляет все объекты `u/<owner_user_id>/*` и строки немедленно (без окна 7 суток), срок исполнения — по SYS-02. Остаточные копии — только в резервных копиях со сроком хранения 30 суток; это фиксируется в SYS-02 и в тексте согласия.
- Версионирование бакетов **выключено**: при включённом версионировании удаление по 152-ФЗ требует удаления всех версий, а защиту от ошибок даёт окно 7 суток и резервные копии.
- Резервное копирование: ночная синхронизация всех бакетов `flt-*` инструментом `rclone sync` (не зависит от сервера хранилища) во второе хранилище на территории РФ (отдельный диск VPS или S3-сервис российского облака — выбор при настройке VPS, SYS-11) с хранением 30 суток; дамп PostgreSQL делается в том же окне, чтобы метаданные и объекты были согласованы; восстановление проверяется раз в квартал. Детали расписания и места — SYS-11.

### 3.9. Шифрование и режим работы в Kubernetes

- Шифрование at-rest: серверное шифрование SSE-S3 с автоматическим применением ко всем объектам (`MINIO_KMS_SECRET_KEY=flt-sse:<base64 32 байта>`, `MINIO_KMS_AUTO_ENCRYPTION=on`); ключ — секрет из `.env` или Vault (ADR-013), ротация — отдельной процедурой SYS-11. Шифрование диска VPS — обязанность оператора (SYS-11). Данные между HAProxy и MinIO и между монолитом и MinIO ходят по внутренней сети контейнеров без TLS; TLS наружу завершает HAProxy (ADR-012).
- Kubernetes (проверяется только в kind, OQ-07): MinIO в режиме **standalone** — собственный шаблон StatefulSet с одним PVC в `deploy/helm/flt/templates/minio/` (паритет с одним контейнером в docker-compose; это обоснованное исключение из общего подхода «публичные chart-ы для инфраструктуры»: chart Bitnami перешёл на платные образы, оператор MinIO избыточен, а сам сервер хранилища может смениться по OQ-64). Итоговое правило выбора chart-ов для инфраструктуры задаёт SYS-11 (OQ-28). Distributed-режим (erasure coding, не менее 4 дисков) — отдельным ADR при переходе на продуктивный Kubernetes.

### 3.10. Сервер хранилища и контракт S3

Код монолита использует только стандартный S3 API: presigned POST/PUT/GET, multipart, `HeadObject`, `PutBucketPolicy`, `PutBucketLifecycleConfiguration`. Специфичны для MinIO только переменные контейнера (`MINIO_*`) и шаг `minio-init` (`mc admin user add`). Это сделано намеренно: по состоянию на 2026-10-10 community-редакция MinIO распространяется только в исходном коде (с октября 2025 года образы и бинарные сборки не публикуются, последний опубликованный образ — `minio/minio:RELEASE.2025-10-15T17-29-55Z`, репозиторий переведён в режим сопровождения). CLAUDE.md фиксирует MinIO в составе контейнеров. Решение пользователя 2026-10-10: на этапе 1 в docker-compose и Helm используется последний опубликованный образ MinIO с зафиксированным тегом (`minio/minio:RELEASE.2025-10-15T17-29-55Z`); выбор продукта для prod (MinIO из исходников, Garage, SeaweedFS, RustFS или иной S3-совместимый сервер) — отдельный вопрос OQ-64, решается до развёртывания VPS (этап 2); все тесты хранилища пишутся против S3 API, чтобы замена сервера свелась к правке `deploy/`. Из политики «последняя стабильная линия образа» (ADR-001) MinIO исключён до решения OQ-64.

### 3.11. Конфигурация монолита (секция `storage` настроек shared kernel)

| Переменная | Назначение | Значение на стенде local |
|---|---|---|
| `S3_ENDPOINT_URL` | внутренний адрес хранилища для монолита | `http://minio:9000` (из контейнера), `http://localhost:9000` (с хоста) |
| `S3_PUBLIC_BASE_URL` | адрес, который видит браузер (origin приложения без пути; совпадает с `APP_PUBLIC_URL`) | `http://flt.localhost` |

| `S3_PRESIGN_TTL_SECONDS` | TTL presigned GET | `900` |
| `S3_UPLOAD_TTL_SECONDS` | TTL presigned POST и PUT частей | `900` (POST), `3600` (multipart) |

### 3.12. Наблюдаемость

Метрики монолита: `flt_files_upload_initiated_total{module}`, `flt_files_upload_confirmed_total{module,result}`, `flt_files_processing_duration_seconds{module}`, `flt_files_gc_deleted_total{module,reason}`; Prometheus собирает метрики MinIO. В логах — `file_id`, `bucket`, `module`, `size`; никогда — `original_filename`, presigned URL и ключи доступа.

### 3.13. Что делается на этапе 1

Только shared kernel и инфраструктура: пакет `app/core/storage` с тестами (unit — состав presigned URL с `S3_PUBLIC_BASE_URL` и path-style адресацией, интеграционные — против контейнера MinIO: POST, multipart, `HEAD`, presigned GET, политика анонимного чтения), миксин и enum статусов, `cli storage-init` (выполняется ролью `migrate`, ADR-004), контейнер MinIO и `minio-init` в docker-compose и Helm, маршрут `/flt-*` в HAProxy, тест маршрута на стенде из N инстансов (3.5). Ни один доменный модуль на этапе 1 файлы не использует; первый потребитель — `cms` (VIS-01, этап 2).

## 4. Последствия

### 4.1. Положительные

- Инстансы монолита не передают байты файлов; файловая нагрузка масштабируется хранилищем и HAProxy, а не Python-процессами.
- Единый жизненный цикл файла (`pending` → `ready` → `deleted`) и единый клиент в shared kernel: каждый модуль добавляет только свои лимиты, типы и обработку.
- Приватность материалов (STU-27): объекты недоступны без ссылки, ссылка живёт 15 минут и выдаётся только после проверки прав; имена файлов пользователя не попадают в ключи и логи.
- Удаление по 152-ФЗ доказуемо: все объекты пользователя лежат под `u/<owner_user_id>/`, версионирование выключено, срок жизни резервных копий известен.
- Загрузка из браузера без CORS, пути `/flt-*` работают одинаково на dev, тестовом стенде и prod (один сертификат, один домен, подпись не зависит от прокси).
- Код не зависит от MinIO: замена сервера хранилища ограничивается `deploy/`.

### 4.2. Отрицательные и их смягчение

| Последствие | Смягчение |
|---|---|
| MinIO доступен снаружи по `/flt-*` | ACL HAProxy на методы и уровень бакета; admin API недостижим (пути вне `/flt-`); бакеты приватные, кроме префикса `public/` бакета `flt-cms`; автотесты 403 на анонимный доступ и листинг |
| Утёкшая presigned-ссылка действует до 15 минут | TTL 15 минут; ссылка привязана к методу и объекту; для скачивания — `attachment`; при необходимости модуль уменьшает TTL |
| Пространство путей `/flt-*` зарезервировано за хранилищем на хосте приложения | имена бакетов фиксированы (`flt-<module>`), фронтенд не создаёт маршруты с таким префиксом (ADR-005); единственная функция сборки публичного URL в shared kernel; интеграционный тест через HAProxy на стенде из N инстансов; правило ADR-012: путь и `Host` не переписываются |
| Нет антивируса | только приватные или перекодированные файлы до этапа 6; хук `scanner`; открытый вопрос к TCH-03 |
| Community-редакция MinIO без обновлений безопасности | зафиксированный тег последнего образа на этапе 1 (решение пользователя 2026-10-10), порт 9000 закрыт снаружи, admin API недостижим через HAProxy; выбор сервера для prod — OQ-64 до этапа 2; код только на S3 API |
| Осиротевшие объекты при сбое между загрузкой и подтверждением | статус `pending` со сроком 24 часа, периодическое задание очистки, lifecycle-правила как страховка |
| Два шага инициализации (`minio-init` и `storage-init`) | оба идемпотентны и выполняются в шаге миграций до старта инстансов; smoke-тест развёртывания проверяет наличие бакетов |
| Бэкапы содержат удалённые данные до 30 суток | срок зафиксирован в SYS-02 и в согласии на обработку персональных данных |

### 4.3. Что нужно сделать
