## 1. Контекст

- **Проблема**: ученик подключает к платформе модели, работающие на его компьютере (LM Studio — STU-05, llama.cpp — STU-02), а платформа подбирает модель под его железо (STU-04). Браузер не может запускать процессы, скачивать гигабайтные модели и читать характеристики видеокарты, поэтому нужно отдельное приложение на компьютере ученика — локальный агент (глоссарий, раздел 5). Нужно решить: язык и сборку агента, установку и обновление, сопряжение и аутентификацию, протокол связи, как инстансы монолита без состояния находят агент ученика, что агенту разрешено делать на машине ученика и что из этого делается на каком этапе.
- **Почему сейчас**: этап 1 А.8 — решение влияет на архитектуру LLM-шлюза (SYS-08: провайдер `local`), на маршруты HAProxy (ADR-012: `/ws/agent`) и на пространство типов сообщений WebSocket (SYS-04). Реализация — этап 4 (STU-05) и этап 5 (STU-02, STU-04).
- **Ограничения**:
  - решения пользователя от 2026-10-10: агент пишется на Python и собирается в исполняемый файл (PyInstaller или Nuitka — выбрать здесь); связь с платформой — исходящий WebSocket через HAProxy; Kafka наружу не публикуется; аутентификация агента — Bearer-токен (ADR-006); формат WebSocket-сообщений и доставка между инстансами — ADR-004; стриминг LLM через агента — ADR-009;
  - CLAUDE.md «Масштабирование и состояние»: агент подключён к одному инстансу, но запрос ученика может прийти на любой; состояние — только в Redis и PostgreSQL; sticky-сессий нет;
  - CLAUDE.md «Ключевые архитектурные требования»: LLM-агностичность — любая функция работает с локальной моделью так же, как с внешней; персональные данные и ключи не попадают в логи;
  - CLAUDE.md «Структура репозитория»: `src/agent/` зарезервирован за агентом; все исходники — только в `src/`;
  - агент не может зависеть от `py-main-lib` и кода монолита: он распространяется на компьютеры учеников, его зависимости должны быть минимальны и свободно лицензированы;
  - у пользователей нет прав администратора на компьютере по умолчанию; антивирусы и SmartScreen относятся к неподписанным исполняемым файлам настороженно.
- **Если не решить**: `llm_gateway` этапа 1 будет спроектирован без канала к локальным моделям, и на этапе 4 его придётся переделывать; `local_runtime` появится без схемы маршрутизации на N инстансах и сломает тесты масштабируемости.
- **Ссылки**: CLAUDE.md «Технологический стек» (локальный агент), «Взаимодействие», «Масштабирование и состояние»; SDD_plan.md этап 1 А.8, этап 4 п. 6 (STU-05), этап 5 п. 2–4 (STU-02, STU-04, STU-03); OQ-19; глоссарий «Локальный агент», «Локальный движок», «Локальный runtime (модуль)», «Характеристики железа».

## 2. Рассматриваемые варианты

Язык (Python) и транспорт (исходящий WebSocket через HAProxy) заданы пользователем, поэтому варианты рассматриваются по четырём открытым осям. В каждой оси выбранный вариант помечен в разделе 3.

### 2.1. Сборка в исполняемый файл

#### Вариант A. PyInstaller, режим onedir

- **Описание**: PyInstaller 6.x собирает каталог с интерпретатором Python 3.14 (ADR-001), зависимостями и кодом агента (`onedir`); каталог упаковывается в установщик (Windows — Inno Setup, macOS — `.dmg` с `.app`, Linux — `tar.gz`). Сборка в GitHub Actions на матрице `windows-latest` (x64), `macos-14` (arm64), `macos-13` (x64), `ubuntu-22.04` (x64).
- **Плюсы**:
  - зрелый инструмент с хуками для `pydantic`, `keyring`, `pystray`, `huggingface_hub`; сборка занимает минуты и не требует компилятора C;
  - `onedir` стартует мгновенно и реже вызывает эвристические срабатывания антивирусов, чем самораспаковывающийся `onefile`;
  - автообновление сводится к замене каталога.
- **Минусы**:
  - дистрибутив 40–60 МБ (интерпретатор и библиотеки);
  - исходный код агента лежит в архиве байткода внутри дистрибутива (для открытого проекта несущественно);
  - без подписи кода SmartScreen показывает предупреждение при первом запуске (общая проблема всех вариантов).
- **Масштабирование на N инстансах**: не применимо (клиентское приложение).
- **Выделение модулей в микросервисы**: не применимо.
- **Трудоёмкость и риски**: низкая; риск — ложные срабатывания антивирусов на неподписанную сборку.

#### Вариант B. Nuitka, режим standalone

- **Описание**: Nuitka транслирует Python в C и компилирует нативный исполняемый файл с зависимостями (`--standalone`); нужен компилятор на каждом сборочном раннере (MSVC, clang, gcc).
- **Плюсы**:
  - нативный код: нет архива байткода, несколько быстрее запуск и выполнение;
  - меньше типовых сигнатур упаковщиков, на которые реагируют антивирусы.
- **Минусы**:
  - компиляция 15–40 минут на каждую платформу, нужен компилятор и его кэш в CI;
  - совместимость с новыми версиями Python и с библиотеками, использующими динамический импорт (`keyring`-бэкенды, `huggingface_hub`), приходится проверять на каждом обновлении;
  - производительность агенту не нужна: тяжёлую работу выполняет `llama-server`, агент только проксирует байты.
- **Масштабирование на N инстансах**: не применимо.
- **Выделение модулей в микросервисы**: не применимо.
- **Трудоёмкость и риски**: средняя; риск — длинные сборки и отладка несовместимостей вместо работы над функциями.

### 2.2. Маршрутизация запросов к агенту между инстансами монолита

#### Вариант A. Реестр «агент → инстанс» в Redis с TTL и пересылка через Redis pub/sub

- **Описание**: инстанс, принявший WebSocket агента, пишет `local_runtime:agent:<agent_id>:instance = <instance_id>` с TTL 90 с и обновляет ключ по heartbeat каждые 30 с. Любой инстанс, которому нужен агент, читает ключ: если это он сам — пишет в соединение напрямую; иначе публикует запрос в канал `local_runtime:agent:<agent_id>:inbox`, а ответы (в том числе части стрима) получает из канала `local_runtime:reply:<request_id>`, на который подписался до публикации. Инстанс-держатель соединения подписан на каналы `inbox` своих агентов.
- **Плюсы**:
  - тот же механизм, что доставка WebSocket-событий между инстансами в ADR-004 (Redis pub/sub) — одна инфраструктура;
  - задержка пересылки — миллисекунды, стриминг не страдает;
  - при остановке инстанса ключ истекает, агент переподключается через HAProxy к другому инстансу и перерегистрируется.
- **Минусы**:
  - pub/sub без гарантии доставки: при сбое Redis или подписчика часть стрима теряется — запрос завершается ошибкой, ученик повторяет (соответствует правилу CLAUDE.md: при потере Redis допустимо потерять незавершённое);
  - нужны тайм-ауты и порядковые номера частей, чтобы обнаруживать потери.
- **Масштабирование на N инстансах**: состояние — только ключ реестра в Redis с TTL и подписки; одновременные запросы к одному агенту с разных инстансов сериализуются очередью агента; сбой Redis рвёт текущие стримы, агенты переподключаются.
- **Выделение модулей в микросервисы**: при выделении `local_runtime` в отдельный сервис реестр и каналы остаются внутри него, остальные модули обращаются к нему через публичный API (в процессе сейчас, по REST или Kafka потом) — пересылка через Redis скрыта за интерфейсом.
- **Трудоёмкость и риски**: низкая-средняя; риск — ошибки в обработке тайм-аутов, покрываются тестами масштабируемости.

#### Вариант B. Пересылка через Kafka

- **Описание**: запросы к агентам публикуются в топик `local_runtime.agent_requests`, ответы — в `local_runtime.agent_replies`; инстанс-держатель фильтрует сообщения своих агентов.
- **Плюсы**:
  - гарантированная доставка и повтор при сбое.
- **Минусы**:
  - задержка Kafka (десятки миллисекунд на хоп) на каждой части стрима; все инстансы читают все части всех стримов (нет адресации по инстансу без партиционирования по `instance_id`, которое ломается при перезапусках);
  - стриминговые части — не доменные события, их хранение в Kafka бессмысленно;
  - противоречит ADR-004: Kafka — для событий и заданий, а не для сообщений с ответом в реальном времени.
- **Масштабирование на N инстансах**: работает, но дорого.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: средняя; риск — задержки стриминга, рост нагрузки на Kafka.

#### Вариант C. Агент держит соединение с каждым инстансом

- **Описание**: агент открывает по WebSocket к каждому инстансу, и любой инстанс пишет агенту напрямую.
- **Минусы**: инстансы не адресуемы снаружи — HAProxy скрывает их и балансирует по кругу; число инстансов меняется; соединений в N раз больше. Вариант невозможен без sticky-маршрутизации, которую CLAUDE.md запрещает.
- **Масштабирование на N инстансах**, **выделение модулей**, **трудоёмкость**: не оцениваются — вариант неприменим в принятой архитектуре.

### 2.3. Общие схемы протокола между агентом и монолитом

#### Вариант A. Отдельный пакет `flt-protocol` в `src/protocol`, устанавливается по пути

- **Описание**: пакет `flt_protocol` с Pydantic-моделями сообщений, перечислением типов и константой `PROTOCOL_VERSION`; монолит ставит его так же, как `py-main-lib` (из папки репозитория, `uv pip install /src/protocol` в `Dockerfile`), агент — как path-зависимость в своём `pyproject.toml`. В PyPI не публикуется.
- **Плюсы**:
  - один источник схем, расхождение невозможно; изменение протокола — один коммит с тестами обеих сторон;
  - контрактный тест сверяет JSON Schema, экспортированную из `flt_protocol`, с `Analytics/Specs/local_runtime/api/asyncapi.yaml`.
- **Минусы**:
  - третий устанавливаемый пакет в репозитории; `Dockerfile` монолита получает второй build-context.
- **Масштабирование на N инстансах**: не применимо.
- **Выделение модулей в микросервисы**: помогает — при выделении `local_runtime` пакет уходит с ним.
- **Трудоёмкость и риски**: низкая.

#### Вариант B. Копия схем в агенте и в `local_runtime`

- **Описание**: модели описаны дважды, тест сравнивает экспортированные JSON Schema.
- **Минусы**: дублирование, расхождения находятся только тестом, правки в двух местах.
- **Масштабирование**, **выделение модулей**: не применимо / нейтрально.
- **Трудоёмкость и риски**: низкая на старте, растёт с числом сообщений.

#### Вариант C. Генерация кода обеих сторон из AsyncAPI

- **Описание**: AsyncAPI — источник, Pydantic-модели генерируются (`datamodel-code-generator`) в оба пакета на этапе сборки.
- **Минусы**: генераторы для AsyncAPI 3 и Pydantic v2 требуют постобработки; сгенерированный код хуже читается; сборка усложняется.
- **Масштабирование**, **выделение модулей**: не применимо / нейтрально.
- **Трудоёмкость и риски**: средняя; риск — борьба с генератором.

### 2.4. Сопряжение агента с учеником

#### Вариант A. Поток авторизации устройства (по образцу RFC 8628)

- **Описание**: агент запрашивает у платформы код сопряжения, открывает браузер на странице подтверждения с этим кодом; ученик, уже вошедший на платформу, подтверждает привязку устройства; агент опрашивает платформу и получает долгоживущий токен агента.
- **Плюсы**: ученик ничего не вводит в агент; агент не видит пароль и токен пользователя; стандартный, понятный поток; работает и без локального браузера (код показывается в трее и вводится вручную на странице).
- **Минусы**: нужны два REST-эндпоинта и состояние в Redis с TTL.
- **Масштабирование на N инстансах**: состояние сопряжения — в Redis с TTL 10 минут; запрос, подтверждение и опрос могут прийти на разные инстансы.
- **Выделение модулей в микросервисы**: нейтрально — эндпоинты принадлежат `local_runtime`.
- **Трудоёмкость и риски**: низкая; риск — перебор кодов, закрывается лимитом запросов и энтропией кода.

#### Вариант B. Код, показанный в UI платформы, вводится в агент

- **Описание**: ученик нажимает «Подключить агент» в UI, получает код, вводит его в окно агента; агент обменивает код на токен.
- **Минусы**: нужен графический диалог ввода в агенте (трей-приложение без окон его не имеет); та же серверная логика, что в A, плюс UI в агенте.
- **Масштабирование**, **выделение модулей**: как у A.
- **Трудоёмкость и риски**: средняя из-за UI.

#### Вариант C. Токен пользователя копируется в агент

- **Описание**: ученик копирует свой токен доступа или refresh-токен в конфигурацию агента.
- **Минусы**: токен доступа короткоживущий, refresh-токен даёт полный доступ к аккаунту; токен проходит через буфер обмена; отзыв устройства невозможен отдельно от выхода из аккаунта. Вариант небезопасен.
- **Масштабирование**, **выделение модулей**, **трудоёмкость**: не оцениваются.

## 3. Решение

- **Выбран**: 2.1 — Вариант A (PyInstaller, onedir); 2.2 — Вариант A (реестр в Redis и pub/sub); 2.3 — Вариант A (пакет `flt-protocol`); 2.4 — Вариант A (авторизация устройства).
- **Решение**: локальный агент — трей-приложение на Python 3.14 (ADR-001, та же версия и политика обновлений, что у монолита) в `src/agent` (пакет `flt_agent`), собираемое PyInstaller в режиме onedir под Windows x64, macOS arm64/x64 и Linux x64; оно связывается с платформой единственным исходящим WebSocket `wss://<domain>/ws/agent` через HAProxy, аутентифицируется долгоживущим токеном агента (`Authorization: Bearer`), полученным потоком авторизации устройства и хранящимся в системном хранилище учётных данных; схемы сообщений — общий пакет `flt_protocol` в `src/protocol`; инстансы монолита находят агент по реестру `local_runtime:agent:<agent_id>:instance` в Redis и пересылают запросы и части стрима через Redis pub/sub; агент выполняет только команды из белого списка протокола и обращается только к локальным движкам на `127.0.0.1` и к каталогам сборок и моделей, которые ведёт платформа.
- **Обоснование**: PyInstaller даёт быстрые сборки без компилятора и достаточен для приложения, которое не выполняет вычислений само (2.1); Redis pub/sub уже выбран ADR-004 для доставки между инстансами и даёт нужную задержку (2.2); общий пакет исключает расхождение схем и уходит вместе с модулем при выделении (2.3); авторизация устройства не требует UI ввода в агенте и не раскрывает агенту учётные данные пользователя (2.4). Рекомендация Claude в OQ-19 подтверждена с уточнениями: режим onedir вместо onefile; сопряжение инициирует агент, а не UI.
- **Отвергнуты**:
  - 2.1 B (Nuitka) — долгие сборки и риск несовместимостей без выгоды для прокси-приложения; пересматривается, если антивирусы будут массово блокировать сборки PyInstaller.
  - 2.2 B (Kafka) — задержки и широковещание частей стрима; 2.2 C — неприменим без sticky-маршрутизации.
  - 2.3 B (копия) — дублирование; 2.3 C (кодогенерация) — сложность сборки.
  - 2.4 B (ввод кода в агент) — лишний UI; 2.4 C (токен пользователя) — небезопасен.
- **Границы решения**: ADR не описывает семантику стриминга LLM и передачу голоса через агента (ADR-009), алгоритм подбора модели под железо (ТЗ STU-04), доставку десктопных уведомлений для заучивания слов (ТЗ STU-34.1: Web Push или агент), форматы сообщений в деталях (AsyncAPI в ТЗ STU-05), подписание кода (новый открытый вопрос, см. отчёт).

### 3.1. Состав и структура агента

```
src/agent/
```

Зависимости агента (все с лицензиями MIT, BSD или Apache-2.0): `websockets`, `httpx`, `pydantic`, `platformdirs`, `keyring`, `psutil`, `py-cpuinfo`, `nvidia-ml-py`, `huggingface_hub`, `pystray`, `Pillow`, `certifi`, `flt-protocol`. Запрещены: `py-main-lib`, любой код `src/backend`, `aioboto3`. Архитектурный тест (ADR-002, import-linter в `src/agent`) проверяет, что `flt_agent` импортирует из репозитория только `flt_protocol`. Качество кода — те же ruff и mypy strict, что у монолита; `make check` в `src/agent`.

Каталоги на компьютере ученика (через `platformdirs`, имя приложения `flt-agent`): конфигурация — `user_config_dir` (`%APPDATA%\flt-agent`, `~/Library/Application Support/flt-agent`, `~/.config/flt-agent`); данные — `user_data_dir/flt-agent/{models,engines,updates}`; логи — `user_log_dir`. Установка — в каталог пользователя без прав администратора (`%LOCALAPPDATA%\Programs\flt-agent`, `~/Applications/FLT Agent.app`, `~/.local/opt/flt-agent`); автозапуск при входе в систему — по согласию пользователя при установке (`HKCU\…\Run`, LaunchAgent, XDG autostart). Агент работает в сеансе пользователя как трей-приложение (LM Studio, видеокарта и хранилище учётных данных доступны именно там); режим `--headless` без трея — для Linux без графической среды и для CI; системная служба не делается.

### 3.2. Сборка, дистрибутивы, подпись, обновление

- Сборка: GitHub Actions (ADR-011) по тегу `agent-v<X.Y.Z>`: PyInstaller onedir на четырёх раннерах; артефакты `flt-agent-<ver>-win-x64-setup.exe` (Inno Setup, установка для пользователя) и `flt-agent-<ver>-win-x64.zip`, `flt-agent-<ver>-macos-arm64.dmg`, `flt-agent-<ver>-macos-x64.dmg`, `flt-agent-<ver>-linux-x64.tar.gz`, файл `SHA256SUMS`. Версия агента — SemVer, независимая от версии монолита; совместимость задаёт `PROTOCOL_VERSION`.
- Размещение дистрибутивов: публичный префикс `public/releases/<ver>/` бакета `flt-local-runtime` (ADR-007) — работает при любой видимости репозитория (OQ-39) и держит трафик в РФ; GitHub Releases — зеркало, если репозиторий публичный. Платформа отдаёт манифест `GET /api/v1/local-runtime/agent-releases/latest?os=windows&arch=x64` → `{version, min_supported_version, url, sha256, size, release_notes_url}`; манифест заполняет CI через S3 API в тот же префикс, ссылки на страницу «Подключить агент» ведут на него.
- Подпись кода: сборки этапа 4 **не подписаны** — сертификат Authenticode (OV, аппаратный токен с 2023 года, 300–500 USD в год, выдача западными УЦ юрлицам РФ ограничена) и Apple Developer Program (99 USD в год, нотаризация) требуют решения пользователя (новый открытый вопрос). Без подписи: Windows SmartScreen показывает предупреждение «неизвестный издатель», macOS Gatekeeper требует открыть приложение через контекстное меню; страница скачивания содержит инструкцию и контрольные суммы. Конвейер сборки сразу содержит шаги `signtool` и `codesign`/`notarytool`, выключенные флагами до появления сертификатов.
- Обновление. Этап 4: при подключении платформа сообщает в `agent.hello_ack` поля `latest_agent_version` и `update_required`; трей показывает «Доступно обновление» и открывает страницу скачивания; при `protocol_version` ниже `min_protocol_version` платформа закрывает соединение с кодом `AGENT_UPDATE_REQUIRED`, а UI платформы показывает инструкцию. Этап 5: автообновление — агент скачивает дистрибутив по манифесту в `updates/<ver>/`, проверяет `sha256` (и подпись, когда она появится), запускает вспомогательный процесс `flt-agent-updater` из состава дистрибутива, который дожидается завершения агента, переименовывает каталоги (`current` → `previous`, `updates/<ver>` → `current`) и перезапускает агент; при трёх неудачных стартах подряд `previous` возвращается. Обновление выполняется только после подтверждения пользователя в трее, если не включён флаг «обновлять автоматически».

### 3.3. Характеристики железа

Собираются при запуске и далее раз в сутки или по команде `hardware.refresh`; отправляются в `agent.hello` и `hardware.profile`. Схема `HardwareProfile` в `flt_protocol`:

| Поле | Источник | Примечание |
|---|---|---|
| `os {name, version, arch}` | `platform` | `windows`, `macos`, `linux`; `x64`, `arm64` |
| `cpu {model, physical_cores, logical_cores, flags}` | `py-cpuinfo`, `psutil` | флаги только `avx2`, `avx512`, `neon` |
| `ram_total_bytes`, `ram_available_bytes` | `psutil.virtual_memory()` | |
| `gpus[] {vendor, name, vram_total_bytes, vram_free_bytes, driver_version, cuda_version, backend_hint}` | NVIDIA — `nvidia-ml-py` (NVML); Apple — `system_profiler -json SPHardwareDataType SPDisplaysDataType` (unified memory = ОЗУ, `backend_hint: metal`); AMD и Intel — Linux: `/sys/class/drm/card*/device/mem_info_vram_total`, имя из `lspci`; Windows: имя из `Get-CimInstance Win32_VideoController`, объём памяти неизвестен (`null`), `backend_hint: vulkan` | `backend_hint` — `cuda`, `metal`, `vulkan`, `cpu` |
| `disk_free_bytes`, `models_dir_bytes` | `psutil.disk_usage(models_dir)` | для проверки места перед скачиванием |
| `agent_version`, `protocol_version` | константы | |

Сервер хранит последний профиль в `local_runtime.hardware_profiles` (JSONB, `agent_id`, `collected_at`); подбор модели (STU-04) работает по нему и по каталогу моделей на стороне платформы — агент выбор не делает.

### 3.4. Локальные движки

Оба движка предоставляют OpenAI-совместимый HTTP API, поэтому в агенте один клиент движка (`engines/base.py`), а `llm_gateway` платформы формирует тело запроса одним и тем же OpenAI-совместимым адаптером (OQ-09, SYS-08); агент тело запроса не интерпретирует и не изменяет, кроме подстановки локального `api-key`.

- **LM Studio (этап 4, STU-05)**: сервер LM Studio слушает `http://127.0.0.1:1234` (порт настраивается в агенте), эндпоинты `GET /v1/models`, `POST /v1/chat/completions` (`stream: true`, SSE), `POST /v1/embeddings`. Обнаружение — успешный `GET /v1/models`; если сервер не запущен и найден CLI `lms` (`~/.lmstudio/bin/lms`, в Windows `%USERPROFILE%\.lmstudio\bin\lms.exe`), команда `engine.start` для `lm_studio` выполняет ровно `lms server start --port <port>`; иначе агент сообщает `ENGINE_NOT_RUNNING`, а UI платформы показывает инструкцию «Developer → Start Server». Загрузку моделей в LM Studio ученик делает сам в LM Studio; агент отдаёт список из `/v1/models`.
- **llama.cpp (этап 5, STU-02)**: используется `llama-server` из официальных сборок GitHub (`ggml-org/llama.cpp`), а не `llama-cpp-python`: сборки под CUDA, Vulkan, Metal и CPU готовы и не требуют компиляции в замороженном приложении, API совпадает с LM Studio. Платформа ведёт каталог сборок `local_runtime.engine_builds` (`build_id`, тег релиза, `os`, `arch`, `backend`, `url`, `sha256`, `size`, `requires` — например `cudart`), агент скачивает только записи каталога, проверяет `sha256`, распаковывает в `engines/llama.cpp/<build_id>/`. Выбор сборки — по `backend_hint`: NVIDIA с драйвером CUDA 12 → `cuda` (+ архив `cudart`), Apple Silicon → `macos-arm64` (Metal), AMD и Intel → `vulkan`, иначе → `cpu` (`avx2`). Запуск: `llama-server --host 127.0.0.1 --port <свободный> --api-key <случайный на запуск> -m <gguf> -ngl <n> -c <ctx>` с параметрами из команды `engine.start`; готовность — `GET /health`; остановка — по команде, при выходе агента и при бездействии дольше настраиваемого срока (по умолчанию 30 минут).
- **Модели (этап 5)**: формат GGUF; каталог `local_runtime.model_catalog` (`repo_id`, `filename`, `quantization`, `size`, `sha256` из LFS-указателя, `min_vram_bytes`, `min_ram_bytes`, `context_length`, `languages`) ведёт платформа (администратор платформы — ТЗ этапа 5). Скачивание — `huggingface_hub.hf_hub_download` в `models/` с докачкой после обрыва, прогресс `model.download_progress` раз в 2 секунды, проверка `sha256` после скачивания. Адрес Hugging Face настраивается (`HF_ENDPOINT`, по умолчанию `https://huggingface.co`; платформа может передать зеркало в каталоге — доступность Hugging Face из сетей РФ нестабильна). Перед скачиванием проверяется место: свободно не меньше `size × 1.1 + 2 ГиБ`; общий объём `models/` ограничен настройкой (по умолчанию 50 ГиБ), превышение требует удаления моделей с подтверждением пользователя. Агент не читает файлы вне `models/` и `engines/`.

### 3.5. Протокол агент ↔ платформа

- Транспорт: один WebSocket `wss://<domain>/ws/agent` → HAProxy → роль `api` монолита (ADR-012: таймауты туннеля как у `/ws/*`); текстовые JSON-кадры в конверте ADR-004 `{type, correlation_id, channel, seq, ts, payload}` (`channel` у агента всегда `null`, `seq` — сквозной номер в соединении); бинарные кадры с заголовком ADR-004 (тип, `stream_id`, `seq`) зарезервированы (голос — ADR-009). Контракт — `Analytics/Specs/local_runtime/api/asyncapi.yaml`, модели — `flt_protocol`. Типы сообщений агента (таблица ниже) отличаются от типов браузера: браузер получает `llm_gateway.completion.start/delta/end/error` (ADR-009), а `llm_gateway` транслирует в них `llm.chunk`/`llm.done`/`llm.error` агента — агент о протоколе браузера не знает.
- Рукопожатие: HTTP-заголовок `Authorization: Bearer flta_<token>` при открытии соединения; первый кадр `agent.hello {agent_version, protocol_version, os, arch, device_label, capabilities: ["lm_studio", "llama_cpp"], hardware_profile}`; ответ `agent.hello_ack {agent_id, server_time, heartbeat_interval_s: 30, latest_agent_version, min_protocol_version, update_required}`. Соединение с неизвестным, отозванным токеном или устаревшим протоколом закрывается с кодом 4401 (`AGENT_UNAUTHORIZED`) или 4426 (`AGENT_UPDATE_REQUIRED`).
- Heartbeat: `agent.heartbeat {engines: [{kind, running, port, models_loaded}]}` каждые 30 с плюс ping/pong уровня WebSocket; инстанс продлевает ключ реестра; два пропущенных heartbeat — сервер закрывает соединение.
- Переподключение: экспоненциальная задержка 1 с → 60 с с джиттером, без ограничения попыток; при разрыве агент прерывает запросы к движку, платформа завершает незавершённые запросы ошибкой `AGENT_DISCONNECTED` (повтор генерации не выполняется автоматически — ADR-009).
- Типы сообщений (белый список `flt_protocol.agent.enums.MessageType`; неизвестный тип → `agent.error {code: UNSUPPORTED_MESSAGE_TYPE}` без разрыва соединения):

| Направление | Типы |
|---|---|
| платформа → агент | `engine.list_models`, `engine.status`, `engine.start`, `engine.stop`, `llm.request`, `llm.cancel`, `model.list`, `model.download`, `model.delete`, `hardware.refresh`, `agent.update` (этап 5) |
| агент → платформа | `agent.hello`, `agent.heartbeat`, `agent.error`, `engine.models`, `engine.status`, `llm.chunk`, `llm.done`, `llm.error`, `model.list_result`, `model.download_progress`, `model.downloaded`, `model.deleted`, `hardware.profile` |

`llm.request {engine, model, body, stream}` несёт OpenAI-совместимое тело; `llm.chunk {seq, delta}` нумеруется с 0; `llm.done {usage}` закрывает запрос; семантика частей и отмены — ADR-009. Этапу 4 нужны `agent.*`, `engine.*`, `llm.*`, `hardware.*`; `model.*` и `agent.update` — этап 5.

### 3.6. Сопряжение и токен агента

1. Агент: `POST /api/v1/local-runtime/pairings` (без аутентификации, лимит 5 запросов в минуту с IP) с `{agent_version, os, arch, device_label}` → `{pairing_id, user_code, verification_url, expires_in: 600, poll_interval: 5}`; `user_code` — 8 символов алфавита без похожих знаков (`ABCDEFGHJKMNPQRSTUVWXYZ23456789`) в виде `XXXX-XXXX`; состояние — `local_runtime:pairing:<pairing_id>` в Redis с TTL 600 с и индекс `local_runtime:pairing_code:<user_code>`.
2. Агент открывает браузер на `verification_url` (`https://<domain>/settings/local-agent?code=XXXX-XXXX`) и дублирует код в меню трея. Ученик, вошедший на платформу, видит сведения об устройстве и подтверждает привязку; платформа создаёт запись `local_runtime.agents` (`id`, `user_id`, `device_label`, `token_hash`, `os`, `arch`, `agent_version`, `created_at`, `last_seen_at`, `revoked_at`) и кладёт токен в состояние сопряжения.
3. Агент опрашивает `POST /api/v1/local-runtime/pairings/{pairing_id}/token` каждые 5 с: `authorization_pending`, `expired` или один раз `{agent_id, agent_token}`; после выдачи состояние удаляется.
4. Токен `flta_` + 32 случайных байта в base64url хранится агентом через `keyring` (служба `flt-agent`, имя — хост платформы); без доступного бэкенда (Linux без Secret Service) — файл `credentials.json` в каталоге конфигурации с правами `0600` и предупреждением в логе. На сервере хранится только `sha256` токена.

Токен агента — отдельный тип учётных данных (ADR-006, раздел 3.4): непрозрачная строка, не JWT; действует только на `/ws/agent` и не даёт доступа к REST API пользователя и к `/ws` (`TokenVerifier` shared kernel отклоняет префикс `flta_`); не истекает, отзывается учеником в UI (список устройств, STU-05) или при удалении аккаунта (событие `identity.user_deleted`); у ученика может быть несколько агентов, активное устройство выбирается в профиле (ТЗ STU-03/STU-05). Проверку по хэшу выполняет обработчик `/ws/agent` модуля `local_runtime`; `identity` участвует в сопряжении только тем, что страница подтверждения требует вошедшего пользователя (обычная cookie-аутентификация) и даёт публичный API `IdentityService.get_user`.

### 3.7. Маршрутизация на N инстансах

- Реестр: `local_runtime:agent:<agent_id>:instance` = `{instance_id, user_id, connected_at}`, TTL 90 с, обновляется heartbeat; `local_runtime:user:<user_id>:agents` — множество подключённых агентов с тем же TTL на запись.
- Запрос: `llm_gateway` (адаптер провайдера `local`, ADR-009) вызывает публичный API `local_runtime` (`LocalRuntimeService.stream(agent_id, request) -> AsyncIterator[Chunk]`); сервис читает реестр; если держатель — текущий инстанс, пишет в соединение; иначе подписывается на `local_runtime:reply:<request_id>`, публикует запрос в `local_runtime:agent:<agent_id>:inbox` и ретранслирует части; держатель публикует части с `seq`; отмена — тем же каналом `inbox` (схема каналов «inbox держателя + `<module>:reply:<request_id>`» — ADR-004; ключи и каналы через `ModuleRedis(prefix="local_runtime")` — ADR-003). `llm_gateway` преобразует `Chunk` (из `llm.chunk`/`llm.done`/`llm.error`) в сообщения браузера `llm_gateway.completion.delta/end/error` (ADR-009). Тайм-ауты: первая часть — 120 с (загрузка модели в память), простой между частями — 60 с; разрыв последовательности `seq` — `AGENT_STREAM_LOST`.
- Сбой Redis: текущие стримы завершаются ошибкой, реестр восстанавливается при переподключении агентов; постоянные данные (агенты, профили железа, каталоги) — в PostgreSQL. Остановка инстанса: агент переподключается к другому инстансу через HAProxy за 1–60 с.
- Тесты масштабируемости (SYS-05, SYS-10): агент (режим `--headless`, движок — заглушка с детерминированным SSE) подключён к инстансу 1; запрос ученика приходит на инстанс 2 и получает стрим; инстанс 1 останавливается посреди стрима — запрос завершается `AGENT_DISCONNECTED`, агент переподключается, следующий запрос с инстанса 3 проходит; два одновременных запроса с разных инстансов не смешивают части.
- Метрики: `flt_local_agents_connected`, `flt_local_agent_requests_total{result}`, `flt_local_agent_first_chunk_seconds`, `flt_local_agent_forwarded_total` (через Redis). В логах — `agent_id`, `request_id`, размеры; никогда — содержимое промптов и ответов.

### 3.8. Безопасность и приватность

- Агент не открывает входящих портов и не запускает локальный HTTP-сервер; команды принимаются только из аутентифицированного WebSocket; `platform_url` задаётся при установке и меняется только с повторным сопряжением; TLS проверяется по системным сертификатам и пакету `certifi`.
- Белый список действий — перечисление типов сообщений; внешние процессы, которые агент вправе запускать: `llama-server` из проверенной сборки в `engines/`, `lms server start`, `system_profiler`, `Get-CimInstance`, `lspci`. Произвольных команд, скриптов, `eval` и загрузки кода с платформы нет; агент не обновляет себя без проверки `sha256`.
- Движки слушают только `127.0.0.1`; `llama-server` получает случайный `api-key` на каждый запуск, чтобы другие локальные процессы им не пользовались.
- Скачивание — только из записей каталогов платформы и только с хостов `github.com`, `objects.githubusercontent.com`, `huggingface.co`, `*.hf.co` и настроенного зеркала; пути файлов строятся из идентификаторов каталога и остаются внутри `models/` и `engines/` (проверка нормализованного пути).
- Данные, покидающие компьютер ученика, идут только на хост платформы: профиль железа (3.3), состояние движков и список моделей, ответы модели на запросы платформы, версия агента. Имя компьютера и имя пользователя ОС не передаются; `device_label` задаёт ученик. Текст запросов и ответов проходит через платформу по необходимости (она их и формирует) и в локальные логи агента не пишется.
- Телеметрия: только локальные логи с ротацией (5 файлов по 5 МиБ) в `user_log_dir`, кнопка «Открыть логи» в трее. Отправка отчётов об ошибках на платформу (`agent.error_report` без путей и текстов запросов) — этап 5, только по включённому пользователем флагу, по умолчанию выключена.
- Процесс работает от пользователя без повышения прав; антивирусные исключения не запрашиваются.

## 4. Последствия

### 4.1. Положительные

- Единый стек Python: агент, протокол и монолит проверяются одними инструментами, схемы сообщений не расходятся.
- `llm_gateway` работает с локальной моделью через тот же OpenAI-совместимый адаптер, что с внешними провайдерами, — LLM-агностичность сохраняется.
- Агент находится с любого инстанса; остановка инстанса стоит ученику одного прерванного ответа, а не потери связи.
- Сопряжение без ввода секретов в агент; устройство отзывается отдельно от аккаунта.
- Ограниченный набор действий агента и каталоги платформы делают поведение агента предсказуемым и проверяемым тестами.

### 4.2. Отрицательные и их смягчение

| Последствие | Смягчение |
|---|---|
| Неподписанные сборки вызывают предупреждения SmartScreen и Gatekeeper | открытый вопрос о сертификатах; инструкция и контрольные суммы на странице скачивания; шаги подписи в CI готовы и выключены |
| Дистрибутив 40–60 МБ | приемлемо рядом с моделями на гигабайты; onedir и дедупликация обновлений не планируются |
| Потеря частей стрима при сбое Redis | ошибка `AGENT_STREAM_LOST` и повтор по действию ученика; постоянные данные не затронуты |
| Hugging Face недоступен или медленный из РФ | настраиваемое зеркало в каталоге; докачка; платформа может хранить копии разрешённых моделей в своём хранилище (решение в ТЗ STU-02) |
| Третий устанавливаемый пакет (`flt-protocol`) | тот же механизм, что `py-main-lib`: build-context в `Dockerfile`, path-зависимость у агента |
| Поддержка четырёх платформ в CI | матрица GitHub Actions; ручная проверка установки на каждой платформе — критерий G3 для STU-05 |
| Токен агента не истекает | хранится в системном хранилище, отзывается в UI, на сервере — только хэш; `last_seen_at` для выявления брошенных устройств |
