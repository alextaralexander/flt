## 1. Контекст

- **Проблема**: CLAUDE.md («Взаимодействие») задаёт три транспорта — REST, WebSocket, Kafka — и принципы (outbox, идемпотентные консьюмеры, dead letter topic, вызовы между модулями через интерфейсы), но не фиксирует реализацию: один эндпоинт WebSocket или на модуль, формат сообщений, доставка событий между инстансами, кто публикует outbox, как устроены ретраи, где живут фоновые задания и периодические задачи, как монолит запускается в ролях API и воркера из одного образа (OQ-17), как модули вызывают друг друга в процессе.
- **Почему сейчас**: этап 1, пункты Г.4 (shared kernel: публикация и потребление событий через outbox, инфраструктура WebSocket с доставкой через Redis), Г.6 (стриминг заглушки LLM по WebSocket), Г.8 (N реплик за HAProxy, миграции отдельным шагом), Г.11 (E2E: фоновое задание через Kafka, остановка инстанса посреди сценария). SYS-04 и SYS-11 пишутся по этому решению.
- **Ограничения**:
  - CLAUDE.md «Взаимодействие»: контракты заранее (OpenAPI, AsyncAPI); синхронный вызов между модулями — публичный API в процессе через интерфейс; Kafka только внутри монолита; модуль публикует только свои события в свои топики; outbox; идемпотентные консьюмеры; ретраи и DLQ; версионирование схем; WebSocket обслуживает монолит, события между инстансами — через Redis pub/sub; единый формат сообщений WebSocket.
  - CLAUDE.md «Масштабирование и состояние»: задания распределяются consumer group; периодические задачи не дублируются; инстанс останавливается в любой момент.
  - Решения этапа 0: только Kafka (NATS удалён); HAProxy — единственная точка входа (`/api/*`, `/ws/*`); health-эндпоинты `/v1/health`, `/v1/ready` (OQ-21); OQ-13: 300 WebSocket-соединений, 50 одновременных LLM-стримов.
  - Boilerplate: FastAPI с роутером `v1_router`; FastStream 0.7 `KafkaRouter` включён в приложение FastAPI (консьюмеры работают в процессе API); публикация — `kafka_router.broker.publish(...)`; ошибка обработки → callback-топик (`KAFKA_ERROR_TOPIC_BY_SOURCE`); один `KAFKA_GROUP_ID` на сервис; имена топиков вида `some_service.inf.second_topic.02`; `TestKafkaBroker` в тестах; WebSocket, outbox, планировщика и ролей запуска нет.
- **Если не решить**: модули начнут публиковать в Kafka напрямую из транзакции (потеря и дублирование событий), консьюмеры будут нагружать процесс API, WebSocket-события с другого инстанса не дойдут до клиента, периодические задачи выполнятся на всех N инстансах, а вызовы между модулями превратятся в импорт внутренностей.
- **Ссылки**: CLAUDE.md «Взаимодействие», «Масштабирование и состояние», «Развёртывание»; SDD_plan.md этап 1 А.4, Б.3, Б.4, Б.11, Г.4, Г.6, Г.8, Г.11; OQ-17, OQ-24; глоссарий раздел 12 (`outbox`, `consumer`, `consumer_group`, `dead_letter_topic`, `background_job`, `runtime_role`, `domain_event`, `topic`).

## 2. Рассматриваемые варианты

Решение состоит из шести подвопросов; варианты рассматриваются внутри каждого. Выбор транспорта по типу взаимодействия (REST, WebSocket, Kafka, прямой вызов) не имеет альтернатив — он задан CLAUDE.md и сведён в правило в разделе 3.

### 2.1. WebSocket: один эндпоинт или эндпоинт на модуль

#### Вариант A. Один эндпоинт `/ws` с мультиплексированием каналов

- **Описание**: одно соединение на клиента; после аутентификации клиент подписывается на каналы `<module>.<channel>[:<id>]` (например `llm_gateway.stream:<correlation_id>`, `classroom.lesson:<lesson_id>`, `notifications.user`). Shared kernel держит реестр обработчиков: модуль регистрирует `WsChannelHandler` для своих каналов (проверка права подписки, обработка входящих команд). Доставка исходящих событий — через Redis pub/sub.
- **Плюсы**:
  - одно соединение, одна аутентификация, одна логика переподключения на клиенте; браузерный лимит соединений не расходуется;
  - в HAProxy один маршрут `/ws` с таймаутами WebSocket (ADR-012);
  - права на канал проверяет модуль-владелец, транспорт — shared kernel.
- **Минусы**:
  - реестр каналов — общая точка: формат имени канала и envelope задаются один раз (SYS-04), менять дорого.
- **Масштабирование на N инстансах**: соединение живёт на одном инстансе; события публикуются в Redis с любого инстанса и любой роли; при остановке инстанса клиент переподключается к другому и переподписывается.
- **Выделение модулей в микросервисы**: нейтрально — транспорт остаётся в API-шлюзе, обработчик канала модуля переезжает за интерфейс (вызов становится Kafka-командой или REST).
- **Трудоёмкость и риски**: средняя (реестр, подписки, pub/sub); риск «толстого» шлюза снимается правилом: shared kernel не содержит логики каналов, только маршрутизацию.

#### Вариант B. Эндпоинт на модуль `/ws/<module>`

- **Описание**: каждый модуль поднимает свой `WebSocket`-роут и свою аутентификацию.
- **Плюсы**:
  - модуль полностью владеет протоколом канала; при выделении маршрут `/ws/<module>` переключается на сервис в HAProxy.
- **Минусы**:
  - клиент держит до 5–7 соединений (LLM, уведомления, класс, заучивание, агент), у каждого своя аутентификация и переподключение; браузерный лимит на домен — 6 HTTP/1.1-соединений, HAProxy должен держать HTTP/2;
  - уведомления, нужные на любой странице, требуют отдельного постоянного соединения;
  - дублируется код аутентификации и heartbeat в каждом модуле.
- **Масштабирование на N инстансах**: как A, но кратно соединениям.
- **Выделение модулей в микросервисы**: помогает маршрутизацией, но WebSocket-шлюз всё равно понадобится для уведомлений.
- **Трудоёмкость и риски**: выше за счёт дублирования.

### 2.2. Именование топиков и версионирование событий

#### Вариант A. `flt.<module>.<event>.v<N>`, DLQ `<topic>.dlq`, задания `flt.<module>.jobs.<job>.v<N>`

- **Описание**: префикс приложения, модуль-владелец, событие в прошедшем времени snake_case, мажорная версия схемы в имени; минорные совместимые изменения — поле `event_version` в envelope. Примеры: `flt.identity.user_registered.v1`, `flt.dictionary.entry_generated.v1`, `flt.materials.jobs.extract_text.v1`, `flt.identity.user_registered.v1.dlq`.
- **Плюсы**:
  - однозначно в общем кластере Kafka (стенды dev и test могут делить брокер с префиксом стенда в `bootstrap`-конфигурации или отдельным кластером — SYS-11);
  - несовместимое изменение — новый топик, старые консьюмеры дочитывают старый;
  - retention и партиции настраиваются по событию.
- **Минусы**:
  - длинные имена.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: помогает — топики модуля определяются префиксом.
- **Трудоёмкость и риски**: низкая.

#### Вариант B. `<module>.<event>` (предварительная схема CLAUDE.md), версия только в схеме

- **Описание**: без префикса приложения и версии в имени.
- **Плюсы**:
  - короче.
- **Минусы**:
  - несовместимое изменение схемы ломает консьюмеров или требует переключателя по `event_version` в каждом консьюмере;
  - конфликты имён в общем кластере.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая сейчас, миграции схем позже.

### 2.3. Transactional outbox: кто публикует

#### Вариант A. Relay в роли `worker` под распределённой блокировкой, таблица `outbox` в схеме каждого модуля

- **Описание**: сервис модуля в одной транзакции с изменением данных пишет строку в `<module>.outbox` (через `OutboxPublisher` shared kernel). Relay — цикл в роли `worker` (ADR-004, п. 2.5): на каждый модуль один активный relay, выбранный блокировкой `shared_kernel:lock:outbox:<module>` (TTL 30 с, продление heartbeat-ом); выборка `SELECT ... WHERE published_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED`; публикация в Kafka с `key = aggregate_id` и заголовками; `UPDATE published_at = now()`; пауза 200 мс при пустой выборке с ростом до 2 с. Реплики `worker` без блокировки ждут; `SKIP LOCKED` страхует от двойной публикации при потере блокировки (ADR-003, п. 2.7). Строки с `published_at` старше 7 суток удаляет периодическая задача. Семантика — at-least-once, порядок по агрегату сохраняется (один relay, один ключ партиции).
- **Плюсы**:
  - событие не теряется (одна транзакция с данными) и не публикуется мимо outbox (прямой `broker.publish` из модулей запрещён import-linter);
  - роль `api` не держит соединение с Kafka: отказ Kafka не влияет на REST и WebSocket, события копятся в outbox;
  - задержка публикации ≤ 300 мс при нагрузке.
- **Минусы**:
  - опрос таблицы каждые 200 мс на модуль (при 20 модулях — 100 лёгких запросов в секунду с индексом по `published_at IS NULL`); `LISTEN/NOTIFY` как ускоритель откладывается до появления потребности.
- **Масштабирование на N инстансах**: relay один на модуль, воркеры взаимозаменяемы; остановка воркера — блокировка истекает, другой подхватывает за ≤ 30 с.
- **Выделение модулей в микросервисы**: помогает — таблица `outbox` и relay уезжают с модулем.
- **Трудоёмкость и риски**: средняя (shared kernel: таблица, publisher, relay, уборка); покрывается тестами на N инстансах.

#### Вариант B. Relay в каждом инстансе всех ролей, только `FOR UPDATE SKIP LOCKED`

- **Описание**: без блокировки, параллельные relay в `api` и `worker`.
- **Плюсы**:
  - меньшая задержка, нет зависимости от Redis.
- **Минусы**:
  - порядок событий одного агрегата нарушается между параллельными выборками (две строки одного `aggregate_id` могут уйти из разных relay в разном порядке);
  - роль `api` получает соединение с Kafka и нагрузку relay.
- **Масштабирование на N инстансах**: работает, но без порядка.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая; нарушение порядка проявляется редко и трудно воспроизводится.

#### Вариант C. CDC (Debezium) из таблицы outbox

- **Описание**: Kafka Connect с коннектором Debezium читает WAL PostgreSQL.
- **Плюсы**:
  - без опроса, минимальная задержка, exactly-once в Kafka.
- **Минусы**:
  - два новых контейнера (Kafka Connect, настройка логической репликации), JVM, ещё одна система в мониторинге; несоразмерно этапу 1.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: высокая эксплуатационная.

### 2.4. Очередь фоновых заданий

#### Вариант A. Kafka: задание — команда в топике `flt.<module>.jobs.<job>.v1`, консьюмер FastStream в роли `worker`

- **Описание**: модуль создаёт запись задания в своей таблице (`<module>.jobs`: `id`, `kind`, `status` `queued|running|succeeded|failed`, `progress`, `payload`, `result`, `error`, `run_after`, `attempts`, `version`) и в той же транзакции — команду в outbox; воркер читает команду, обновляет статус, публикует прогресс в WebSocket-канал, по завершении — доменное событие. Отложенные задания: периодическая задача ставит в outbox команды с наступившим `run_after`. Задания длиннее 5 минут разбиваются на шаги, каждый шаг — отдельная команда (например, извлечение текста по страницам).
- **Плюсы**:
  - один брокер, одна модель идемпотентности (inbox), одни ретраи и DLQ, один инструмент тестов (`TestKafkaBroker`);
  - consumer group распределяет задания между воркерами; при остановке воркера незавершённое задание доставляется повторно.
- **Минусы**:
  - нет встроенных отложенных и периодических задач — реализуются планировщиком роли `worker`;
  - `max.poll.interval.ms` ограничивает длительность одного сообщения (ставится 10 мин).
- **Масштабирование на N инстансах**: выполнение один раз при N потребителях — consumer group плюс inbox.
- **Выделение модулей в микросервисы**: помогает — топики заданий модуля уезжают с ним.
- **Трудоёмкость и риски**: средняя; планировщик — простой цикл с cron-выражениями под блокировкой.

#### Вариант B. Отдельная система очередей (Celery, arq, Taskiq) на Redis

- **Описание**: задания в Redis, воркеры Celery или arq.
- **Плюсы**:
  - отложенные и периодические задачи из коробки; привычные декораторы.
- **Минусы**:
  - Redis становится хранилищем очереди: по CLAUDE.md потеря Redis допустима только для кэша, лимитов, блокировок и быстрого теста, а потеря очереди заданий — нет;
  - вторая модель доставки и ретраев рядом с Kafka, второй набор тестовых инструментов;
  - события и команды расходятся по разным транспортам, outbox не покрывает задания.
- **Масштабирование на N инстансах**: работает.
- **Выделение модулей в микросервисы**: мешает — у выделенного сервиса две шины.
- **Трудоёмкость и риски**: низкая на старте, долг позже.

### 2.5. Роли запуска монолита из одного образа (OQ-17)

#### Вариант A. Один образ, роль задаётся `APP_ROLE` (`api`, `worker`, `all`, `migrate`, `media_agent`)

- **Описание**: точка входа образа `python -m app` читает `APP_ROLE` (переопределяется аргументом `--role` для `make`). `api`: uvicorn, REST `/api/v1/...`, WebSocket `/ws` и `/ws/agent`, `/v1/health`, `/v1/ready`, `/v1/metrics`, `/api/docs`, `/api/openapi.json`; соединения с Kafka нет. `worker`: FastStream `AsgiFastStream` с консьюмерами всех модулей, relay outbox, планировщик периодических задач; служебный HTTP на порту 8001 — `/v1/health`, `/v1/ready`, `/v1/metrics`, `/asyncapi/kafka`. `all`: `api` + `worker` в одном процессе — локальная разработка и pytest (`TestKafkaBroker`). `migrate`: `make migrate` (`alembic -n <module> upgrade head` по каждому модулю реестра — ADR-002), затем идемпотентная инициализация инфраструктуры: создание топиков Kafka по декларациям модулей, `storage-init` (бакеты `flt-<module>`, политики, lifecycle-правила — ADR-007), шаблоны индексов OpenSearch и коллекции Qdrant (ADR-014); выход с кодом 0. `media_agent` (этап 6, ADR-015): процесс `livekit-agents` — AI-преподаватель в комнатах LiveKit; HTTP не обслуживает, кроме служебного порта 8001 с `/v1/health`, `/v1/ready`, `/v1/metrics`. Readiness: `api` — PostgreSQL доступен; `worker` — PostgreSQL и Kafka доступны; Redis в readiness не входит (ADR-003, правило 8). Остановка: `SIGTERM` → `api` перестаёт принимать соединения, активным стримам даётся `SHUTDOWN_GRACE_SECONDS=30` на завершение (ADR-009), затем WebSocket закрываются кодом 1012 (клиенты переподключаются); `worker` — прекращает poll, дорабатывает текущее сообщение, отпускает блокировки; `terminationGracePeriodSeconds=40`.
- **Плюсы**:
  - один образ, один код; `api` и `worker` масштабируются независимо (OQ-30 — HPA по ролям);
  - отказ Kafka не влияет на REST и WebSocket;
  - локальная разработка не усложняется (`all`).
- **Минусы**:
  - две группы инстансов в docker-compose и Helm; метрики и логи помечаются ролью.
- **Масштабирование на N инстансах**: `api` — N = 3 за HAProxy; `worker` — 2 реплики, consumer group и блокировки распределяют работу; `migrate` — ровно один запуск на обновление.
- **Выделение модулей в микросервисы**: нейтрально — выделенный сервис получает те же роли.
- **Трудоёмкость и риски**: средняя: `main.py` превращается в фабрику по роли; `uvi_run.py` заменяется.

#### Вариант B. Один процесс со всеми ролями (как в boilerplate)

- **Описание**: консьюмеры, relay и планировщик в каждом процессе API.
- **Плюсы**:
  - проще конфигурация.
- **Минусы**:
  - нагрузка консьюмеров (обработка материалов, генерация программ) конкурирует с задержкой REST (p95 ≤ 300 мс, OQ-13);
  - N инстансов = N consumer-ов на каждый топик, даже когда заданий нет; при масштабировании API растёт число консьюмеров и наоборот;
  - отказ Kafka ломает readiness всех инстансов.
- **Масштабирование на N инстансах**: работает, но ролям нельзя задать разные ресурсы.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: нулевая сейчас; переделка позже под нагрузкой.

#### Вариант C. Отдельные образы для API и воркера

- **Описание**: два Dockerfile.
- **Плюсы**:
  - меньший образ API.
- **Минусы**:
  - дублирование сборки и публикации; расхождение версий между образами.
- **Масштабирование на N инстансах**: как A.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: лишняя сборка в CI.

### 2.6. Синхронные вызовы между модулями и внедрение зависимостей

#### Вариант A. `Protocol` в публичном API модуля, минимальный контейнер shared kernel, `Depends` как адаптер

- **Описание**: публичный API модуля (подпакет `app/modules/<module>/public` по ADR-002) экспортирует `typing.Protocol` сервисов (`IdentityService`), Pydantic-DTO и классы событий. Shared kernel даёт контейнер `container.register(IdentityService, factory)` / `container.resolve(IdentityService)`; модуль регистрирует реализацию при подключении (`register_module(app, container)`). В HTTP-контроллерах реализация приходит через `Depends(provide(IdentityService))` (фабрика `get_identity_service()` из ADR-002 — обёртка над `container.resolve`), в консьюмерах Kafka и планировщике — через `container.resolve`. Тесты подменяют `container.override(IdentityService, fake)`. Правила: вызывающий не передаёт свою сессию SQLAlchemy — вызываемый открывает свою (ADR-003, раздел 3, правило 1); прямой вызов допустим для чтения и синхронных проверок (есть ли пользователь, разрешён ли провайдер, какой у ученика рабочий уровень); изменение данных другого модуля через прямой вызов запрещено — публикуется событие или команда в топик заданий модуля-владельца.
- **Плюсы**:
  - одна точка подмены для всех ролей; `Depends` остаётся идиомой FastAPI;
  - при выделении модуля реализация `Protocol` заменяется HTTP-клиентом или Kafka-адаптером без изменения вызывающих.
- **Минусы**:
  - собственный контейнер (около 100 строк) вместо библиотеки; граф зависимостей проверяется архитектурным тестом на циклы (ADR-002).
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: помогает.
- **Трудоёмкость и риски**: низкая.

#### Вариант B. Только `Depends` FastAPI

- **Описание**: сервисы других модулей — через `Depends()` в контроллерах, как в boilerplate.
- **Плюсы**:
  - без нового кода.
- **Минусы**:
  - `Depends` не работает в relay outbox, планировщике и в `container`-независимых консьюмерах FastStream вне FastAPI (роль `worker` работает без FastAPI-приложения);
  - `Depends(ConcreteService)` импортирует реализацию чужого модуля — нарушение границы.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: мешает.
- **Трудоёмкость и риски**: низкая сейчас.

#### Вариант C. Библиотека `dependency-injector`

- **Описание**: декларативные контейнеры с провайдерами и wiring.
- **Плюсы**:
  - зрелая библиотека, конфигурация и ресурсы из коробки.
- **Минусы**:
  - wiring по модулям, собственный синтаксис, ещё одна зависимость; возможности избыточны для 20 интерфейсов.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: средняя кривая обучения.

## 3. Решение

- **Выбран**: 2.1 — A; 2.2 — A; 2.3 — A; 2.4 — A; 2.5 — A; 2.6 — A.
- **Решение**: REST — роутер FastAPI на модуль с префиксом `/api/v1/<module>`; WebSocket — один эндпоинт `/ws` на роли `api` с мультиплексированием каналов `<module>.<channel>` и доставкой событий между инстансами через Redis pub/sub; Kafka — FastStream, топики `flt.<module>.<event>.v<N>`, публикация только через transactional outbox в схеме модуля с relay в роли `worker`, идемпотентность через таблицу `processed_events`, ретраи в процессе и dead letter topic `<topic>.dlq`, фоновые задания — команды в топиках `flt.<module>.jobs.<job>.v<N>`; синхронные вызовы между модулями — через `Protocol` публичного API и контейнер shared kernel; монолит запускается из одного образа в ролях `api`, `worker`, `all`, `migrate`, `media_agent`, заданных `APP_ROLE`.
- **Обоснование**: вариант A каждого подвопроса использует уже принятые компоненты (FastAPI, FastStream, Redis, HAProxy) без новых контейнеров, изолирует REST и WebSocket от отказов Kafka, сохраняет порядок событий по агрегату и даёт независимое масштабирование ролей.
- **Отвергнуты**:
  - 2.1 B — кратное число соединений и дублирование аутентификации.
  - 2.2 B — несовместимые изменения схем без нового топика ломают консьюмеров.
  - 2.3 B — нарушение порядка событий агрегата; 2.3 C — два контейнера JVM ради задержки, которая не требуется.
  - 2.4 B — очередь в Redis противоречит политике потери Redis, вторая шина рядом с Kafka.
  - 2.5 B — консьюмеры конкурируют с задержкой REST; 2.5 C — дублирование сборки.
  - 2.6 B — не работает вне FastAPI; 2.6 C — избыточно.

### 3.1. Правило выбора транспорта

| Ситуация | Транспорт |
|---|---|
| Фронтенд или внешний клиент запрашивает или изменяет данные и ждёт ответа | REST `/api/v1/<module>/...` (конвенции — SYS-03) |
| Сервер должен доставить фронтенду данные без запроса: стриминг LLM, прогресс задания, уведомление, событие класса, присутствие | WebSocket `/ws`, канал модуля-владельца |
| Модулю нужны данные другого модуля для ответа прямо сейчас (чтение, проверка) | прямой вызов `Protocol` публичного API в процессе, своя транзакция у вызываемого |
| Модуль должен сообщить о свершившемся факте; другим модулям нужно отреагировать | доменное событие через outbox в `flt.<module>.<event>.v<N>` |
| Модулю нужно, чтобы другой модуль изменил свои данные | событие (если факт уже произошёл) или команда в топик заданий модуля-владельца `flt.<owner>.jobs.<job>.v<N>`; прямой вызов на запись запрещён |
| Задача длинная (> 2 с) или не требует немедленного ответа: генерация программы, обработка материала, скачивание модели | фоновое задание: запись в `<module>.jobs` + команда через outbox; прогресс — WebSocket |
| Повторяющаяся задача по расписанию: уборка outbox, напоминания заучивания, пересчёт лимитов | планировщик роли `worker` под распределённой блокировкой |
| HTTP между модулями внутри монолита | запрещён; появляется только как реализация `Protocol` после выделения модуля |

### 3.2. REST

- Каждый модуль подключает `APIRouter(prefix="/api/v1/<module>", tags=["<module>"])`; роутер монолита объединяет их. Монолит обслуживает путь `/api/v1/...` сам, HAProxy путь не переписывает, `ROOT_PATH` не используется (ADR-012), поэтому OpenAPI совпадает с публичными URL. Единственное исключение из правила «префикс = имя модуля» — `/api/v1/auth/*`, принадлежащий модулю `identity` (OQ-12, оформляется в SYS-03). OpenAPI отдаётся на `/api/docs` и `/api/openapi.json` (снаружи закрыты ACL HAProxy, на local и dev открываются переменной `FLT_EXPOSE_DOCS` — ADR-012). Служебные пути `/v1/health`, `/v1/ready`, `/v1/metrics` (api на `:8000`, worker на `:8001`) и `/asyncapi/kafka` остаются вне `/api` и наружу не публикуются (ADR-010).
- Имя модуля в пути — осознанно: при выделении модуля HAProxy переключает `/api/v1/<module>/*` на новый сервис без изменения клиентов.
- Ошибки — `ErrorResponseV1`; версионирование, пагинация, идентификаторы, время, локаль — SYS-03.

### 3.3. WebSocket

- Эндпоинт `/ws` на роли `api`. Отдельный эндпоинт `/ws/agent` резервируется для локального агента (ADR-008) с тем же envelope и собственной аутентификацией агента.
- Аутентификация завершается до первой подписки: способ передачи токена — ADR-006 (cookie при handshake или первое сообщение `auth` с токеном); соединение без аутентификации в течение 5 с закрывается кодом 4401; анонимный быстрый тест (VIS-03) подключается с идентификатором анонимной сессии из Redis.
- Envelope сообщения в обе стороны:

```json
{
  "type": "llm_gateway.stream.delta",
  "correlation_id": "01999d1e-7c3a-7b2e-9f0a-2b7f1d8e4c55",
  "channel": "llm_gateway.stream:01999d1e-7c3a-7b2e-9f0a-2b7f1d8e4c55",
  "seq": 42,
  "ts": "2026-10-10T12:00:00.123Z",
  "payload": {"text": "Hel"}
}
```

  Поля конверта: `type` (строка `<module>.<name>` или тип shared kernel), `correlation_id` (UUID; у команд клиента генерирует клиент, у событий сервера — повторяет команду или равен `request_id`), `channel` (канал, к которому относится сообщение; у типов shared kernel — `null`), `seq` (целое, с 0), `ts` (время сервера, ISO 8601 UTC), `payload` (объект по схеме типа). Типы shared kernel: клиент → сервер `auth`, `subscribe`, `unsubscribe`, `ping`; сервер → клиент `ack`, `error`, `pong`, `event`, `<module>.job.progress` (прогресс фонового задания модуля: `payload = {job_id, stage, percent, message_key}`, не чаще 1 сообщения в секунду на задание; завершение — `<module>.job.completed` с `result_ref` и `<module>.job.failed` с `code` — ADR-009). Типы модулей — `<module>.<name>`, их схемы — Pydantic-модели в публичном API модуля и AsyncAPI модуля (SYS-04). `seq` монотонен в пределах канала и соединения; `correlation_id` связывает команду, её события и записи в логах (`request_id` в ADR-010).
- **Бинарные кадры** (аудио — ADR-009, зарезервировано для агента — ADR-008): бинарное WebSocket-сообщение с 9-байтовым заголовком — тип кадра 1 байт (`0x01` аудио клиента, `0x02` аудио сервера, остальные значения резервируются в SYS-04), `stream_id` 4 байта (big-endian, выдаётся сервером в текстовом сообщении открытия потока), `seq` 4 байта (big-endian, с 0 в пределах `stream_id`); далее — данные. Бинарные кадры принадлежат потоку, открытому текстовым сообщением, и без него отбрасываются.
- **Коды закрытия**: `1011` — внутренняя ошибка или мёртвый клиент (`send` не завершился за `WS_SEND_TIMEOUT_SECONDS`, ADR-009); `1012` — остановка инстанса, клиент переподключается сразу; `1013` — переполнение исходящей очереди (`WS_OUTBOX_MAX`, ADR-009), клиент переподключается и восстанавливает состояние по REST; `4401` — нет аутентификации в течение 5 с или сессия отозвана (ADR-006); `4429` — превышен лимит соединений на пользователя. Код `4426` (`AGENT_UPDATE_REQUIRED`) используется только на `/ws/agent` (ADR-008).
- Подписка: shared kernel вызывает `can_subscribe(user, channel)` обработчика модуля; при отказе — `error` с кодом `forbidden`. Входящие команды модуля (например, `llm_gateway.completion.request`) передаются обработчику модуля через контейнер (п. 2.6).
- Доставка между инстансами: инстанс держит таблицу «канал → локальные соединения»; при первой локальной подписке выполняет `SUBSCRIBE ws:channel:<channel>` в Redis (отдельное соединение `PubSub`), при последней отписке — `UNSUBSCRIBE`. Публикация из любого инстанса и роли: `ws_publisher.publish(channel, type, payload)` → `PUBLISH ws:channel:<channel> <envelope>`; дополнительно **канал пользователя** `ws:user:<user_id>` для адресных событий (уведомления, прогресс заданий, отзыв сессии — ADR-006). Для запросов «инстанс → инстанс» с ответом (пересылка к локальному агенту, ADR-008) используется пара каналов: входящий канал держателя соединения и **канал ответа** `<module>:reply:<request_id>`, на который запрашивающий инстанс подписывается до публикации запроса (для агента — `local_runtime:agent:<agent_id>:inbox` и `local_runtime:reply:<request_id>`, ADR-008). Каналы `ws:*` принадлежат shared kernel, каналы `<module>:*` — модулю (префикс по ADR-003). Pub/sub не хранит сообщения (ADR-003, раздел 3, правило 6).
- Переподключение: клиент (общий WebSocket-клиент shared-слоя фронтенда, ADR-005) переподключается с экспоненциальной задержкой 1–30 с, аутентифицируется, переподписывается на свои каналы. Восстановление состояния: события WebSocket — уведомления, а не источник истины; у каждого канала есть REST-эндпоинт текущего состояния, который клиент вызывает после переподключения (например, `GET /api/v1/learning_plan/jobs/{id}` для прогресса задания). Незавершённый стрим LLM не возобновляется: модуль-владелец сохраняет частичный ответ с `interrupted = true`, клиент читает его по REST и повторяет запрос с новым `correlation_id` (ADR-009).
- Heartbeat: сервер отправляет `ping` каждые 30 с, закрывает соединение без `pong` за 60 с; таймаут туннеля HAProxy — 1 ч (ADR-012). Лимит соединений на пользователя — 5 (ключ shared kernel `shared_kernel:ws:conns:<user_id>`, TTL 60 с с продлением; префикс — по ADR-003), остальные закрываются кодом 4429.
- Остановка инстанса: активным стримам даётся `SHUTDOWN_GRACE_SECONDS=30` (ADR-009), затем закрытие соединений кодом 1012 (Service Restart); клиент переподключается без ожидания.

### 3.4. Kafka

- **Топики**: `flt.<module>.<event>.v<N>` для событий, `flt.<module>.jobs.<job>.v<N>` для команд заданий, `<topic>.dlq` для необработанных сообщений. Имена событий — английский, snake_case, прошедшее время; команд — инфинитив (`extract_text`). Модуль публикует только в свои топики. Партиций по умолчанию 6, `replication.factor` — 1 в docker-compose, 3 в Kubernetes при трёх брокерах (SYS-11); retention событий — 7 суток, DLQ — 30 суток. Топики создаются ролью `migrate` по декларациям модулей (`topics.py` в публичном API модуля: имя, партиции, retention); `KAFKA_AUTO_CREATE_TOPICS_ENABLE` — только на стенде local. Это решение закрывает OQ-24 (вариант 2 рекомендации); SYS-04 фиксирует его как требование.
- **Envelope события** (тело — JSON, схема — Pydantic-модель события в публичном API модуля):

```json
{
  "event_id": "01999d1e-7c3a-7b2e-9f0a-2b7f1d8e4c55",
  "event_type": "identity.user_registered",
  "event_version": 1,
  "occurred_at": "2026-10-10T12:00:00Z",
  "producer": "identity",
  "aggregate_id": "01999d1e-7c3a-7b2e-9f0a-2b7f1d8e4c56",
  "correlation_id": "01999d1e-7c3a-7b2e-9f0a-2b7f1d8e4c57",
  "causation_id": null,
  "payload": {"user_id": "01999d1e-7c3a-7b2e-9f0a-2b7f1d8e4c56", "locale": "ru"}
}
```

  Заголовки Kafka: `event_id`, `event_type`, `content_type=application/json`, `request_id` (ID запроса из контекста публикатора — ADR-010; консьюмер привязывает его к своим логам), `traceparent` (middleware boilerplate). Ключ сообщения — `aggregate_id`. Совместимые изменения (новые необязательные поля) увеличивают `event_version`; несовместимые — новый топик `.v<N+1>`. Контрактный тест сверяет AsyncAPI, который генерирует FastStream, с `Analytics/Specs/<module>/api/asyncapi.yaml`.
- **Outbox**: таблица в схеме каждого модуля, создаётся миграцией модуля из декларации shared kernel:

```sql
CREATE TABLE <module>.outbox (
  id             uuid PRIMARY KEY,                  -- UUID v7 = event_id
  topic          text NOT NULL,
  key            text NULL,                         -- aggregate_id
  event_type     text NOT NULL,
  event_version  integer NOT NULL,
  headers        jsonb NOT NULL DEFAULT '{}'::jsonb,
  body           jsonb NOT NULL,                    -- envelope целиком
  occurred_at    timestamptz NOT NULL,
  published_at   timestamptz NULL,
  attempts       integer NOT NULL DEFAULT 0,
  last_error     text NULL
);
CREATE INDEX ix_<module>_outbox_unpublished ON <module>.outbox (id) WHERE published_at IS NULL;
```

  Запись — только через `OutboxPublisher.publish(session, event)` shared kernel в сессии вызывающего; прямой `broker.publish` вне shared kernel запрещён import-linter (исключение — тесты). Relay — п. 2.3 A. Публикация в Kafka с `acks=all`, `enable.idempotence=true`.
- **Консьюмеры и идемпотентность**: `group_id = "flt.<module>.<handler>"` (например `flt.dictionary.index_entries`), по группе на обработчик. Обработчик выполняется в одной транзакции модуля: `INSERT INTO <module>.processed_events (consumer, event_id, processed_at) ... ON CONFLICT DO NOTHING` — при конфликте сообщение пропускается; затем бизнес-изменение и собственные события в outbox; commit; затем ack Kafka (`AckPolicy.REJECT_ON_ERROR`, ack после commit). Таблица:

```sql
CREATE TABLE <module>.processed_events (
  consumer     text NOT NULL,
  event_id     uuid NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer, event_id)
);
```

  Строки старше 30 суток удаляет периодическая задача.
- **Ретраи и DLQ**: ошибка обработчика → повтор в процессе с задержками 1 с, 5 с, 25 с (3 попытки); после исчерпания — публикация исходного сообщения в `<topic>.dlq` с заголовками `error`, `error_type`, `attempts`, `consumer`, `original_topic`, `failed_at` и ack исходного (партиция не блокируется). Ошибки валидации схемы (`ValidationError`) — в DLQ без ретраев. Разбор DLQ: команда `python -m app dlq replay --topic <topic> [--event-id ...]` роли `worker` под ручным запуском администратора; метрика `flt_kafka_dlq_messages_total{topic}` и алерт (ADR-010). Callback-топики boilerplate (`KAFKA_ERROR_TOPIC_BY_SOURCE`) заменяются этой схемой.
- **Фоновые задания и планировщик**: п. 2.4 A. Планировщик — цикл в роли `worker`: каждые 10 с проверяет расписание задач (`cron`-выражение в декларации модуля `schedules.py`), берёт блокировку `shared_kernel:lock:schedule:<module>.<task>` с TTL = интервал задачи, выполняет; отсутствие блокировки — пропуск без ошибки; журнал запусков хранится в схеме модуля-владельца задачи (`<module>.scheduled_runs`), у shared kernel собственных таблиц нет. Периодическая задача обязана быть идемпотентной.

### 3.5. Роли запуска

| Роль | Что входит | Порт | Readiness | docker-compose | Helm |
|---|---|---|---|---|---|
| `api` | uvicorn: REST `/api/v1/*`, WebSocket `/ws` и `/ws/agent`, `/v1/health`, `/v1/ready`, `/v1/metrics`, `/api/docs`, `/api/openapi.json`; подписка на Redis pub/sub; Kafka не подключается | 8000 | PostgreSQL доступен, приложение инициализировано | сервис `api`, `deploy.replicas: 3` (или `--scale api=3`), за HAProxy | Deployment `flt-api` за headless Service `flt-api` (ADR-012), `replicas: 2` минимум, HPA — OQ-30 |

- Роль задаётся переменной окружения `APP_ROLE` (значения `api`, `worker`, `all`, `migrate`, `media_agent`; по умолчанию `all` только на стенде local, на остальных стендах обязательна). Точка входа образа: `CMD ["python", "-m", "app"]`; `make dev` → `all`, `make run` → `migrate` затем `api`. `uvi_run.py` и `MIGRATE_ON_START` удаляются (ADR-003); uvicorn запускается с `proxy_headers=True` и `forwarded_allow_ips` из настроек (ADR-012).
- `KAFKA_GROUP_ID` из настроек boilerplate перестаёт быть единым на сервис: группа вычисляется из модуля и обработчика; `KAFKA_CLIENT_ID = flt-<role>-<instance_id>`.
- Поле `role` добавляется в JSON-логи и метки метрик (ADR-010); `instance_id` = `HOSTNAME`.
- Остановка — п. 2.5 A. E2E этапа 1 Г.11 останавливает один инстанс `api` и один `worker` посреди сценария.

- **Границы решения**: конвенции REST (пагинация, ошибки, локаль) — SYS-03; полный протокол WebSocket и форматы AsyncAPI — SYS-04; аутентификация WebSocket — ADR-006; семантика стрима LLM, сохранение частичного ответа и голос — ADR-009; протокол локального агента — ADR-008; маршруты, таймауты и health-check HAProxy — ADR-012; число брокеров Kafka, конфигурация compose-реплик и Helm — SYS-11; раскладка пакетов `outbox`, `inbox`, `ws`, `container` в shared kernel — ADR-002.

## 4. Последствия

### 4.1. Положительные

- Событие публикуется ровно тогда, когда зафиксировано изменение данных; порядок по агрегату сохраняется; повтор доставки не меняет результат.
- REST и WebSocket не зависят от Kafka; консьюмеры не влияют на задержку API; роли масштабируются раздельно.
- Клиент держит одно соединение WebSocket; событие доходит независимо от инстанса, на котором возникло.
- Фоновые задания, события и команды используют одну модель доставки, одни тесты (`TestKafkaBroker`) и один стенд на N инстансах.
- Выделение модуля: топики, outbox, inbox и `Protocol` уже разделены по модулям; меняется только реализация интерфейса.

### 4.2. Отрицательные и их смягчение

| Последствие | Смягчение |
|---|---|
| Задержка события ≈ 200–300 мс из-за опроса outbox | достаточно для всех сценариев BRD; при потребности — `LISTEN/NOTIFY` как сигнал relay без изменения контракта |
| Опрос outbox каждого модуля нагружает PostgreSQL | частичный индекс по непубликованным строкам, пауза с ростом до 2 с при простое, уборка опубликованных строк |
| In-process ретраи блокируют партицию до 31 с | три попытки с короткими паузами; долгие сбои уходят в DLQ; при потребности — retry-топики по решению SYS-04 |
| Pub/sub не хранит события: при разрыве соединения часть уведомлений теряется | REST-эндпоинт состояния на каждый канал; частичный ответ LLM сохраняется модулем-владельцем с `interrupted = true`, стрим не возобновляется (ADR-009); `seq` позволяет клиенту заметить пропуск |
| Две группы инстансов в развёртывании, служебный порт воркера | шаблоны compose и Helm в SYS-11; одна `values`-секция на роль |
| Собственный контейнер зависимостей вместо библиотеки | около 100 строк, покрыт тестами; граф проверяется на циклы архитектурным тестом |
| Имя модуля в URL REST фиксирует карту модулей наружу | переименование модуля — редкое событие; при необходимости старый префикс остаётся алиасом в HAProxy на один релиз |
