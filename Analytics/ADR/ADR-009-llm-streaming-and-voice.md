## 1. Контекст

- **Проблема**: ответ LLM генерируется секундами и десятками секунд; ученик должен видеть текст по мере генерации, уметь прервать его, а платформа — учитывать расход токенов и работать на N инстансах без состояния. Источников потока три: внешний провайдер (OpenAI-совместимый SSE, SYS-08), локальная модель через агента на компьютере ученика (второе WebSocket-соединение, ADR-008) и длительные фоновые генерации (программа обучения STU-18, обработка материалов STU-27), которые выполняет воркер через Kafka. На этапе 5 добавляется голос: речь ученика должна распознаваться потоково, ответ AI-преподавателя — озвучиваться по мере генерации, аватар — синхронизировать мимику (STU-29). Нужно выбрать транспорт для текста и для голоса и определить, где исполняется запрос к LLM.
- **Почему сейчас**: этап 1 Г.6 (`llm_gateway`: интерфейс провайдера, один OpenAI-совместимый провайдер, стриминг на фронтенд через WebSocket) и Г.11 (E2E: стриминговый ответ заглушки LLM на N инстансах с остановкой инстанса посреди сценария). Решение о голосе нужно сейчас, потому что оно определяет, нужен ли медиасервер до этапа 6 и как проектировать модуль `speech`.
- **Ограничения**:
  - CLAUDE.md, «Взаимодействие»: стриминг ответов LLM — WebSocket, который обслуживает сам монолит; события между инстансами — Redis pub/sub; Kafka — для долгих задач и развязки модулей; локальный агент связывается исходящим WebSocket через HAProxy;
  - CLAUDE.md, «Масштабирование и состояние»: клиент может быть подключён к любому инстансу; sticky-сессии не используются; инстанс можно остановить в любой момент;
  - CLAUDE.md, «LLM-агностичность»: любая функция работает с любым провайдером, внешним или локальным; то же для провайдеров речи;
  - ADR-015 (по заданию): LiveKit — для групповых занятий с этапа 6; для голоса один на один решение принимается здесь;
  - OQ-13: 50 одновременных LLM-стримов, 300 WebSocket-соединений; p95 REST ≤ 300 мс без обращения к LLM; время первого токена не нормируется, нормируется накладная задержка платформы;
  - 152-ФЗ и OQ-35: аудио по умолчанию не сохраняется, передача голоса зарубежным провайдерам — по отдельному согласию.
- **Если не решить**: Г.6 и Г.11 реализуются без контракта сообщений; агент (ADR-008) и голос (этап 5) потребуют второго транспорта и переделки клиента.
- **Ссылки**: CLAUDE.md «Взаимодействие», «Масштабирование и состояние», «Технологический стек» (синтез и распознавание речи, аватар); SDD_plan.md этап 1 А.9, Г.6, Г.11, этап 5 STU-28; OQ-13, OQ-26, OQ-35; глоссарий: «Стриминг», «LLM-шлюз», «Локальный агент», «Синтез речи (TTS)», «Распознавание речи (STT)», «Медиасервер».

## 2. Рассматриваемые варианты

### 2.1. Транспорт текстового стрима

#### Вариант A. Server-Sent Events: `POST` запроса, ответ `text/event-stream` с того же инстанса

- **Описание**: клиент отправляет `POST /api/v1/lessons/{id}/messages`, инстанс держит HTTP-ответ открытым и пишет события `delta` по мере получения от провайдера; отмена — `AbortController` (разрыв соединения) или отдельный `POST …/cancel`.
- **Плюсы**:
  - проще на сервере: нет мультиплексирования, стрим живёт в одном обработчике;
  - автоматическое переподключение `EventSource` (не применимо к `POST` — нужен `fetch` с ручным чтением).
- **Минусы**:
  - второй долгоживущий канал рядом с WebSocket, который и так нужен для уведомлений, прогресса заданий и событий класса: два набора таймаутов HAProxy, два механизма аутентификации и переподключения;
  - односторонний: отмена, подтверждения и голос требуют отдельных запросов или другого транспорта;
  - агент (ADR-008) всё равно общается по WebSocket — для локальных моделей получается SSE наружу и WebSocket внутрь;
  - лимит 6 соединений HTTP/1.1 на origin в браузере при нескольких одновременных стримах (через HAProxy с HTTP/2 снимается, но зависит от ADR-012).
- **Масштабирование на N инстансах**: стрим привязан к инстансу, принявшему `POST`; фоновые генерации с воркера не доставляются (нужен отдельный канал);
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая для одного случая, растёт с каждым новым типом стрима.

#### Вариант B. WebSocket: монолит ретранслирует поток провайдера сообщениями `start` / `delta` / `end` / `error` с `correlation_id` (выбран)

- **Описание**: единственное WebSocket-соединение `/ws` (ADR-004); запрос и отмена — сообщения клиента; стрим — последовательность сообщений сервера с `correlation_id` и `seq`; тот же канал несёт прогресс фоновых заданий и события от агента.
- **Плюсы**:
  - один канал, одна аутентификация (ADR-006), одно переподключение (ADR-004/ADR-005), одна конфигурация таймаутов в HAProxy;
  - двунаправленный: отмена, подтверждения, голосовые бинарные кадры — в том же соединении;
  - симметричен агенту: монолит — ретранслятор между двумя WebSocket;
  - стрим от воркера (фоновая генерация) доставляется через Redis pub/sub в то же соединение.
- **Минусы**:
  - мультиплексирование и обратное давление реализуются вручную (раздел 3.4);
  - нет автоматического возобновления стрима при переподключении: стрим привязан к инстансу (раздел 3.5).
- **Масштабирование на N инстансах**: интерактивный стрим живёт на инстансе соединения, состояние в памяти — только в рамках одного стрима (не между запросами, допустимо по CLAUDE.md: это обработчик одного запроса); фоновые — через Redis pub/sub на любой инстанс; потеря инстанса — стрим прерывается, клиент повторяет.
- **Выделение модулей в микросервисы**: помогает — WebSocket-инфраструктура в shared kernel, модули публикуют события в каналы Redis; при выделении `llm_gateway` канал остаётся тем же.
- **Трудоёмкость и риски**: средняя; риск — потеря сообщений pub/sub (at-most-once), смягчается тем, что через pub/sub идут только грубые события прогресса, а не токены (раздел 3.2).

#### Вариант C. WebRTC data channel (через LiveKit) для текста и аудио

- **Описание**: клиент подключается к LiveKit, текст идёт по data channel, аудио — по медиатреку; монолит участвует как агент LiveKit.
- **Плюсы**:
  - один транспорт для текста и голоса с минимальной задержкой.
- **Минусы**:
  - медиасервер и TURN нужны с этапа 1 вместо этапа 6; медиатрафик мимо HAProxy (UDP) — конфигурация VPS и Kubernetes усложняется до появления голоса;
  - текстовые уведомления и прогресс заданий не имеют отношения к WebRTC — WebSocket всё равно нужен;
  - локальный агент на Python через WebRTC — лишняя сложность (ADR-008 выбрал WebSocket).
- **Масштабирование на N инстансах**: инстанс-агент LiveKit — отдельная роль процесса (ADR-004) с собственным масштабированием.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: высокая на этапе 1.

### 2.2. Где исполняется запрос к LLM

#### Вариант D. Всегда на инстансе, держащем WebSocket клиента (прямой стрим)

- **Описание**: обработчик WebSocket вызывает публичный API `llm_gateway` (async-генератор) в том же процессе и отправляет дельты в сокет.
- **Плюсы**: минимальная задержка (нет брокера между провайдером и клиентом); отмена — отмена `asyncio.Task`; usage приходит в том же генераторе.
- **Минусы**: длительные генерации (минуты) гибнут при остановке инстанса и при уходе клиента; роль `api` несёт нагрузку генерации (ожидание ввода-вывода, не CPU).
- **Масштабирование на N инстансах**: равномерно по соединениям; остановка инстанса прерывает его стримы.
- **Выделение модулей в микросервисы**: `llm_gateway` как сервис будет вызываться по gRPC/WebSocket-стриму — интерфейс async-генератора сохраняется.
- **Трудоёмкость и риски**: низкая.

#### Вариант E. Всегда через Kafka: задание воркеру, дельты обратно через Redis pub/sub

- **Описание**: каждый запрос — задание в Kafka; воркер стримит от провайдера и публикует дельты в Redis; инстанс соединения пересылает клиенту.
- **Плюсы**: генерация переживает уход клиента; роль `api` разгружена; единый путь для интерактивных и фоновых запросов.
- **Минусы**: задержка Kafka (десятки миллисекунд на старт) и два дополнительных прыжка на каждую дельту; Redis pub/sub — at-most-once: потеря дельты требует повторной синхронизации; отмена — ещё одно сообщение Kafka с задержкой; каждая дельта — публикация в Redis (50 стримов × 20 дельт/с = 1000 публикаций/с — приемлемо, но без пользы для интерактивного случая).
- **Масштабирование на N инстансах**: воркеры масштабируются отдельно (ADR-004); потеря воркера — задание переназначается, но клиент получает стрим с начала.
- **Выделение модулей в микросервисы**: помогает.
- **Трудоёмкость и риски**: средняя; риск потери и дублирования дельт.

#### Вариант F. Гибрид: интерактивные запросы — вариант D; фоновые генерации — вариант E с грубыми событиями прогресса (выбран)

- **Описание**: правило выбора — раздел 3.2. Интерактивный диалог идёт напрямую; фоновые задания идут через Kafka и сообщают прогресс (не токены) через Redis pub/sub, результат сохраняется в PostgreSQL и читается по REST.
- **Плюсы**: задержка интерактива как в D; долговечность фона как в E; через pub/sub не идут токены — потеря сообщения прогресса безвредна.
- **Минусы**: два пути кода; критерий выбора должен быть зафиксирован в каждом ТЗ.
- **Масштабирование на N инстансах**: как у D и E соответственно.
- **Выделение модулей в микросервисы**: помогает.
- **Трудоёмкость и риски**: средняя.

### 2.3. Ретрансляция к локальному агенту (браузер на инстансе A, агент на инстансе B)

| Вариант | Описание | Плюсы | Минусы |
|---|---|---|---|
| G. Redis pub/sub (выбран) | A публикует запрос в канал агента, B (держит сокет агента) пересылает агенту; дельты от агента B публикует в канал корреляции, A пересылает браузеру. Реестр «агент → инстанс» в Redis с TTL по heartbeat | не нужна связь инстанс–инстанс; любой инстанс равноправен; при падении B агент переподключается к другому инстансу и обновляет реестр | каждая дельта проходит через Redis (задержка < 1 мс в одной сети); at-most-once |
| H. Адресная маршрутизация инстанс → инстанс | A по реестру находит B и открывает к нему прямое HTTP/WebSocket-соединение | дельты без Redis | сеть между инстансами и их адресация (Service per pod, в docker-compose — имена реплик); ломает «любой инстанс равноправен»; HAProxy не участвует; при выделении модулей — ещё один внутренний протокол |
| I. Подключать агент к тому же инстансу, что и браузер | HAProxy направляет агент на инстанс браузера | дельты в одном процессе | требует sticky-маршрутизации по пользователю — запрещено CLAUDE.md |

### 2.4. Голос один на один с AI-преподавателем (STU-28, этап 5)

#### Вариант J. WebSocket с бинарными аудио-кадрами (выбран как базовый)

- **Описание**: браузер захватывает микрофон (`getUserMedia` с `echoCancellation`, `noiseSuppression`), `AudioWorklet` отдаёт PCM16 16 кГц моно кадрами по 20 мс (640 байт), кадры уходят бинарными WebSocket-сообщениями с 9-байтовым заголовком (ADR-004: тип 1 байт, `stream_id` 4 байта, `seq` 4 байта); монолит передаёт их потоковому STT-провайдеру (`speech`), промежуточные и финальные транскрипты возвращает текстовыми сообщениями; ответ LLM по предложениям уходит в потоковый TTS, аудио (PCM16 24 кГц) возвращается бинарными кадрами и проигрывается через `AudioWorklet` с буфером 100–200 мс; VAD на клиенте (`@ricky0123/vad-web`, Silero в WASM) определяет конец фразы и даёт barge-in (клиент шлёт `speech.tts.cancel`, сервер отменяет TTS и LLM).
- **Плюсы**:
  - никакой новой инфраструктуры: тот же `/ws`, та же аутентификация, HAProxy, N инстансов;
  - клиент инициирует соединение по TCP/TLS — нет NAT-траверса, TURN и UDP-портов;
  - работает в мобильных браузерах для STU-34.2 (аудио без экрана);
  - аудио не сохраняется на диске и не проходит через сторонний медиасервер (OQ-35);
  - половинный дуплекс обучения (ученик говорит — преподаватель отвечает) не требует задержки телефонного разговора.
- **Минусы**:
  - TCP: при потере пакетов — head-of-line blocking, задержка растёт (на проводном и Wi-Fi-соединении в РФ потери редки; на мобильной сети возможны паузы);
  - нет встроенного jitter-буфера и адаптивного битрейта — реализуются на клиенте (буфер) и выбором кодека;
  - PCM16: 32 КБ/с вверх и 48 КБ/с вниз; при переходе на Opus (WebCodecs `AudioEncoder`, поддержка в Chrome и Safari 26+) — 6–8 КБ/с, но кодирование на клиенте и декодирование на сервере (`opuslib`/`pyogg`) добавляются позже.
- **Масштабирование на N инстансах**: голосовая сессия, как и текстовый стрим, живёт на инстансе соединения; состояние сессии (контекст диалога) — в PostgreSQL и Redis по правилам `lessons`; остановка инстанса прерывает текущую реплику, клиент переподключается и продолжает занятие.
- **Выделение модулей в микросервисы**: `speech` как сервис получит тот же стриминговый интерфейс (gRPC-стрим вместо async-генератора); сокет остаётся в shared kernel.
- **Трудоёмкость и риски**: средняя; риск — задержка «конец речи → первый звук ответа» выше 1,5 с из-за транспорта; измеряется в ТЗ STU-28 (раздел 3.6).

#### Вариант K. WebRTC через LiveKit (ADR-015) с этапа 5

- **Описание**: браузер подключается к комнате LiveKit; монолит (роль `voice-agent` — в терминах ADR-015 это роль `media_agent`; LiveKit Agents для Python) — участник комнаты: получает аудиотрек ученика, выполняет STT → LLM → TTS, публикует аудиотрек ответа.
- **Плюсы**:
  - UDP/SRTP с jitter-буфером, Opus с адаптивным битрейтом, FEC — лучшая устойчивость к потерям и наименьшая задержка;
  - LiveKit Agents даёт готовые VAD, turn detection, barge-in и интеграции STT/TTS;
  - один и тот же механизм для участия AI-преподавателя в групповых занятиях (ADR-015).
- **Минусы**:
  - медиасервер и TURN появляются на этапе 5 вместо 6: ещё два контейнера, UDP-порты мимо HAProxy, настройка на VPS и в Kubernetes (`hostNetwork` или `NodePort`-диапазон);
  - отдельная роль процесса `media_agent` (ADR-004, ADR-015) с собственным масштабированием и регистрацией в LiveKit нужна уже на этапе 5;
  - аудио проходит через медиасервер — ещё одна точка в описании обработки персональных данных (OQ-35);
  - интеграции STT/TTS внутри LiveKit Agents обходят модуль `speech` и его провайдеров по ключу ученика — противоречит LLM-агностичности, если не писать свои плагины;
  - на мобильном браузере с заблокированным экраном (STU-34.2) WebRTC-соединение живёт не дольше WebSocket.
- **Масштабирование на N инстансах**: процессы роли `media_agent` масштабируются отдельно; LiveKit — свой кластер.
- **Выделение модулей в микросервисы**: роль `media_agent` фактически уже отдельный сервис.
- **Трудоёмкость и риски**: высокая на этапе 5.

## 3. Решение

- **Выбран**: транспорт — вариант B; исполнение — вариант F; ретрансляция к агенту — вариант G; голос один на один — вариант J как базовый с критерием перехода на K.
- **Решение**: ответы LLM стримятся клиенту сообщениями `start` / `delta` / `end` / `error` с `correlation_id` по единственному WebSocket-соединению монолита; интерактивные запросы исполняются на инстансе соединения прямым асинхронным потоком от провайдера, фоновые генерации — воркером через Kafka с событиями прогресса через Redis pub/sub и результатом в PostgreSQL; стрим от локальной модели ретранслируется между инстансами через Redis pub/sub по реестру «агент → инстанс»; голос один на один (этап 5) передаётся бинарными кадрами по тому же WebSocket (PCM16, кодек согласуется при старте сессии), LiveKit используется только для групповых занятий (ADR-015), пересмотр — по измеримому критерию раздела 3.7 (p95 накладной задержки транспорта > 300 мс или > 5 % обрывов сессий) — **подтверждено пользователем 2026-10-10**; потоковые STT и TTS — через провайдеров модуля `speech`.
- **Обоснование**: один канал для всех асинхронных взаимодействий (CLAUDE.md, «Взаимодействие») устраняет дублирование аутентификации, переподключения и таймаутов; прямой стрим даёт минимальную накладную задержку платформы (OQ-13), а Kafka сохраняется там, где важна долговечность; Redis pub/sub уже выбран для доставки между инстансами (CLAUDE.md), и для агента он не добавляет инфраструктуры; голос по WebSocket не требует медиасервера до этапа 6 и укладывается в требования STU-28 и STU-34.2 (сравнение в 2.4).
- **Отвергнуты**:
  - Вариант A (SSE) — второй долгоживущий канал, односторонний, несимметричен агенту.
  - Вариант C (WebRTC для текста) — медиасервер с этапа 1 без пользы для текста.
  - Вариант D (только прямой стрим) — фоновые генерации гибнут с инстансом.
  - Вариант E (только Kafka) — лишняя задержка и at-most-once на каждую дельту интерактива.
  - Вариант H (адресная маршрутизация) — связь инстанс–инстанс ломает равноправие инстансов.
  - Вариант I (агент на инстанс браузера) — sticky-маршрутизация запрещена.
  - Вариант K (LiveKit для голоса 1:1) — медиасервер и роль `media_agent` на этапе 5, обход провайдеров `speech`; остаётся кандидатом при недостижении целевой задержки (раздел 3.7) и остаётся способом участия AI-преподавателя в групповых занятиях (ADR-015).
- **Границы решения**: конверт сообщения, `seq`, heartbeat, переподключение и восстановление состояния каналов по REST — ADR-004/SYS-04 (здесь — только семантика стрима поверх конверта); интерфейс провайдера, возможности моделей, запись расхода токенов, лимиты быстрого теста — SYS-08; формат сообщений агента и его аутентификация — ADR-008; участие AI-преподавателя в групповом занятии и запись занятий — ADR-015 и TCH-08; хранение аудио — OQ-35/SYS-02.

### 3.1. Сообщения стрима (поверх конверта ADR-004; AsyncAPI — `Analytics/Specs/llm_gateway/api/asyncapi.yaml`)

Владелец семантики диалога — модуль, которому принадлежит сценарий (`lessons` для занятий, `assessment` для теста уровня); `llm_gateway` предоставляет примитив стрима и собственный канал для диагностики («проверить соединение» STU-01) и для этапа 1. Имена типов — `<модуль>.<объект>.<событие>` (SYS-04). Все поля — в `payload` конверта; `correlation_id` (UUID) генерирует клиент и повторяет во всех сообщениях стрима.

| Направление | Тип | Поля payload | Назначение |
|---|---|---|---|
| клиент → сервер | `llm_gateway.completion.request` | `messages[]` (роль, текст), `provider_binding_id` (ключ или агент ученика; для быстрого теста — `null` = модель платформы), `llm_model`, `params` (`temperature`, `max_tokens`), `client_ts` | запуск стрима (этап 1: диагностический канал и Г.11; `lessons.message.send` на этапе 2 использует тот же примитив) |
| клиент → сервер | `llm_gateway.completion.cancel` | — | отмена по `correlation_id` |
| сервер → клиент | `llm_gateway.completion.start` | `request_id` (UUID сервера), `provider`, `llm_model`, `started_at` | провайдер принял запрос |
| сервер → клиент | `llm_gateway.completion.delta` | `seq` (с 0, без пропусков в рамках стрима), `kind` (`text`, `tool_call`, `reasoning`), `text`, `tool_call` (объект при `kind = tool_call`) | фрагмент |
| сервер → клиент | `llm_gateway.completion.end` | `finish_reason` (`stop`, `length`, `tool_calls`, `cancelled`, `content_filter`), `usage` (`prompt_tokens`, `completion_tokens`, `total_tokens`, `estimated: bool`), `duration_ms`, `ttft_ms` | завершение; после него сообщений с этим `correlation_id` нет |
| сервер → клиент | `llm_gateway.completion.error` | `code` (`provider_unavailable`, `provider_auth`, `rate_limited`, `context_too_long`, `agent_offline`, `instance_shutdown`, `timeout`, `internal`), `message` (ключ i18n), `retryable: bool`, `partial_seq` (последний доставленный `seq`) | ошибка; завершает стрим |
| сервер → клиент | `<модуль>.job.progress` | `job_id`, `stage`, `percent`, `message_key` | прогресс фоновой генерации (ADR-004, не более 1 сообщения в секунду на задание) |
| сервер → клиент | `<модуль>.job.completed` / `<модуль>.job.failed` | `job_id`, `result_ref` (REST-путь результата) / `code` | завершение фоновой генерации |

Правила: порядок `start → delta* → (end | error)`; клиент собирает текст по `seq` и игнорирует дубликаты; `end` всегда содержит `usage` (при `cancelled` и `error` — оценка, `estimated = true`, по правилам SYS-08); одновременно у одного соединения не более `LLM_MAX_CONCURRENT_STREAMS_PER_CONNECTION=3` стримов, лишние получают `error rate_limited`.

### 3.2. Где исполняется запрос

| Признак | Прямой стрим (вариант D) | Фоновое задание через Kafka (вариант E) |
|---|---|---|
| Пользователь ждёт результат на экране | да | нет или результат нужен независимо от присутствия |
| Ожидаемая длительность | ≤ `LLM_INTERACTIVE_TIMEOUT_SECONDS=120` | дольше или многошаговая |
| Результат при уходе клиента | не нужен (прерывается) | должен сохраниться |
| Примеры | реплики занятия (STU-20–STU-23), демо-урок (VIS-03), словарная статья (STU-12), проверка соединения (STU-01) | генерация программы обучения (STU-18), обработка материалов (STU-27), автоматический подбор модели (STU-04) |
| Как исполняется | обработчик WebSocket на инстансе соединения вызывает `llm_gateway.stream_completion(...)` — async-генератор; дельты пишутся в сокет | роль `api` принимает REST-запрос, создаёт запись задания и публикует задание через outbox (ADR-004); воркер вызывает тот же `stream_completion`, агрегирует текст, публикует прогресс в канал пользователя Redis pub/sub, сохраняет результат в PostgreSQL модуля |
| Отмена | сообщение `cancel` или разрыв соединения → `task.cancel()` → закрытие httpx-стрима провайдера | REST `DELETE .../jobs/{id}` → флаг отмены в PostgreSQL + ключ `<модуль>:job_cancel:<id>` в Redis (TTL 1 ч), воркер проверяет флаг между шагами и каждые 5 с |
| Учёт токенов | `usage` из `end` записывается `llm_gateway` синхронно перед отправкой `end` | записывается воркером по завершении |

Каждое ТЗ, вызывающее LLM, указывает выбранный путь в разделе «Состояние и масштабируемость». Через Redis pub/sub никогда не передаются токены ответа — только события прогресса и завершения (at-most-once допустимо: клиент перечитывает статус задания по REST после переподключения).

### 3.3. Поток от провайдера

- Внешние провайдеры: `httpx.AsyncClient.stream("POST", …)` с SSE-парсером (OpenAI-совместимый формат `data: {…}` и `data: [DONE]`, `stream_options: {"include_usage": true}` для финального `usage`); адаптер провайдера (SYS-08) преобразует чанки в `Delta` dataclass; таймауты: соединение 10 с, первый токен `LLM_TTFT_TIMEOUT_SECONDS=60`, между дельтами 30 с.
- Заглушка для тестов (SYS-10): провайдер `stub` выдаёт детерминированный текст из фикстуры с настраиваемой задержкой между дельтами (`LLM_STUB_DELTA_DELAY_MS`, по умолчанию 20) — на нём идут Г.6, Г.11 и тесты на N инстансах.
- Коалесценция: дельты провайдера накапливаются и отправляются клиенту не чаще чем раз в `LLM_DELTA_FLUSH_MS=40` или по достижении 256 символов, что снижает число WebSocket-кадров без заметной для глаза задержки.

### 3.4. Обратное давление и остановка инстанса

- Отправка в сокет — `await websocket.send_json(...)` в той же корутине, что читает провайдера: медленный клиент замедляет чтение, провайдер держит поток (TCP backpressure). Если `send` не завершается за `WS_SEND_TIMEOUT_SECONDS=15` — соединение считается мёртвым, закрывается с кодом 1011, стрим отменяется.
- Исходящая очередь соединения для событий из Redis pub/sub (прогресс, уведомления) ограничена `WS_OUTBOX_MAX=1000` сообщений; при переполнении соединение закрывается с кодом 1013 (клиент переподключается и восстанавливает состояние по REST). Токены через эту очередь не идут (3.2).
- Остановка инстанса (SIGTERM): инстанс выходит из балансировки (readiness `503`), новые стримы не принимаются (`error instance_shutdown`, `retryable = true`), активные стримы получают до `SHUTDOWN_GRACE_SECONDS=30` на завершение, затем отменяются с `error instance_shutdown`; соединения закрываются кодом 1012 (ADR-004). Клиент переподключается к другому инстансу и повторяет запрос с новым `correlation_id`; модуль-владелец сохраняет частичный ответ как сообщение с флагом `interrupted = true` (3.5). Этот сценарий — обязательный тест Г.11.

### 3.5. Разрыв соединения и частичные ответы

- При разрыве соединения все стримы этого соединения отменяются немедленно (чтобы не платить провайдеру за невидимый ответ). Перед отменой `llm_gateway` отдаёт вызывающему модулю накопленный текст; модуль-владелец (`lessons`) сохраняет его как сообщение с `interrupted = true` и `partial_seq`. После переподключения клиент получает историю по REST и видит прерванную реплику с кнопкой «продолжить» (новая генерация с контекстом).
- Возобновление стрима на другом инстансе не поддерживается: стрим — обработка одного запроса на одном инстансе. Восстановление после переподключения по ADR-004 (переподписка и перечитывание состояния канала по REST) относится к событиям, не к дельтам.

### 3.6. Локальные модели через агента (этап 4, STU-05)

Цепочка: браузер ⇄ (WebSocket) инстанс A ⇄ Redis pub/sub ⇄ инстанс B ⇄ (WebSocket) агент ⇄ LM Studio / llama.cpp (OpenAI-совместимый HTTP на `localhost` ученика).

- Реестр (имена — ADR-008, принят его вариант): при подключении агента инстанс B пишет `local_runtime:agent:<agent_id>:instance` = `{instance_id, user_id, connected_at}` с TTL 90 с (через `ModuleRedis(prefix="local_runtime")`, ADR-003) и продлевает по heartbeat агента каждые 30 с; при закрытии — удаляет. `llm_gateway` спрашивает `local_runtime.is_online(agent_id)` через публичный API.
- Запрос: адаптер `LocalAgentProvider` (реализует тот же интерфейс провайдера SYS-08) вызывает публичный API `local_runtime` (`LocalRuntimeService.stream(agent_id, request)`): сервис подписывается на канал `local_runtime:reply:<request_id>` и публикует запрос в канал `local_runtime:agent:<agent_id>:inbox` (схема «inbox держателя + `<module>:reply:<request_id>`» — ADR-004); B пересылает запрос агенту сообщением `llm.request`; агент стримит `llm.chunk {seq, delta}`, завершает `llm.done {usage}` или `llm.error` (типы агента — ADR-008), B публикует их в канал ответа с `seq`; A получает их как async-генератор и **транслирует в сообщения браузера** `llm_gateway.completion.delta/end/error` (3.1) — агент о протоколе браузера не знает, браузер о протоколе агента тоже. Отмена — `llm.cancel` тем же каналом `inbox`. Таймауты: первая часть — 120 с (загрузка модели в память), простой между частями — 60 с (ADR-008); нет ответа агента — `error agent_offline`; разрыв `seq` — `AGENT_STREAM_LOST` → `error agent_offline` с `retryable = true`.
- Потеря B: агент переподключается через HAProxy к любому инстансу, реестр обновляется; активный стрим прерывается `error agent_offline` (`retryable = true`), клиент повторяет.
- Один стрим через Redis — не более 50 сообщений в секунду после коалесценции; при 50 одновременных стримах (OQ-13) — 2500 сообщений/с, в пределах одного Redis.

### 3.7. Голос один на один (этап 5, STU-28; задел)

- Сессия: `speech.session.start` `{lesson_id, codec: "pcm16" | "opus", sample_rate, stt_provider_binding_id, tts_provider_binding_id, voice}` → сервер отвечает `speech.session.ready {stream_id, codec}`; аудио ученика — бинарные кадры типа `0x01`, аудио преподавателя — `0x02`; текстовые сообщения: `speech.stt.partial {text}`, `speech.stt.final {text, confidence}`, `speech.tts.start {utterance_id, text}`, `speech.tts.end {utterance_id}`, `speech.tts.cancel` (barge-in), `speech.session.end`.
- Конвейер на инстансе соединения: кадры → `STTProvider.stream()` (gRPC/WebSocket провайдера: Yandex SpeechKit, SaluteSpeech, OpenAI Realtime/Whisper-стрим, локальный whisper через агента) → `final` → запрос к LLM (3.1) → разбиение дельт на предложения → `TTSProvider.synthesize_stream()` по предложениям с опережением на одно предложение → кадры клиенту. Интерфейсы провайдеров речи — SYS-08 по аналогии с LLM.
- Кодек на старте этапа 5 — PCM16 (вверх 16 кГц, вниз 24 кГц); Opus через WebCodecs добавляется, если расход трафика на мобильной сети окажется препятствием (измерение в STU-34.2).
- Аватар (STU-29): вместе с `speech.tts.start` сервер передаёт `visemes[]` с таймкодами, если провайдер TTS их отдаёт (Azure, Yandex — нет; тогда клиент строит мимику по амплитуде сигнала); детали — ТЗ STU-29.
- Критерий пересмотра в пользу LiveKit (вариант K): если в ТЗ STU-28 измеренная накладная задержка транспорта (без времени STT, LLM и TTS) «конец речи → первый кадр ответа» на p95 превышает 300 мс или доля прерванных сессий из-за потерь пакетов превышает 5 % на мобильной сети — оформляется новый ADR; до этого LiveKit остаётся инструментом групповых занятий (ADR-015). Критерий подтверждён пользователем 2026-10-10.
- Персональные данные: аудио обрабатывается в памяти процесса в рамках одного запроса и не пишется на диск инстанса; сохранение записей — только по OQ-35; передача голоса зарубежному провайдеру — по согласию `foreign_llm_transfer` (ADR-006, таблица `consents`; расширение вида согласия на речь — SYS-02).

### 3.8. Что реализуется на этапе 1

Г.6: интерфейс провайдера и async-генератор `stream_completion`; провайдеры `stub` и один OpenAI-совместимый (OQ-09); сообщения `llm_gateway.completion.request/cancel/start/delta/end/error`; коалесценция, таймауты, отмена, лимит стримов на соединение, запись `usage` в `llm_gateway.usage_records` (структура — SYS-08); обработка SIGTERM с `instance_shutdown`. Г.11: E2E на N инстансах — стрим заглушки, остановка инстанса посреди стрима, повтор на другом инстансе. Не на этапе 1: фоновые задания LLM (первое — STU-18, этап 4; механизм заданий Kafka сам по себе — Г.4 и ADR-004), ретрансляция к агенту (этап 4), голос (этап 5).

## 4. Последствия

### 4.1. Положительные

- Один канал `/ws` для текста, прогресса, событий агента и голоса; клиент (ADR-005) реализует один механизм подписок.
- Накладная задержка платформы в интерактиве — только процесс инстанса и HAProxy; Kafka и Redis не стоят на пути токенов.
- Фоновые генерации долговечны и не зависят от присутствия клиента.
- Голос появляется на этапе 5 без медиасервера; переход на LiveKit — измеримое, а не априорное решение.
- Агент и внешние провайдеры неразличимы для вызывающих модулей (один интерфейс провайдера).

### 4.2. Отрицательные и их смягчение

| Последствие | Смягчение |
|---|---|
| Стрим прерывается при остановке инстанса | Частичный ответ сохраняется с `interrupted = true`; клиент повторяет; graceful shutdown 30 с; тест Г.11 |
| Redis pub/sub at-most-once для прогресса и для дельт агента | Через pub/sub не идут токены внешних провайдеров; прогресс перечитывается по REST; стрим агента при потере завершается `agent_offline` и повторяется |
| Голос по TCP чувствителен к потерям на мобильной сети | Буфер 100–200 мс на клиенте, PCM16 → Opus при необходимости, критерий перехода на LiveKit (3.7) |
| Два пути исполнения (прямой и Kafka) | Таблица критериев 3.2 обязательна в каждом ТЗ с LLM; оба пути используют один `stream_completion` |
| Роль `api` несёт нагрузку ожидания провайдеров | Нагрузка — ввод-вывод; лимит стримов на соединение; при росте — отдельный пул инстансов роли `api` для WebSocket (ADR-004/SYS-11) |
| `usage` при отмене — оценка | Поле `estimated`; методика оценки — SYS-08 |
