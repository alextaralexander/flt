## 1. Контекст

- **Проблема**: в составе контейнеров (CLAUDE.md, «Состав контейнеров») зафиксированы OpenSearch (логи обязательно, полнотекстовый поиск при необходимости) и Qdrant (семантический и полнотекстовый поиск при необходимости). Нужно решить: один кластер OpenSearch для логов и поиска или два; что ищется в PostgreSQL, что в OpenSearch, что в Qdrant; как индексы обновляются и перестраиваются из источника истины; как именуются индексы и коллекции по модулям; чьей моделью считаются эмбеддинги; как обеспечивается многоязычность (русский, английский, арабский, языки с иероглифами) и приватность собственных материалов; что из этого делается на этапе 1.
- **Почему сейчас**: этап 1, пункт Г.8 требует полного состава контейнеров в docker-compose и Helm, Г.4 — клиентов shared kernel. Первое использование поиска — этап 4 (STU-12, индекс кэша словарных статей), затем этап 5 (STU-27, семантический поиск по материалам) и этап 7 (STU-35.6). Без решения сейчас модули этапа 4 спроектируют индексацию по-разному.
- **Ограничения**:
  - CLAUDE.md «Масштабирование и состояние»: источник истины — PostgreSQL и MinIO; индексы OpenSearch и Qdrant производные, обновляются по событиям Kafka и при потере перестраиваются.
  - CLAUDE.md «Модульный монолит»: модуль владеет своими индексами OpenSearch и коллекциями Qdrant.
  - CLAUDE.md «Ключевые архитектурные требования»: i18n с первого дня — арабская вязь, иероглифы; LLM-агностичность; собственные материалы приватны (STU-27: поиск только по своим материалам); персональные данные — 152-ФЗ, удаление по запросу.
  - Шаблон `module-spec.md`, разделы 5.4 и 5.5: таблицы индексов и коллекций с источником истины, событием обновления и перестроением.
  - Boilerplate: зависимость `opensearch-py>=3.1` и настройки `OPEN_SEARCH_*` используются только для отправки логов (`app/core/logging/opensearch_sink.py`), которая выключается (CLAUDE.md «Отличия проекта от boilerplate», п. 3; ADR-010). Клиента Qdrant нет.
  - OQ-13: 10 000 зарегистрированных за год; объём индексов на старте — десятки тысяч словарных статей, тысячи материалов.
- **Если не решить**: модули начнут писать в индекс синхронно из транзакции (рассинхронизация с PostgreSQL), эмбеддинги разных моделей попадут в одну коллекцию (несравнимые векторы), приватные материалы окажутся доступны через поиск другим ученикам, а логи и поиск будут конкурировать за один узел без правила разделения.
- **Ссылки**: CLAUDE.md «Технологический стек», «Состав контейнеров», «Масштабирование и состояние»; SDD_plan.md этап 1 А.14, Г.4, Г.8; этап 4 п. 15 (STU-12); этап 5 п. 12 (STU-27); глоссарий: `entry_cache`, `material`, `social_search`, `llm_gateway`, `local_agent`; OQ-50, OQ-51 (ключ кэша статей).

## 2. Рассматриваемые варианты

### 2.1. Где какой поиск

#### Вариант A. Три уровня: PostgreSQL для точных выборок и фильтров, OpenSearch для многоязычного полнотекстового поиска, Qdrant для семантического и гибридного

- **Описание**: PostgreSQL — точное и префиксное совпадение (поиск статьи кэша по нормализованному слову, фильтры каталога курсов по языку и уровню, поиск пользователя по email администратором) через индексы B-tree и `pg_trgm`; OpenSearch — полнотекстовый поиск с языковыми анализаторами по значениям и примерам словарных статей, по тексту материалов, по страницам учеников и групп; Qdrant — поиск по смыслу (RAG по материалам, похожие статьи), гибридный поиск — плотный вектор плюс разреженный (BM25) в одной коллекции Qdrant, когда нужен один ранжированный список.
- **Плюсы**:
  - каждое хранилище делает то, для чего предназначено; каталог курсов и кэш статей на этапах 2–4 не требуют индексации вовсе;
  - OpenSearch и Qdrant включаются только там, где ТЗ указывает индекс.
- **Минусы**:
  - три разных API; для гибридного поиска нужно выбрать между OpenSearch (k-NN плагин) и Qdrant (разреженные векторы) — выбирается Qdrant (п. 2.2).
- **Масштабирование на N инстансах**: индексы общие, инстансы без состояния; запись в индексы — из консьюмеров роли `worker`.
- **Выделение модулей в микросервисы**: нейтрально — индексы именуются по модулям.
- **Трудоёмкость и риски**: средняя; клиенты shared kernel делаются один раз.

#### Вариант B. Только PostgreSQL: `tsvector`, `pg_trgm`, `pgvector`

- **Описание**: полнотекстовый поиск словарями PostgreSQL, векторы в `pgvector`, без OpenSearch для поиска и без Qdrant.
- **Плюсы**:
  - нет производных индексов, одна транзакция, меньше контейнеров для поиска (OpenSearch остаётся для логов).
- **Минусы**:
  - словари PostgreSQL для арабского, китайского, японского и корейского отсутствуют или слабы (нет сегментации иероглифов, нет нормализации арабских огласовок без расширений);
  - `pgvector` при сотнях тысяч чанков материалов нагружает источник истины индексом HNSW и его перестроением; фильтрация по владельцу вместе с ANN в `pgvector` ограничена;
  - противоречит CLAUDE.md: Qdrant и OpenSearch зафиксированы в составе контейнеров и в SDD_plan.md (ADR-014).
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая на старте; качество поиска по CJK и арабскому не достигается.

#### Вариант C. Всё в OpenSearch (полнотекстовый и k-NN)

- **Описание**: векторы в OpenSearch k-NN (Faiss или Lucene HNSW), Qdrant не используется.
- **Плюсы**:
  - один движок для поиска.
- **Минусы**:
  - k-NN в OpenSearch требует больше памяти JVM на тот же объём векторов, фильтрация по владельцу — пост-фильтр или эффективная фильтрация с ограничениями по типу движка;
  - OpenSearch делит узел с логами (п. 2.3), векторная нагрузка усиливает конкуренцию;
  - Qdrant зафиксирован в составе контейнеров.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: средняя; риск по памяти.

### 2.2. Векторное хранилище

#### Вариант A. Qdrant, коллекция на сущность модуля с именованными векторами по моделям эмбеддингов

- **Описание**: `qdrant-client` (async). Коллекция `flt_<module>_<entity>` (например `flt_materials_chunks`); именованные векторы — по одному на модель эмбеддингов (`"e5_multilingual_small": {"size": 384, "distance": "Cosine"}`), плюс разреженный вектор `"bm25"` для гибридного поиска; payload: `owner_id`, `source_id` (ID записи PostgreSQL), `language`, `module`-специфичные поля; индекс payload по `owner_id` и `source_id`. Запрос с фильтром `must: owner_id == <user>` обязателен для приватных коллекций — обёртка shared kernel требует `scope` при поиске в коллекции, помеченной `private=True`.
- **Плюсы**:
  - фильтрация по владельцу выполняется внутри ANN, а не после; разные модели эмбеддингов сосуществуют без несравнимых векторов в одном поле;
  - гибридный поиск (плотный + BM25) в одном запросе `query_points` с `prefetch` и `fusion: rrf`.
- **Минусы**:
  - ещё один клиент и контейнер (уже зафиксирован в составе);
  - смена модели эмбеддингов — новый именованный вектор и пересчёт всей коллекции фоновым заданием.
- **Масштабирование на N инстансах**: Qdrant один; запись из консьюмеров `worker`, чтение из `api`.
- **Выделение модулей в микросервисы**: помогает — коллекции модуля определяются префиксом.
- **Трудоёмкость и риски**: средняя; впервые нужен на этапе 5.

#### Вариант B. `pgvector` в схеме модуля

- **Описание**: расширение в PostgreSQL, колонка `vector` в таблице чанков.
- **Плюсы**:
  - транзакционность с источником истины, нет синхронизации.
- **Минусы**:
  - нагрузка HNSW на источник истины; одна размерность на колонку — смена модели требует новой колонки и миграции; расширение ставится в `public` и не переносится вместе со схемой модуля без установки на целевой базе.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая на старте; отклоняется по причинам 2.1 B.

### 2.3. OpenSearch: один кластер для логов и поиска или два

#### Вариант A. Один кластер (один узел в docker-compose), разделение по индексам, пользователям и политике хранения, с порогом разделения

- **Описание**: один контейнер `opensearch` (образ `flt-opensearch` на основе официального с установленными плагинами `analysis-icu`, `analysis-kuromoji`, `analysis-nori`, `analysis-smartcn`). Логи (ADR-010): индексы `flt-logs-YYYY.MM.DD`, ISM-политика `flt-logs-retention` удаления через 14 суток (значение — `LOGS_RETENTION_DAYS`, SYS-11), пишет пользователь `fluent-bit` с правом только на `flt-logs-*`, читает `grafana`. Поиск: индексы `flt-<module>-<entity>-v<N>` за алиасом `flt-<module>-<entity>`, пишет и читает пользователь `flt-backend` с правами на `flt-*`, кроме `flt-logs-*`. Плагин безопасности включён на всех стендах; пароль администратора — `OPENSEARCH_ADMIN_PASSWORD` (ADR-013; контейнер получает его как `OPENSEARCH_INITIAL_ADMIN_PASSWORD`). Heap — 1 ГБ в docker-compose (`OPENSEARCH_JAVA_OPTS=-Xms1g -Xmx1g`), `discovery.type=single-node`; в Helm — chart `opensearch-project/opensearch` с образом `flt-opensearch` (итоговое правило выбора chart-ов для инфраструктуры задаёт SYS-11, OQ-28). Порог разделения на два кластера (фиксируется в SYS-11): объём поисковых индексов больше 20 ГБ или p95 поискового запроса больше 200 мс при пиковой записи логов; разделение — только изменение `values` Helm и второго сервиса compose, код не меняется (адрес поиска — `OPENSEARCH_URL`, адрес логов — конфигурация Fluent Bit).
- **Плюсы**:
  - один контейнер JVM вместо двух на VPS (OQ-07), один набор учётных данных и мониторинга;
  - разделение по пользователям не даёт модулям читать логи и наоборот.
- **Минусы**:
  - всплеск записи логов влияет на задержку поиска; смягчается лимитом ресурсов и порогом разделения;
  - собственный образ ради плагинов анализа.
- **Масштабирование на N инстансах**: нейтрально — N инстансов пишут логи через Fluent Bit, поиск общий.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая; порог проверяется метриками ADR-010.

#### Вариант B. Два кластера с первого дня

- **Описание**: `opensearch-logs` и `opensearch-search`.
- **Плюсы**:
  - полная изоляция нагрузок.
- **Минусы**:
  - два JVM-процесса по 1 ГБ heap на VPS, когда поисковых индексов нет до этапа 4; два набора учётных данных и дашбордов.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: лишние ресурсы на этапах 1–3.

### 2.4. Обновление индексов

#### Вариант A. Консьюмер модуля-владельца по собственным событиям outbox плюс полное перестроение по команде через алиас

- **Описание**: модуль публикует доменные события (`flt.dictionary.entry_generated.v1`, `flt.dictionary.entry_deleted.v1`, `flt.materials.material_text_extracted.v1`, `flt.materials.material_deleted.v1`); консьюмер того же модуля (`group_id = flt.<module>.index_<entity>`) читает запись из PostgreSQL по `source_id` из события (а не из payload, чтобы индексировать актуальное состояние) и выполняет upsert или delete в индексе и коллекции; идемпотентность — `processed_events` (ADR-004) и `_id = source_id` в OpenSearch, `id = source_id` в Qdrant. Полное перестроение — команда `python -m app search reindex --module dictionary --entity entries` роли `worker`: создаёт `flt-dictionary-entries-v<N+1>` по актуальному шаблону, заполняет из PostgreSQL порциями по 500 строк фоновым заданием (ADR-004), переключает алиас атомарно (`_aliases` с `remove` и `add` в одном запросе), удаляет старый индекс; для Qdrant — новая коллекция и переключение алиаса коллекции. Консьюмер во время перестроения пишет в оба индекса (старый и новый) по алиасу записи.
- **Плюсы**:
  - источник истины не ждёт индекс: транзакция PostgreSQL не зависит от OpenSearch и Qdrant;
  - потеря индекса восстанавливается командой без простоя (алиас);
  - индексацией владеет модуль, другие модули индексы не трогают.
- **Минусы**:
  - задержка появления в поиске — задержка outbox плюс консьюмер (≈ 0.5–2 с);
  - двойная запись во время перестроения — код консьюмера учитывает активный «индекс записи».
- **Масштабирование на N инстансах**: консьюмер в consumer group, перестроение — одно задание под блокировкой.
- **Выделение модулей в микросервисы**: помогает — консьюмер и индекс уезжают с модулем.
- **Трудоёмкость и риски**: средняя; общий код индексатора (`SearchIndexer` базовый класс) в shared kernel без бизнес-логики.

#### Вариант B. Синхронная запись в индекс из транзакции (dual write)

- **Описание**: сервис после `commit` вызывает клиент индекса.
- **Плюсы**:
  - индекс обновляется мгновенно.
- **Минусы**:
  - при сбое индекса после `commit` данные расходятся без следа; при сбое `commit` после записи в индекс — призрачные документы; латентность REST растёт на время записи в два хранилища;
  - противоречит CLAUDE.md: обновление индексов по событиям Kafka.
- **Масштабирование на N инстансах**: работает, но без согласованности.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая; расхождение данных неизбежно.

#### Вариант C. Периодическая полная синхронизация

- **Описание**: задание раз в N минут сравнивает `updated_at` и переиндексирует.
- **Плюсы**:
  - просто.
- **Минусы**:
  - задержка в минуты; удаления требуют отдельного учёта; полное сканирование таблиц.
- **Масштабирование на N инстансах**: под блокировкой.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая; не подходит для словаря и социального поиска.

### 2.5. Модель эмбеддингов

#### Вариант A. Модель платформы для эмбеддингов: многоязычная open-source модель в отдельном контейнере `embeddings`, за интерфейсом `EmbeddingsProvider` LLM-шлюза

- **Описание**: контейнер `embeddings` (Text Embeddings Inference, CPU-образ) с моделью класса `intfloat/multilingual-e5-small` (384 измерения, 100+ языков, включая арабский и CJK); `llm_gateway` предоставляет `EmbeddingsProvider` с реализацией `platform` по умолчанию и возможностью реализации через провайдера ученика (`learner`) позже. Одна модель для всех учеников → один именованный вектор в коллекции; текст материалов не покидает платформу (152-ФЗ и приватность STU-27); токены ученика не расходуются на индексацию.
- **Плюсы**:
  - сравнимые векторы для всех пользователей, поиск по общим коллекциям (похожие статьи) возможен;
  - без внешних вызовов и ключей при индексации; детерминированно в тестах (заглушка по интерфейсу).
- **Минусы**:
  - ещё один контейнер в обоих вариантах развёртывания (CPU, ≈ 1 ГБ памяти), не входит в текущий состав контейнеров CLAUDE.md — требует решения пользователя;
  - качество ниже крупных облачных моделей эмбеддингов.
- **Масштабирование на N инстансах**: контейнер общий; при нагрузке — реплики за Service.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: средняя; появляется на этапе 5.

#### Вариант B. Эмбеддинги моделью ученика через LLM-шлюз

- **Описание**: `llm_gateway` вызывает эмбеддинги у провайдера ученика (OpenAI `text-embedding-3-small`, YandexGPT embeddings, локальная модель через агента).
- **Плюсы**:
  - нет нового контейнера; LLM-агностичность по букве.
- **Минусы**:
  - у разных учеников разные модели → векторы несравнимы, нужен именованный вектор на каждую модель и пересчёт при смене провайдера учеником;
  - у части провайдеров и локальных движков эмбеддингов нет (LM Studio — зависит от модели);
  - текст материалов уходит зарубежному провайдеру — требуется отдельное согласие (SYS-02); расход токенов ученика на индексацию.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: высокая эксплуатационная сложность коллекций.

#### Вариант C. Модель эмбеддингов в процессе монолита (FastEmbed, ONNX)

- **Описание**: модель загружается в процесс роли `worker` при старте.
- **Плюсы**:
  - без контейнера.
- **Минусы**:
  - ≈ 0.5 ГБ памяти и CPU в каждом воркере; модель — неизменяемая конфигурация (допустимо по CLAUDE.md), но увеличивает образ и время старта; при выделении модуля `materials` модель переезжает с ним.
- **Масштабирование на N инстансах**: каждый воркер несёт модель.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая; подходит как запасной вариант, если новый контейнер отклонён.

### 2.6. Многоязычный анализ в OpenSearch

#### Вариант A. Один индекс на сущность, поле текста на язык, заполняется только поле языка документа

- **Описание**: шаблон индекса объявляет поля `text_ru`, `text_en`, `text_ar`, `text_zh`, `text_ja`, `text_ko`, `text_und` с анализаторами: `ru` — `icu_tokenizer` + `icu_folding` + `russian_stemmer`; `en` — `icu_tokenizer` + `icu_folding` + `english_stemmer`; `ar` — `icu_normalizer` + `arabic_normalization` + `arabic_stem` (убирает огласовки и варианты алефа); `zh` — `smartcn`; `ja` — `kuromoji`; `ko` — `nori`; `und` — `icu_tokenizer` + `icu_folding` (для языков без специального анализатора). Документ хранит `language` (код из реестра `languages`, SYS-07) и текст только в поле своего языка; запрос идёт в поле известного языка (изучаемый язык ученика) или `multi_match` по всем полям. Новый язык с собственным анализатором — обновление шаблона и перестроение индекса (п. 2.4).
- **Плюсы**:
  - один индекс и один алиас на сущность, анализатор точно соответствует языку документа;
  - направление текста (RTL) на индексацию не влияет; смешанный текст в примерах (арабский с латиницей) обрабатывается ICU.
- **Минусы**:
  - список полей растёт с числом поддерживаемых языков (ограничен реестром `languages`).
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: низкая; анализаторы покрываются тестами на примерах слов каждого языка.

#### Вариант B. Индекс на язык (`flt-dictionary-entries-ru`)

- **Описание**: отдельный индекс и шаблон на каждый язык.
- **Плюсы**:
  - независимые настройки шардов по языкам.
- **Минусы**:
  - число индексов = сущности × языки; алиасы и перестроения множатся; поиск по нескольким языкам — по нескольким индексам.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: выше эксплуатационная.

## 3. Решение

- **Выбран**: 2.1 — A; 2.2 — A; 2.3 — A; 2.4 — A; 2.5 — A как рекомендация, окончательно — по новому OQ (см. раздел 4.3 и отчёт); 2.6 — A.
- **Решение**: поиск делится на три уровня — точные выборки и фильтры в PostgreSQL, многоязычный полнотекстовый поиск в OpenSearch (один кластер с логами, разделение по индексам, пользователям и политике хранения, с порогом разделения), семантический и гибридный поиск в Qdrant; индексы и коллекции производные — их обновляет консьюмер модуля-владельца по собственным событиям outbox, а перестраивает команда `search reindex` через алиас; имена `flt-<module>-<entity>` (OpenSearch, алиас над `-v<N>`) и `flt_<module>_<entity>` (Qdrant); эмбеддинги — одной моделью платформы за интерфейсом `EmbeddingsProvider` LLM-шлюза; на этапе 1 реализуются только клиенты shared kernel, контейнеры и инициализация шаблонов ролью `migrate`.
- **Обоснование**: вариант A каждого подвопроса сохраняет PostgreSQL и MinIO единственным источником истины, использует зафиксированные CLAUDE.md контейнеры без добавления новых до этапа 5, обеспечивает качество поиска для арабского и CJK (ICU и специализированные анализаторы), приватность материалов (фильтр владельца внутри ANN) и путь выделения модулей (префиксы модулей в именах).
- **Отвергнуты**:
  - 2.1 B — нет анализаторов для арабского и CJK, противоречит составу контейнеров; 2.1 C — память JVM и конкуренция с логами.
  - 2.2 B — нагрузка на источник истины, одна размерность на колонку.
  - 2.3 B — второй JVM-процесс до появления поисковых индексов.
  - 2.4 B — расхождение данных без следа; 2.4 C — задержка в минуты и учёт удалений.
  - 2.5 B — несравнимые векторы и передача текста материалов провайдеру; 2.5 C — запасной вариант, если контейнер `embeddings` отклонён.
  - 2.6 B — умножение индексов.
- **Правила решения** (входят в SYS-05 и спецификации модулей):
  1. **Что индексировать.** Модуль заводит индекс или коллекцию только по требованию ТЗ (разделы 5.4 и 5.5 спецификации модуля); до этого ищет в PostgreSQL. Плановые индексы: `flt-dictionary-entries` (STU-12, этап 4; содержит заголовок, значения, примеры, язык; ключ кэша при этом остаётся в PostgreSQL — OQ-51), `flt_materials_chunks` (STU-27, этап 5; чанки текста материалов, payload `owner_id`, `material_id`, `language`, `page`), `flt-social-profiles` и `flt-social-groups` (STU-35.6, этап 7; только публичные поля с учётом настроек приватности). Каталог курсов (VIS-02) и поиск пользователей администратором (ADM-01) — PostgreSQL (`pg_trgm`).
  2. **Именование.** OpenSearch: физический индекс `flt-<module>-<entity>-v<N>`, алиас чтения `flt-<module>-<entity>`, алиас записи `flt-<module>-<entity>-write`; шаблон индекса `flt-<module>-<entity>`; все имена строчные, дефисы. Qdrant: коллекция `flt_<module>_<entity>` (при перестроении — `flt_<module>_<entity>_v<N>` и алиас). Модуль обращается только к именам со своим префиксом — обёртка shared kernel подставляет префикс и запрещает чужой.
  3. **Декларация и инициализация.** Модуль объявляет индексы и коллекции в публичном API (`search.py`: имя, шаблон маппинга, размеры векторов, признак `private`); роль `migrate` (ADR-004) идемпотентно создаёт шаблоны индексов, алиасы и коллекции. Изменение маппинга — новый `-v<N>` и перестроение; шаблон версионируется вместе с кодом модуля.
  4. **Приватность и персональные данные.** Коллекции и индексы с данными конкретного пользователя помечаются `private=True`; поиск в них без `owner_id` отклоняется обёрткой. В индексы попадает минимум персональных данных (идентификаторы и публичные поля); удаление пользователя или материала по запросу (SYS-02) публикует событие удаления, консьюмер удаляет документы; перестроение из источника истины исключает удалённое автоматически. Тест SYS-02: после удаления пользователя в индексах нет документов с его `owner_id`.
  5. **Клиенты shared kernel.** `AsyncOpenSearch` (`opensearch-py`) и `AsyncQdrantClient` (`qdrant-client`) создаются лениво в lifespan, один на процесс, живут в пакете `app/core/search` (ADR-002; контракт import-linter запрещает импорт `opensearchpy` и `qdrant_client` из модулей — только обёртки); настройки `OPENSEARCH_URL`, `OPENSEARCH_USERNAME=flt-backend`, `OPENSEARCH_PASSWORD`, `OPENSEARCH_VERIFY_SSL`, `QDRANT_URL`, `QDRANT_API_KEY` (секреты — ADR-013); настройки boilerplate `OPEN_SEARCH_*` для отправки логов удаляются вместе с `opensearch_sink.py` (ADR-010), зависимость `opensearch-py` остаётся. Таймауты: поисковый запрос — 2 с, индексация — 10 с. Отказ OpenSearch или Qdrant не влияет на `/v1/ready` (ADR-010) и виден в деталях `/v1/health`; поиск отвечает 503 с `Retry-After`, консьюмеры индексации повторяют и уходят в DLQ (ADR-004), откуда `search reindex` восстанавливает индекс. Метрики `flt_search_requests_total{engine,module,status}`, `flt_search_latency_seconds`, `flt_search_index_lag_seconds` (ADR-010).
  6. **Эмбеддинги.** Вызов только через `EmbeddingsProvider` модуля `llm_gateway` (SYS-08); модель и её идентификатор (`embedding_model`) записываются в payload точки Qdrant; имя именованного вектора = идентификатор модели. Выбор модели платформы и контейнера `embeddings` — новый открытый вопрос (раздел 4.3), решить до начала этапа 5; в тестах — детерминированная заглушка эмбеддингов.
  7. **Этап 1.** Делается: контейнеры `opensearch` (образ `flt-opensearch` с плагинами анализа) и `qdrant` в docker-compose и Helm с постоянными томами; пользователи `flt-backend`, `fluent-bit`, `grafana` и `admin` в OpenSearch (ADR-010); клиенты и обёртки shared kernel; базовый класс `SearchIndexer`; команда `search reindex`; инициализация шаблонов индексов и коллекций ролью `migrate` (ADR-004); проверки клиентов в `/v1/health`; smoke-тест этапа 1 Г.8 создаёт тестовый шаблон индекса и коллекцию и удаляет их. Не делается: индексы модулей, эмбеддинги, контейнер `embeddings`.
- **Границы решения**: состав полей индексов и ключ кэша статей — ТЗ STU-12 (OQ-50, OQ-51); разбиение материалов на чанки, извлечение текста и RAG — ТЗ STU-27 и ADR-007; интерфейс `EmbeddingsProvider` и его реализации — SYS-08; доставка логов и ISM-политика — ADR-010 и SYS-11; реестр языков и кодов — SYS-07; выбор модели эмбеддингов — новый OQ.

## 4. Последствия

### 4.1. Положительные

- Источник истины один; любой индекс и коллекция восстанавливаются командой без простоя.
- Модуль владеет своими индексами и консьюмерами: при выделении переезжают имена с префиксом модуля, декларации и индексатор.
- Арабский и языки с иероглифами ищутся анализаторами, предназначенными для них; добавление языка — изменение шаблона и перестроение.
- Приватность материалов обеспечивается на уровне запроса к Qdrant, а не только в UI.
- На этапах 1–3 поисковые индексы ресурсов не потребляют; один узел OpenSearch обслуживает логи.

### 4.2. Отрицательные и их смягчение

| Последствие | Смягчение |
|---|---|
| Данные появляются в поиске с задержкой 0.5–2 с | приемлемо для словаря, материалов и социального поиска; свои статьи ученик видит из PostgreSQL сразу |
| Логи и поиск делят узел OpenSearch | разделение по пользователям и индексам, лимиты ресурсов, порог разделения в SYS-11, метрики задержки |
| Собственный образ OpenSearch с плагинами анализа | Dockerfile в `deploy/config/opensearch`, сборка в CI (ADR-011), версия плагинов = версия OpenSearch |
| Смена модели эмбеддингов требует пересчёта коллекции | именованные векторы позволяют считать новую модель рядом и переключить чтение без простоя |
| Два клиента и две обёртки в shared kernel до первого реального использования (этап 4) | минимальный объём на этапе 1: подключение, health, декларации, `reindex`; индексаторы пишутся в модулях |
| Нужен новый контейнер `embeddings` (если принят вариант 2.5 A) | решение пользователя по новому OQ до этапа 5; запасной вариант 2.5 C без контейнера |
