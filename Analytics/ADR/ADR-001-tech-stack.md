## 1. Контекст

- **Проблема**: CLAUDE.md фиксирует стек (Python и FastAPI на бэкенде, React и TypeScript на фронтенде) и правило «при обновлении переходить на актуальную стабильную версию», но не определяет, что считается «актуальной стабильной» версией, когда и как выполняется переход, кто обновляет зависимости и как версии фиксируются. Boilerplate бэкенда зафиксирован на Python 3.13 (`.python-version`, `Dockerfile`), `pyproject.toml` допускает `>=3.12`, `uv.lock` собран в июне 2026 года и уже отстаёт от текущих версий (ruff 0.15.20 против 0.17.0, fastapi 0.139.0 против 0.143.0, starlette 1.3.1 против 1.7.0). CPython 3.14.0 вышел 2025-10-07, а CPython 3.15.0 по PEP 790 был запланирован на 2026-10-01 — к дате этого ADR «последних стабильных» версий две. Boilerplate фронтенда импортирован с устаревшими версиями (React 18, Vite 5, Tailwind 3, ESLint 8, Vitest 2, Storybook 8), версия Node не зафиксирована (`.nvmrc` и `engines` отсутствуют). `renovate.json` лежит внутри `src/backend/py-monolyth`, покрывает только бэкенд и содержит правило `faststream <0.7`, противоречащее `pyproject.toml` (линия 0.7). Внутренняя библиотека `src/backend/py-main-lib` объявляет жёсткие пины (`fastapi==0.115.6`, `SQLAlchemy==2.0.29`) в `setup.py`, которые игнорируются установкой `--no-deps`.
- **Почему сейчас**: этап 1, п. А.1 (первое ADR этапа) и п. Г.1 (скелет репозитория: `.python-version`, `Dockerfile`, `pyproject.toml`, `renovate.json`, обновление frontend). Все остальные ADR и спецификации ссылаются на версии из этого документа.
- **Ограничения**:
  - CLAUDE.md «Технологический стек»: Python и FastAPI, другие языки на бэкенде не используются; React и TypeScript на фронтенде; «Конкретные версии Python, React и зависимостей фиксируются в `pyproject.toml` и `package.json`, а не в этом документе. При обновлении переходить на актуальную стабильную версию»; переход на 3.14 «решается в ADR-001 после проверки совместимости зависимостей»;
  - CLAUDE.md «Backend-сервис (boilerplate)»: uv, FastAPI и Pydantic v2, SQLAlchemy 2.0 async, Alembic, FastStream (Kafka), ruff, mypy strict, bandit, detect-secrets, pre-commit, Docker-сборка из `uv.lock`;
  - решения пользователя 2026-10-10: только Kafka (NATS удалён); pnpm для frontend (ADR-005); локальный агент на Python со сборкой в исполняемый файл (ADR-008); GitHub Actions (OQ-06); медиасервер LiveKit (ADR-015);
  - `src/backend/py-monolyth/CLAUDE.md`: источник истины по зависимостям — `pyproject.toml`, лок — `uv.lock`, `uv.lock` не редактируется вручную (`make lock`), FastStream линия 0.7 с потолком `<0.8` («следующую major-линию брать осознанно вместе с py-main-lib»);
  - `py-main-lib` ставится из папки без своих зависимостей (`uv pip install --no-deps`), private registry недоступен;
  - OQ-15 (planned → ADR-001): перейти на 3.14 в п. Г.1, если `uv lock` и тесты проходят; иначе остаться на 3.13 и пересмотреть в начале этапа 2.
- **Если не решить**: каждое обновление будет отдельным спором «обновлять или нет», `uv.lock` и `package.json` будут стареть между этапами, а переход на новый CPython случится в неудобный момент под давлением окончания поддержки библиотек.
- **Ссылки**: CLAUDE.md «Технологический стек», «Backend-сервис (boilerplate)», «Frontend (boilerplate)», «Отличия проекта от boilerplate»; `src/backend/py-monolyth/CLAUDE.md` «Зависимости и окружение»; SDD_plan.md этап 1 (А.1, А.5, Г.1); OQ-15; ADR-002, ADR-005, ADR-008, ADR-011.

## 2. Рассматриваемые варианты

Две независимые части: версия Python сейчас (2.1) и политика версий для всего стека (2.2).

### 2.1. Версия Python для монолита и локального агента

#### Вариант A. Остаться на Python 3.13 до начала этапа 2

- **Описание**: `.python-version`, `Dockerfile` и `requires-python` не меняются; проверка 3.14 повторяется в начале этапа 2.
- **Плюсы**:
  - нулевой риск в п. Г.1;
  - совпадает с тем, на чём проверялся boilerplate при импорте (2026-09-21).
- **Минусы**:
  - отступление от правила «последние стабильные версии» при фактически подтверждённой совместимости (раздел 1.1);
  - весь код этапа 1 (shared kernel, `identity`, `llm_gateway`, агент) пишется под 3.13 и потом переводится — лишний прогон всех тестов на N инстансах;
  - 3.13 вышел в октябре 2024; к концу этапа 1 он на две минорные версии позади.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: внедрение — ноль; риск — переход в середине разработки.

#### Вариант B. Перейти на Python 3.14 в п. Г.1 (до первого кода)

- **Описание**: `.python-version` = `3.14`, `requires-python = ">=3.14"`, `target-version = "py314"` в ruff, `python_version = "3.14"` в mypy, базовые образы `ghcr.io/astral-sh/uv:python3.14-bookworm-slim` и `python:3.14-slim` в `Dockerfile`, `uv lock --upgrade` с новыми версиями из раздела 1.1; локальный агент (ADR-008) собирается тем же интерпретатором. Условие перехода выполнено: `make check` на 3.14 зелёный (раздел 1.1); подтверждается повторно в CI на первом коммите п. Г.1.
- **Плюсы**:
  - соответствует правилу проекта и подтверждено фактами: все колёса есть, тесты, mypy и ruff зелёные;
  - весь код этапа 1 сразу пишется под целевую версию; переход на 3.15 будет первым и единственным переходом в ближайший год;
  - 3.14 получает исправления до октября 2027 и security-обновления до октября 2030.
- **Минусы**:
  - отладочный опыт на 3.14 у библиотек моложе на год, чем на 3.13: возможны редкие ошибки в бинарных пакетах, не покрытые тестами boilerplate;
  - образы `python:3.14-slim` и `uv:python3.14` должны существовать на момент сборки (проверено: uv распространяет сборку CPython 3.14.0, образы Docker Hub `python:3.14` публикуются с октября 2025).
- **Масштабирование на N инстансах**: нейтрально; интерпретатор одинаков во всех инстансах, так как ставится из образа.
- **Выделение модулей в микросервисы**: нейтрально; все будущие сервисы собираются из того же базового образа.
- **Трудоёмкость и риски**: внедрение — 1 час в п. Г.1 плюс прогон CI; риск — регрессия библиотеки на 3.14; смягчение — откат на 3.13 заключается в правке четырёх строк и `uv lock`, порядок отката описан в разделе 3.1.

#### Вариант C. Перейти сразу на Python 3.15

- **Описание**: `.python-version` = `3.15` (релиз запланирован на 2026-10-01).
- **Плюсы**:
  - формально самая новая версия.
- **Минусы**:
  - uv 0.9.11 не знает 3.15, бинарные зависимости (asyncpg, pydantic-core, uvloop, aiokafka) выпускают колёса для новой линии в течение 1–3 месяцев после релиза — сборка из sdist в Docker увеличит время сборки и число отказов;
  - факт выхода 3.15.0 не подтверждён на дату ADR; первая исправительная версия 3.15.1 ожидается в декабре 2026;
  - проверка, аналогичная разделу 1.1, невозможна до появления колёс.
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: внедрение — неизвестно; риск — остановка этапа 1 из-за отсутствия колёс.

### 2.2. Политика версий для всего стека

#### Вариант D. «Всегда самое новое»: Renovate с автослиянием всех обновлений

- **Описание**: Renovate открывает PR на каждое обновление и сливает автоматически при зелёном CI, включая мажорные версии и новые линии CPython и Node в день релиза.
- **Плюсы**:
  - нулевое отставание, минимум ручной работы.
- **Минусы**:
  - мажорные обновления (FastStream 0.8, Pydantic 3, React следующей линии, Tailwind следующей линии) меняют API и ломают код; зелёный CI не гарантирует отсутствие изменений поведения, не покрытых тестами (например, стриминг через WebSocket с реальным браузером);
  - автослияние в `main` противоречит OQ-05 (слияние только через PR, одобренный человеком на G3) и тратит минуты CI на каждый патч (ADR-011);
  - CPython и Node `X.0` — самые нестабильные выпуски линии.
- **Масштабирование на N инстансах**: риск одновременного обновления всех инстансов на непроверенную версию библиотеки.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: внедрение — полдня; риск — внезапные поломки `main`.

#### Вариант E. «Последние стабильные с предохранителями»: еженедельное обслуживание lock-файлов, мажорные обновления — отдельными PR вручную, новые линии runtime — после первой исправительной версии

- **Описание**: точные определения — раздел 3.2. Коротко: диапазоны в `pyproject.toml` и `package.json`, точные версии в `uv.lock` и `pnpm-lock.yaml`; Renovate (GitHub App) на уровне репозитория раз в неделю пересобирает lock-файлы и группирует минорные и патч-обновления в один PR, мажорные — отдельный PR на пакет с меткой `deps:major`, который Claude выполняет как мини-ТЗ (миграция, тесты, `make check`); новая линия CPython или Node принимается не раньше выхода первой исправительной версии (`X.Y.1`) и только после проверки по методике раздела 1.1; инфраструктурные образы (PostgreSQL, Redis, Kafka, HAProxy, Nginx, MinIO, OpenSearch, Qdrant, LiveKit, Prometheus, Grafana, Fluent Bit) закреплены на минорном теге и обновляются Renovate тем же порядком одновременно в docker-compose и Helm.
- **Плюсы**:
  - соответствует правилу «последние стабильные версии» без приёма `X.0`-выпусков runtime-ов и без автослияния;
  - обновления проходят через тот же конвейер и CI, что и фичи; человек видит мажорные изменения;
  - одинаковые версии во всех инстансах и в обоих вариантах развёртывания — через lock-файлы и общие теги образов.
- **Минусы**:
  - еженедельный PR обновлений требует внимания (5–10 минут при зелёном CI);
  - отставание от `X.0` runtime-ов на 1–2 месяца.
- **Масштабирование на N инстансах**: обновление проходит через образ; все инстансы одной версии; откат — предыдущий тег образа (ADR-011).
- **Выделение модулей в микросервисы**: нейтрально; политика применяется к каждому сервису.
- **Трудоёмкость и риски**: внедрение — полдня (перенос и расширение `renovate.json`); риск — накопление отложенных мажорных PR; смягчение — ревью зависимостей в конце каждого этапа (SDD_plan.md, раздел 8).

#### Вариант F. «Заморозка на этап»: версии фиксируются в начале этапа и не меняются до его конца

- **Описание**: `uv lock --upgrade` и `pnpm update` выполняются один раз в начале каждого этапа.
- **Плюсы**:
  - предсказуемость внутри этапа.
- **Минусы**:
  - этапы длятся месяцами; security-обновления откладываются;
  - в конце этапа накапливаются десятки обновлений сразу — большой PR с неясной причиной поломок;
  - противоречит правилу CLAUDE.md «при обновлении переходить на актуальную стабильную версию».
- **Масштабирование на N инстансах**: нейтрально.
- **Выделение модулей в микросервисы**: нейтрально.
- **Трудоёмкость и риски**: внедрение — ноль; риск — уязвимости и большие скачки версий.

## 3. Решение

- **Выбран**: Вариант B (Python 3.14 в п. Г.1) + Вариант E (последние стабильные с предохранителями).
- **Решение**: стек FLT — Python 3.14 и FastAPI на бэкенде, в локальном агенте (`src/agent`), общем пакете протокола (`src/protocol`) и репозиторных инструментах (`src/tools`, ADR-011), React и TypeScript на фронтенде, Node.js линии Active LTS (сейчас 24) и pnpm; версии фиксируются диапазонами в `pyproject.toml` и `package.json` и точно — в `uv.lock` и `pnpm-lock.yaml`; Renovate еженедельно обновляет lock-файлы и минорные версии одним PR, мажорные версии — отдельными PR, выполняемыми вручную через `make check` и CI; новая линия CPython или Node принимается после выхода `X.Y.1` и проверки по методике раздела 1.1; версии инфраструктурных образов закреплены на минорных тегах одинаково в docker-compose и Helm (исключение — MinIO: зафиксированный тег последнего опубликованного образа до решения OQ-64, ADR-007 §3.10). Переход на Python 3.14 подтверждён пользователем 2026-10-10. Внутренняя библиотека `py-main-lib` свободно правится в репозитории FLT — перевод на `pyproject.toml` с диапазонами, `ConfigDict`, чистка, path-зависимость uv (подтверждено пользователем 2026-10-10, OQ-69).
- **Обоснование**: совместимость 3.14 доказана полным прогоном `make check` на реальном дереве (раздел 1.1), поэтому вариант A — отступление от правила без причины, а вариант C невозможно проверить. Вариант E даёт регулярность обновлений без автослияния в защищённый `main` и без приёма `X.0`-выпусков, что согласуется с OQ-05 и ADR-011.
- **Отвергнуты**:
  - Вариант A — совместимость подтверждена, переход позже дороже.
  - Вариант C — нет колёс и поддержки в uv на дату решения; принимается по правилу раздела 3.2 после 3.15.1.
  - Вариант D — автослияние противоречит OQ-05; `X.0`-выпуски runtime-ов небезопасны.
  - Вариант F — противоречит правилу CLAUDE.md и откладывает security-обновления.
- **Границы решения**: ADR не выбирает конкретные версии библиотек фронтенда (ADR-005), инструмент сборки агента в исполняемый файл (ADR-008), версии Helm, kind и действий GitHub (ADR-011, SYS-12), версии инфраструктурных образов по контейнерам (SYS-11); не пересматривает состав стека (языки, брокер, хранилища), зафиксированный в CLAUDE.md и решениях OQ.

### 3.2. Политика версий (правила)

1. **Определение «последней стабильной»**. Для библиотек — последняя версия на PyPI или npm без маркеров pre-release. Для runtime-ов (CPython, Node.js) — последняя линия, у которой вышла первая исправительная версия (`X.Y.1`) и которая входит в поддерживаемые линии инструментов проекта (uv, Vite, Vitest, Playwright, Storybook); для Node дополнительно — статус Active LTS. Для инфраструктурных образов — последняя стабильная минорная линия официального образа.
2. **Фиксация**. Backend: диапазоны `>=X.Y,<след. major` в `pyproject.toml`, точные версии в `uv.lock`; `uv.lock` не редактируется вручную (`make lock`); Docker-сборка — `uv sync --frozen`. Frontend: диапазоны `^X.Y.Z` в `package.json`, точные версии в `pnpm-lock.yaml`; установка — `pnpm install --frozen-lockfile`. Runtime — `.python-version`, `.nvmrc`, `packageManager`, теги базовых образов. Образы инфраструктуры — минорный тег, одинаковый в docker-compose и Helm (паритет проверяет тест в SYS-11).
3. **Автоматические обновления**. Renovate подключается к репозиторию как GitHub App; `renovate.json` переносится в корень репозитория и охватывает менеджеры `pep621` (uv), `npm` (pnpm), `dockerfile`, `docker-compose`, `helm-values`, `github-actions`, `pre-commit`. Расписание — `before 6am on monday` (как в boilerplate). Правила: `lockFileMaintenance` включено (еженедельная пересборка `uv.lock` и `pnpm-lock.yaml` одним PR); минорные и патч-обновления группируются в PR `deps: weekly minor and patch`; мажорные — отдельный PR на пакет с меткой `deps:major`; обновления CPython, Node и базовых образов — отдельные PR с меткой `deps:runtime`, которые не открываются для `X.Y.0` (правило `minimumReleaseAge = 30 days` для менеджеров `dockerfile` и `github-actions`, для runtime-ов — проверка `X.Y.1` вручную). Автослияние выключено для всех PR; `dependencyDashboard` включён.
4. **Порядок приёма обновлений**. Еженедельный PR сливается при зелёном CI (ADR-011) после просмотра пользователем; мажорный PR выполняется Claude как мини-задача: чтение changelog, миграция, `make check` или `pnpm`-проверки, тесты на N инстансах, запись в `Analytics/ADR` только если меняется архитектурное решение (например, FastStream 0.8 с изменением интеграции FastAPI). Обновление runtime-а — PR с проверкой по методике раздела 1.1 (lock, колёса, установка, полный `make check`, сборка образа).
5. **Ограничения потолков**. Явные потолки в `pyproject.toml` (`faststream <0.8`, `redis <7`, `SQLAlchemy <2.1`) снимаются только мажорным PR с обоснованием в описании PR; новые потолки ниже текущего major не вводятся без причины, записанной комментарием в `pyproject.toml`.
6. **Ревью зависимостей в конце этапа** (SDD_plan.md, раздел 8): открытые мажорные PR и отложенные обновления runtime-ов разбираются на гейте GS; список отложенного фиксируется в реестре открытых вопросов.
7. **Единство версий**. Все роли монолита (`api`, `worker`, `migrate`, `media_agent` — ADR-004) собираются из одного образа и одного `uv.lock`; `src/agent`, `src/protocol` и `src/tools` — отдельные проекты uv с тем же интерпретатором и той же политикой обновлений (их lock-файлы обслуживает тот же Renovate); frontend — из одного `pnpm-lock.yaml`. Версия, которая работает на стенде local, в CI, в docker-compose на VPS и в Helm в kind, одна и та же.

## 4. Последствия

### 4.1. Положительные

- Решение по Python 3.14 опирается на факты (раздел 1.1), а не на предположения; код этапа 1 сразу пишется под целевую версию.
- Правило «последние стабильные версии» получает проверяемые критерии (`X.Y.1`, Active LTS, колёса для всех бинарных пакетов) и механизм исполнения (Renovate, еженедельный PR, мажорные PR вручную).
- `uv.lock` и `pnpm-lock.yaml` перестают стареть между этапами; security-обновления приходят в течение недели.
- Единые версии во всех инстансах и обоих вариантах развёртывания — следствие lock-файлов и общих тегов образов.

### 4.2. Отрицательные и их смягчение

| Последствие | Смягчение |
|---|---|
| Еженедельный PR обновлений требует просмотра пользователем и минут CI | Один PR в неделю, быстрая ступень CI; при зелёном CI просмотр занимает минуты (ADR-011) |
| Мажорные обновления (FastStream 0.8, Pydantic 3, React и Tailwind следующих линий) потребуют миграции кода | Отдельные PR по правилу 4; потолки в `pyproject.toml` защищают от случайного приёма |
| Отставание от `X.0`-выпусков CPython и Node на 1–2 месяца | Осознанно: `X.Y.1` и колёса для всех бинарных пакетов — условие стабильности |
| Отладочный опыт библиотек на 3.14 моложе, чем на 3.13 | Полный `make check` зелёный; порядок отката описан в разделе 3.1 |
| `faststream.kafka.fastapi.KafkaRouter` помечен к удалению в FastStream 1.0 | Замена на `faststream_fastapi` или на отдельный FastStream-приложение в lifespan — в п. Г.1 вместе с раскладкой Kafka-роутеров по модулям (ADR-002, ADR-004) |
| `py-main-lib` с class-based `Config` в Pydantic и жёсткими пинами в `setup.py` | Перевод библиотеки на `pyproject.toml` с диапазонами и `ConfigDict` в п. Г.1; библиотека становится `path`-зависимостью uv |
| `renovate.json` boilerplate содержит устаревшее правило `faststream <0.7` | Исправляется при переносе в корень |
