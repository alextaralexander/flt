# CLAUDE.md — Foreign Language Trainer (FLT)

Инструкции для Claude при работе с этим репозиторием.

## О проекте

FLT — платформа для изучения иностранных языков с помощью LLM (внешних: OpenAI, Claude, YandexGPT, GigaChat и др.; локальных: llama.cpp, LM Studio).
Модель платформы используется только в быстром тесте без регистрации. Для обучения ученик подключает свою внешнюю или локальную модель.
Все курсы бесплатные, платежей на платформе нет. Ученик может состоять в нескольких классах и курсах.
Полные бизнес-требования: [Analytics/BRD/FLT_BRD.md](Analytics/BRD/FLT_BRD.md) — источник истины по функциональности.
План работы (порядок ТЗ, тестов и кода по этапам): [Analytics/BRD/SDD_plan.md](Analytics/BRD/SDD_plan.md).
Репозиторий: https://github.com/alextaralexander/flt

Роли пользователей: Посетитель портала, Ученик, Администратор преподавателя/класса, Администратор платформы.

## Процесс разработки: спецификации + TDD

Проект разрабатывается **полностью через вайбкодинг на основе спецификаций** (spec-driven development) и по **TDD**. Код пишет Claude, человек формулирует требования, утверждает спецификации и принимает результат. Структура репозитория, документация и процессы строятся так, чтобы Claude мог работать по ним самостоятельно и предсказуемо.

### Источник истины

Цепочка: **BRD → спецификация → тесты → код**.
- Спецификация — главный артефакт. Код и тесты вторичны и должны ей соответствовать.
- Сначала меняется спецификация, потом тесты, потом код. Код без спецификации не пишется.
- Если в ходе реализации выяснилось, что спецификация неполна или противоречива, нужно остановиться, предложить правку спецификации и дождаться утверждения.

### Спецификации

- Расположение: `Analytics/Specs/<модуль>/<ID>-<slug>.md`, где ID — идентификатор пункта BRD (см. SDD_plan.md). Одна спецификация на фичу, модуль совпадает с модулем backend/frontend. Системные спецификации — `Analytics/Specs/_system/`, ADR — `Analytics/ADR/`.
- Шаблоны: `Analytics/Specs/_templates/` (TODO: создать). Обязательные разделы:
  - цель и ссылка на пункт BRD;
  - роли и пользовательские сценарии;
  - **критерии приёмки** в формате Given / When / Then, у каждого свой ID (например `STU-12.1-AC3`);
  - контракты: OpenAPI для REST, AsyncAPI для WebSocket и Kafka;
  - модель данных модуля;
  - состояние и масштабируемость: что хранится в PostgreSQL, что в Redis, как фича ведёт себя при одновременных запросах к разным инстансам;
  - UI: экраны, состояния, i18n/RTL;
  - нефункциональные требования и граничные случаи;
  - вне рамок (что сознательно не делается);
  - статус: `draft` → `approved` → `implemented`.
- Контракты API — spec-first: код и клиенты генерируются/проверяются по контракту, а не наоборот.
- Спецификации пишутся так, чтобы их можно было реализовать без устных пояснений: однозначно, с примерами, без «и т.д.».

### TDD

Для каждого функционала автотесты создаются **сразу, до или вместе с кодом**. Фича без тестов не считается готовой.

Цикл:
1. **Red** — по критериям приёмки из спецификации пишутся тесты, они падают.
2. **Green** — минимальный код, чтобы тесты прошли.
3. **Refactor** — улучшение кода при зелёных тестах.

Правила:
- Каждый критерий приёмки покрыт минимум одним тестом. Тест ссылается на ID критерия (в имени или аннотации/тэге), чтобы прослеживалась связь спецификация ↔ тест.
- Нельзя ослаблять, удалять или отключать тесты, чтобы «пройти» сборку. Если тест неверен — сначала исправить спецификацию/тест с объяснением причины.
- Исправление бага начинается с теста, который его воспроизводит.
- LLM-провайдеры, TTS/STT и прочие внешние сервисы в тестах подменяются заглушками/моками; тесты детерминированы и не требуют сети или ключей.

Уровни тестов:
- **Backend**: unit-тесты; интеграционные тесты модуля через его публичный API (с реальными PostgreSQL, Redis, Kafka и, если фича их использует, MinIO, OpenSearch, Qdrant в контейнерах); контрактные тесты REST, WebSocket и Kafka; архитектурные тесты границ модулей. Инструменты — из boilerplate (pytest, pytest-asyncio, pytest-cov, `TestKafkaBroker`), для границ модулей добавляется import-linter или аналог (ADR-002).
- **Frontend**: unit-тесты и тесты компонентов; тесты модулей с моками REST и WebSocket по контракту. Инструменты — из boilerplate: Vitest, Testing Library, MSW.
- **E2E**: ключевые пользовательские сценарии из спецификаций, в т.ч. RTL-языки. Инструмент — Playwright из boilerplate фронтенда.
- **Масштабируемость**: тесты каждой фичи на стенде из N инстансов монолита (раздел «Масштабирование и состояние»). Интеграционные backend-тесты и E2E по умолчанию выполняются на этом стенде.
- Порог покрытия backend — не ниже 75% (`fail_under` в `src/backend/py-monolyth/pyproject.toml`), повышать можно, понижать нельзя. Порог frontend — задаётся в ADR-005. Все тесты запускаются в CI, красная сборка блокирует слияние.

### Определение готовности (Definition of Done)

- [ ] Спецификация в статусе `approved`, после реализации — `implemented`
- [ ] Все критерии приёмки покрыты тестами, все тесты зелёные
- [ ] Границы модулей не нарушены (архитектурные тесты зелёные)
- [ ] Контракт API соответствует реализации
- [ ] Тесты на N инстансах зелёные, состояние хранится только в PostgreSQL, MinIO и Redis
- [ ] Добавлены метрики и логи, нужные для эксплуатации фичи
- [ ] Строки UI вынесены в i18n
- [ ] docker-compose и Helm charts обновлены (если затронуто развёртывание)
- [ ] Документация модуля обновлена

### Отличия проекта от boilerplate

Boilerplate рассчитан на небольшой микросервис. В FLT действуют следующие отличия. Они реализуются на этапе 1, решения фиксируются в ADR.

1. **Доменные модули вместо слоёв на весь сервис.** Boilerplate раскладывает весь код по слоям (`app/api/controllers`, `services`, `dao`, `schemas`). В FLT каждый доменный модуль — отдельный пакет со своими слоями внутри по образцу boilerplate, `app/core` остаётся общим ядром. Точная раскладка и адаптация скаффолдера под модули — ADR-002.
2. **Только Kafka.** Сделано 2026-09-22: NATS удалён полностью — код и тесты, настройки и env-файлы, зависимость `nats-py`, контейнер в docker-compose, NATS-функции в `src/backend/py-main-lib` (`auth_user_nats`, `UserTopicViolationError`). Пример Kafka-обработчика теперь отвечает в исходящий Kafka-топик.
3. **Логи.** Встроенная отправка логов из приложения в OpenSearch (`OPEN_SEARCH_LOGS_ENABLED`) выключена. Приложение пишет JSON-логи в stdout, их собирает Fluent Bit.
4. **Секреты.** Boilerplate умеет сам читать секреты из Vault (`configs/vault_config.py`) и берёт их из переменных окружения, если Vault недоступен. Как получать секреты в Kubernetes — ADR-013. В docker-compose Vault нет, секреты из переменных окружения.
5. **Трейсы.** Boilerplate экспортирует трейсы OpenTelemetry по OTLP, а коллектора в составе контейнеров нет. Добавить коллектор или отключить экспорт — ADR-010.
6. **Выпуск токенов.** Boilerplate только проверяет JWT. Токены выпускает модуль `identity` (регистрация и вход, VIS-04 и VIS-05).
7. **Инфраструктура и сборка.** Сделано 2026-09-22: `make compose-up` поднимает инфраструктуру из `deploy/docker-compose/docker-compose.yml`, `Dockerfile` берёт py-main-lib из build-context-а (`make docker-build`). Осталось: `.pre-commit-config.yaml` лежит в `src/backend/py-monolyth` — подключить на уровне репозитория.
8. **Имя сервиса.** `python-boilerplate` переименовать в `flt-backend` (pyproject, Makefile, env-файлы).
9. `BOILERPLATE.md` — манифест для другого процесса разработки, в FLT не используется.
10. **Тестовая БД.** pytest и стенд local используют одну базу и схему (`flt` / `ms_py_test`), а тесты пересоздают таблицы: запуск тестов стирает локальные данные, а локальные данные могут ломать тесты. Развести на этапе 1.
11. **Топики Kafka.** Сервис подписывается на топики при старте. Локальная Kafka создаёт их автоматически (`KAFKA_AUTO_CREATE_TOPICS_ENABLE`). Для остальных стендов — создавать топики явно (SYS-04).

### Отличия проекта от boilerplate

Реализуются на этапе 1, решения фиксируются в ADR-005.

1. **Версии устарели.** В boilerplate React 18, Vite 5, Tailwind 3, ESLint 8 со старым форматом конфига, TypeScript 5, Vitest 2, React Router 7, Storybook 8. По правилу проекта нужны последние стабильные версии: обновить, конфиг ESLint перевести на flat config. Менеджер пакетов (yarn 1 или другой) — ADR-005.
2. **Демо-фичи.** `auth`, `comments`, `discussions`, `teams`, `users` — примеры стиля. Остаются как образец до появления первых модулей FLT, затем удаляются вместе с их моками, тестами и роутами.
3. **Модули.** `src/features/<модуль>` соответствуют модулям бэкенда. Правило ESLint `import/no-restricted-paths` получает зону на каждый модуль.
4. **i18n и RTL.** В boilerplate их нет. Добавить i18next с языками интерфейса ru, en, ar. Направление текста задаётся для всего документа, в стилях только логические классы Tailwind (`ms-*`, `pe-*`, `rtl:`), Radix — через `DirectionProvider`.
5. **API.** Клиент и типы генерируются из OpenAPI-контрактов, моки MSW — по тем же контрактам. Базовые адреса относительные: `/api` и `/ws` через HAProxy, чтобы одна сборка работала на всех стендах. В dev-режиме Vite проксирует их на бэкенд.
6. **WebSocket.** В boilerplate нет — добавить общий клиент в shared-слое: переподключение, подписки модулей.
7. **Аутентификация.** Boilerplate рассчитан на cookie-сессию (`react-query-auth`, `withCredentials`), бэкенд проверяет JWT в заголовке `Authorization: Bearer`. Способ передачи токена — ADR-006.
8. **Сборка и раздача.** Production-сборка раздаётся Nginx (контейнер из «Состава контейнеров»), Dockerfile и конфигурация Nginx — на этапе 1.
9. **Порог покрытия** в boilerplate не задан — задать в ADR-005.
10. **Git-хуки.** Скрипт `prepare` вызывает husky, а lint-staged настроен внутри `package.json` приложения — подключить на уровне репозитория вместе с pre-commit бэкенда.

## Взаимодействие

| Тип | Технология | Где используется |
|---|---|---|
| Синхронное | REST (FastAPI) | запросы фронтенда к бэкенду, внешние клиенты |
| Асинхронное с фронтендом | WebSocket (FastAPI) | стриминг ответов LLM, прогресс длительных задач, уведомления, чат и события класса |
| Асинхронное внутри монолита и с другими сервисами | Kafka | доменные события между модулями, очереди фоновых заданий, интеграция с другими сервисами |

Правила:
- Контракты описываются заранее, в ТЗ: REST — OpenAPI, WebSocket и Kafka — AsyncAPI. FastAPI генерирует OpenAPI из кода, контрактные тесты сверяют его с контрактом из ТЗ.
- Синхронный вызов между модулями монолита — вызов публичного API модуля внутри процесса, не HTTP. Вызов идёт через интерфейс, чтобы при выделении модуля в микросервис заменить реализацию на REST или Kafka, не меняя вызывающий код.
- Сейчас Kafka используется только внутри монолита. Внешние участники появятся при выделении модулей в микросервисы. Локальный агент связывается с платформой по WebSocket через HAProxy, Kafka наружу не публикуется.
- Kafka используется, где нужна асинхронность: не нужен немедленный ответ, задача долгая (генерация программы обучения, обработка загруженных материалов, скачивание моделей) или модули нужно развязать.
- Модуль публикует только свои события и только в свои топики. Именование топиков: `<модуль>.<событие>` (TODO: утвердить в SYS-04).
- События, связанные с изменением данных, публикуются через transactional outbox, чтобы не терять и не дублировать их.
- Консьюмеры Kafka идемпотентны. Для необрабатываемых сообщений — ретраи и dead letter topic.
- Схемы сообщений версионируются, изменения обратно совместимы.
- WebSocket обслуживает сам монолит (FastAPI), события между инстансами доставляются через Redis pub/sub. Отдельный брокер (NATS и т.п.) для этого не нужен и не используется.
- WebSocket: аутентификация при подключении, единый формат сообщений (тип, ID корреляции, данные), переподключение с восстановлением состояния, в том числе к другому инстансу.

## Масштабирование и состояние

Монолит масштабируется горизонтально: при росте нагрузки поднимаются новые инстансы. Это свойство поддерживается **постоянно**: любая фича должна корректно работать на N инстансах.

Где хранится состояние:

| Состояние | Где | Примеры |
|---|---|---|
| Постоянное | PostgreSQL | пользователи, курсы, программы обучения, прогресс, словари, настройки |
| Файлы | MinIO | материалы учеников, медиа, демо-видео. Метаданные файлов — в PostgreSQL |
| Поисковые индексы (производные) | OpenSearch, Qdrant | полнотекстовый и семантический поиск по курсам, словарям, материалам |
| In-memory (временное, общее для всех инстансов) | Redis | сессии, кэш, лимиты запросов, распределённые блокировки, присутствие онлайн, состояние анонимного быстрого теста, доставка WebSocket-событий между инстансами |
| В памяти процесса или на диске инстанса | **запрещено** | — |

Правила:
- Инстанс не хранит состояние между запросами: ни в глобальных переменных, ни в локальных кэшах, ни в файлах на диске. Любой запрос может попасть на любой инстанс.
- Кэш в памяти процесса допустим только для неизменяемых данных, одинаковых на всех инстансах (например, конфигурация, загруженная при старте).
- Sticky-сессии не используются. Корректность не зависит от того, на какой инстанс попал клиент.
- У всех ключей Redis есть TTL. Потеря Redis не приводит к потере постоянных данных. Долгоживущие данные входа (refresh-токены) хранятся в PostgreSQL, поэтому сбой Redis не разлогинивает пользователей; допустимо потерять кэш, лимиты, блокировки и незавершённый быстрый тест. В Kubernetes Redis работает с репликой и Sentinel, в docker-compose — один экземпляр.
- Конкурентные изменения с разных инстансов не теряются и не дублируются: оптимистические блокировки (версия записи), уникальные ограничения в PostgreSQL, распределённые блокировки в Redis для критических секций.
- WebSocket-событие доставляется клиенту, к какому бы инстансу он ни был подключён (через Redis pub/sub). После переподключения к другому инстансу клиент восстанавливает состояние из Redis и PostgreSQL.
- Задания из Kafka распределяются между инстансами через consumer group. Периодические задачи не выполняются на всех инстансах сразу: запуск через распределённую блокировку или отдельную роль.
- Миграции Alembic выполняются один раз отдельным шагом, а не каждым инстансом при старте. Миграции совместимы с предыдущей версией кода: при обновлении старые и новые инстансы работают одновременно.
- Инстанс можно остановить в любой момент: незавершённые задания Kafka доставит повторно, клиенты переподключатся к другим инстансам.
- Файлы не хранятся на диске инстанса: сами файлы — в MinIO, их метаданные — в PostgreSQL.
- Источник истины — PostgreSQL и MinIO. Индексы OpenSearch и Qdrant производные: они обновляются по событиям Kafka и при потере перестраиваются из источника истины.

**Тесты масштабируемости.** Каждая фича проверяется на стенде из N инстансов монолита (N = 3) за HAProxy с той же конфигурацией, что и при развёртывании (запросы распределяются по кругу), с общими PostgreSQL, Redis, Kafka и остальными контейнерами, которые использует фича. Проверяется, что:
- шаги одного сценария, попавшие на разные инстансы, дают согласованный результат;
- одновременные запросы к одним и тем же данным через разные инстансы не теряют и не дублируют изменения;
- WebSocket-клиент получает события, возникшие на другом инстансе;
- задание выполняется один раз при N потребителях;
- лимиты и блокировки действуют глобально, а не на каждом инстансе отдельно;
- остановка инстанса посреди сценария не ломает сценарий.

## Модульный монолит

Главное правило: **каждый модуль должен быть готов к выделению в отдельный микросервис** без переписывания. Помнить об этом при любом изменении.

### Backend (Python)

- Модули выделяются по бизнес-доменам (bounded contexts), а не по техническим слоям. Предварительная карта модулей — Приложение В в SDD_plan.md, утверждается в SYS-01.
- Каждый модуль — отдельный Python-пакет. Его публичный API — то, что экспортирует пакет верхнего уровня: сервисные интерфейсы, Pydantic-схемы, события. Другие модули импортируют **только** публичный API и никогда не импортируют внутренние пакеты, модели SQLAlchemy или репозитории чужого модуля.
- Каждый модуль владеет своими данными: своя схема PostgreSQL, свои модели SQLAlchemy, свои миграции Alembic. Никаких JOIN'ов, `relationship` и внешних ключей между таблицами разных модулей. Ссылки между модулями — по идентификаторам. В Redis модуль использует только ключи со своим префиксом `<модуль>:`. Также модуль владеет своими бакетами MinIO, индексами OpenSearch и коллекциями Qdrant.
- Каждый модуль подключает свой FastAPI-роутер, свои обработчики WebSocket и Kafka и свою секцию настроек.
- Никаких циклических зависимостей между модулями.
- Границы модулей проверяются автоматически (TODO: import-linter или аналог), нарушение границ ломает сборку.
- Общий код (`shared`/`common`) минимален: только настоящие сквозные вещи. Не превращать его в свалку бизнес-логики.
- Конфигурация модуля изолирована, чтобы его можно было вынести в отдельный сервис.

### Логичность разбиения

Разбиение на модули поддерживается **постоянно** в ходе разработки, а не только на старте:
- в каждом ТЗ определять, к какому модулю относится новая логика. Если не подходит ни один, предложить новый модуль;
- если модуль разрастается и берёт чужую ответственность или два модуля слишком часто обращаются друг к другу, предложить перенос логики, разделение или объединение модулей;
- изменение разбиения сначала фиксируется в SYS-01 (карта модулей), затем выполняется рефакторинг при зелёных тестах;
- в конце каждого этапа проводится ревью разбиения (SDD_plan.md, раздел 8).

### Frontend

- Модули (feature-модули) повторяют доменное разбиение бэкенда.
- Модули не импортируют друг друга. Связываются они только на уровне `src/app` (роуты, страницы). Контроль — правило ESLint `import/no-restricted-paths` с зоной на каждый модуль и `import/no-cycle`.
- Barrel-файлы (`index.ts` с реэкспортом) не используются: по рекомендации bulletproof-react импорт идёт напрямую из файлов, это не мешает Vite оптимизировать сборку.
- Модуль владеет своими компонентами, API-хуками к соответствующему backend-модулю, состоянием и WebSocket-подписками. Роуты страниц лежат в `src/app/routes`.
- Общие UI-компоненты, i18n, тема, утилиты, WebSocket-соединение — в отдельном shared-слое без бизнес-логики.
- Структура должна позволять позже вынести модуль в микрофронтенд.
- Интерфейс адаптивный: телефон, планшет, десктоп. Нативных мобильных приложений пока нет, но API и аутентификация проектируются так, чтобы добавить их без переделки.
- Собранная статика раздаётся Nginx. К бэкенду frontend обращается только через HAProxy по относительным путям (`/api`, `/ws`).

## Развёртывание

С самого начала поддерживаем **оба** варианта, и они должны оставаться в синхронизированном состоянии:

1. **docker-compose** — локальная разработка и простые установки.
2. **Kubernetes (Helm charts)** — продуктивные и масштабируемые установки.

Правила:
- Любое изменение, затрагивающее развёртывание (новый сервис, переменная окружения, порт, volume, секрет, зависимость, топик Kafka), вносится **одновременно** в docker-compose и в Helm charts.
- Оба варианта содержат одинаковый состав контейнеров (см. «Состав контейнеров»). Отличия: Vault есть только в Kubernetes; Redis в Kubernetes работает с репликой и Sentinel, в docker-compose — один экземпляр.
- Монолит запускается в N экземплярах за HAProxy: в docker-compose — несколько реплик, в Helm — несколько реплик (по умолчанию не меньше 2) и автомасштабирование (TODO: HPA). Sticky-сессии не используются.
- Миграции Alembic выполняются отдельным шагом до запуска новых инстансов: отдельный сервис в docker-compose, Job или init-контейнер в Helm.
- Конфигурация и секреты передаются монолиту через переменные окружения или файлы. В docker-compose секреты берутся из `.env` (не коммитится), в Kubernetes — из Vault. Boilerplate умеет сам читать секреты из Vault, а без Vault берёт их из переменных окружения, поэтому код монолита в обоих вариантах одинаковый (способ для Kubernetes — ADR-013).
- Структуру Helm charts закладывать с учётом будущего разделения на микросервисы.
- docker-compose — `deploy/docker-compose/docker-compose.yml` (сейчас бэкенд и его инфраструктура), Helm — TODO: `deploy/helm/`. Роли запуска монолита из одного образа (API, воркеры Kafka) — утвердить в ADR-004.

### Состав контейнеров

Минимальный состав. Вспомогательные контейнеры (миграции Alembic, экспортёры метрик для PostgreSQL, Redis, Kafka) добавляются по мере необходимости.

|---|----------------------------------------------------------------------------------------------------------------------------------|---|---|

| Python-монолит | backend (FastAPI), N экземпляров                                                                                                 | да | да |
| Redis | in-memory состояние                                                                                                              | да | да, с репликой и Sentinel |
| PostgreSQL | постоянное состояние                                                                                                             | да | да |
| Kafka | события между модулями, очереди заданий                                                                                          | да | да |
| Nginx | раздача статики frontend                                                                                                         | да | да |
| MinIO | S3-хранилище файлов                                                                                                              | да | да |
| Prometheus | сбор метрик                                                                                                                      | да | да |
| Grafana | дашборды, алерты, просмотр логов из OpenSearch                                                                                   | да | да |
| OpenSearch | хранение всех логов обязательно, полнотекстовый поиск при необходимости                                                          | да | да |

### Маршрутизация через HAProxy

HAProxy — единственная точка входа снаружи. Предварительная схема (TODO: утвердить в ADR-012):
- TLS завершается на HAProxy. В Kubernetes HAProxy публикуется через Service типа LoadBalancer (облачный балансировщик или MetalLB), его конфигурация та же, что в docker-compose;
- `/api/*` → инстансы монолита (REST);
- `/ws/*` → инстансы монолита (WebSocket, с увеличенными таймаутами соединения);
- остальные пути → Nginx со статикой frontend;
- медиатрафик видеосвязи (WebRTC) идёт напрямую на медиасервер, мимо HAProxy; через HAProxy проходит только сигнальный канал (TODO: ADR-015);
- доступ клиентов к файлам в MinIO (presigned URL через HAProxy или отдача через монолит) — TODO: решить в ADR-007.

HAProxy проверяет инстансы монолита по readiness-эндпоинту и исключает из балансировки те, что не прошли проверку. Эндпоинты метрик и health наружу не публикуются.

## Наблюдаемость

- **Метрики**: монолит отдаёт метрики в формате Prometheus на `/metrics`. Технические: запросы, задержки, ошибки, WebSocket-соединения, лаг консьюмеров Kafka, пулы соединений. Плюс бизнес-метрики модулей. Prometheus собирает метрики со всех инстансов.
- **Health-эндпоинты** (аналог actuator, есть в boilerplate): `/v1/health` — процесс жив; `/v1/ready` — инстанс готов принимать трафик. Их используют HAProxy, probes в Kubernetes и healthcheck в docker-compose.
- **Логи**: структурированные JSON-логи в stdout. Поля: время, уровень, модуль, ID инстанса, ID запроса (корреляции). Логи собирает Fluent Bit и доставляет в OpenSearch. Просматриваются логи в Grafana через источник данных OpenSearch. Секреты и персональные данные в логи не пишутся.
- **Дашборды и алерты** Grafana хранятся в репозитории как код и разворачиваются в обоих вариантах.

make test-cov         # тесты с покрытием (порог 75%)
make check            # format → lint → mypy → security → tests (Definition of Done)

make makemigration name="add_x"                      # создать миграцию

make compose-down     # остановить их

## Ключевые архитектурные требования

- **LLM-агностичность**: любая функция должна работать с любым подключённым провайдером (внешним или локальным). Не завязываться на API конкретного вендора вне слоя адаптеров. То же относится к провайдерам синтеза и распознавания речи.
- **i18n с первого дня**: язык интерфейса и изучаемый язык — разные настройки. Поддержка LTR и RTL, арабской вязи, иероглифов. Не хардкодить строки UI. Языки интерфейса на старте: русский, английский, арабский.
- **Уровни CEFR (A1–C2)**: текущий, рабочий и целевой уровень — отдельные сущности; прогресс ведётся параллельно по каждому изучаемому языку.
- **Расширяемость**: плагины (UI, языки, LLM/серверы), MCP, скилы — закладывать точки расширения в каркас, даже если сами плагины будут на этапе 7.
- **Разграничение ролей**: права проверять на сервере, не только в UI.
- **Персональные данные**: 152-ФЗ — хранение на территории РФ, согласия, удаление по запросу, отдельное согласие на передачу данных зарубежным LLM-провайдерам. На старте только пользователи 18+. Секреты, API-ключи и персональные данные не попадают в логи.
- **API-ключи учеников** к внешним LLM хранятся на сервере в зашифрованном виде. Ключ шифрования — в Vault (Kubernetes) или `.env` (docker-compose).
- **Горизонтальное масштабирование**: монолит не хранит состояние в инстансе и масштабируется запуском новых инстансов (раздел «Масштабирование и состояние»).

- Backend пишется только на Python (FastAPI, SQLAlchemy, Alembic). Другие языки на бэкенде не предлагать и не использовать.
- Бэкенд развивается из boilerplate в `src/backend/py-monolyth`: соблюдать `src/backend/py-monolyth/CLAUDE.md` с учётом «Отличий проекта от boilerplate», новый код сначала генерировать скаффолдером, перед коммитом прогонять `make check`.
- Фронтенд развивается из boilerplate в `src/frontend`: соблюдать `src/frontend/docs` с учётом «Отличий проекта от boilerplate» фронтенда, перед коммитом прогонять `yarn lint`, `yarn check-types`, `yarn test`.
- Все исходники — только внутри `src/` в подпапках по компонентам.
- Тип взаимодействия выбирать по разделу «Взаимодействие»: REST, WebSocket или Kafka.
- Метрики, логи и health-эндпоинты делать по разделу «Наблюдаемость».
- Новые контейнеры добавлять одновременно в docker-compose и Helm и отражать в таблице «Состав контейнеров».

- Работать только по утверждённой спецификации. Нет спецификации — сначала предложить её черновик по шаблону.
- Порядок работы над фичей: спецификация → тесты (red) → код (green) → рефакторинг → проверка по Definition of Done.
